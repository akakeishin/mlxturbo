# KERNEL-BRIEF-MOE-GDN — MoE ルーティングと GDN (2026-08-27)

hyper-connections の次の標的。前提と道具は docs/KERNEL-HANDOFF-HC.md を先に読むこと。

## 着手前の見立て (実装より先に測る)

`tools/ablate.py` の段は**部品ごと消す**ので、消えた時間には重みの読み出しが
混ざっている。融合カーネルで削れるのは起動費用のぶんだけなので、そこを
分けないと取り分を見誤る。

層構成: MoE は全 48 層、GDN は 36 層 (`full_attention_interval=4` なので
4 層に 1 回は full attention)。expert は 6bit、GDN の射影は 8bit。

| 部品 | ablate 実測 | ablation が消す重み | 帯域下限 (400GB/s) | 削れる余地 |
|---|---|---|---|---|
| hyper-connections | 20.93ms | 0.62GB | 1.6ms | 19.4ms (16.2ms 回収済み) |
| **MoE** | 11.0ms | 1.82GB | 4.6ms | **約 5-6ms** |
| **GDN** | 8.0ms | 1.51GB | 3.8ms | **約 3-4ms** |

内訳の根拠:

- MoE: expert は top_k=10 / 512、1 expert あたり 3 x 2560 x 640 を 6bit で
  36.86MB/層/token。48 層で 1.77GB。gate (2560x512) を足して約 1.82GB
- GDN: `in_proj_qkv` (2560 -> 10240) 26.2MB + `in_proj_z` (2560 -> 6144)
  15.7MB を 8bit で、36 層で 1.51GB。`out_proj` は ablation でも残るので
  この数字には入っていない

**HC は 93% が起動費用だったが、こちらは半分以上が重み読みで削れない。**
BRIEF-HC の「MoE と GDN で 45 tok/s」は楽観的。両方うまくいって
34.29 -> 26-27 ms/token、**37-38 tok/s 圏**が現実的な線。

## 実測: MoE の内訳 (2026-08-27、tools/ablate_moe.py)

4 段 x 3 ラウンドを交互に測って中央値。振れ 0.04-1.82ms、合計 11.09ms が
`ablate.py` の 11.0ms と一致するので測定は健全。

| 段 | 費用 | 融合で削れるか |
|---|---|---|
| ルーティング (gate -> topk -> softmax) | **2.69ms** | 削れる |
| shared gate (sigmoid) | **0.24ms** | 削れる |
| expert 行列積 (switch_mlp) | **8.16ms** | 重み読み。削れない |
| 合計 | 11.09ms | |

**融合で狙えるのは 2.93ms だけ。**着手前の見立て (5-6ms) は外していた。
expert 行列積の 8.16ms は帯域下限 4.6ms に対し実効 220GB/s 相当で、
MLX の `gather_qmm` は既に妥当な線に乗っている。

ルーティングの 2.69ms は 48 層で割ると 56us/層、5 op なので 11us/op。
既知のディスパッチ費用そのもの。1 本に畳めば 2ms 前後は回収できる見込み。

### これで優先順位が変わる

`ablate.py` の「残り (embed/lm_head/norm/dispatch) 10.1ms」が、MoE
ルーティングの 4 倍近い未解明ブロックになった。中身は embed / lm_head /
最終 norm だけでなく、**12 層ぶんの full attention 本体**と各層の
hyper-connection の合流演算 (`hyper + (x[..., None, :] * inject[..., None])`)
が入っている。`ablate.py` が外しているのは QSA indexer だけ。

**2.9ms のために MoE カーネルを書く前に、ここを割ること。**
`tools/ablate_gdn.py` が GDN の 5 段分解と full attention の切り出しを測る。

## 先に測ること

`tools/ablate_moe.py` で MoE の 11ms を 3 つに割る。

    そのまま
    - ルーティング (gate -> argpartition -> softmax -> take_along_axis)
    - shared gate (shared_expert_gate -> sigmoid -> 乗算)
    - expert 行列積 (switch_mlp ごと)

融合で狙えるのは上 2 段。expert 行列積は MLX の `gather_qmm` が既に 1 本の
カーネルで、中身は重み読みなので触っても減らない。

GDN 側も同様に、`gated_delta_update` (既にカーネル化されている
`fastmlx/kernels/gated_delta_states.py` を参照) と射影・conv1d・
RMSNormGated を分けてから決める。

## 実測: lm_head とメモリ圧 (2026-08-28)

主セッションの「lm_head も削れる」を受けて測った。**結果は「カーネルでは
削れない。環境が原因」**。

| | 時間 (M=1) | 実効帯域 |
|---|---|---|
| lm_head、98GB モデル常駐 | 6.17ms | 109 GB/s |
| **lm_head、モデル非常駐** | **2.14ms** | **315.6 GB/s** |
| 経路 nocap / mma を強制 | 6.30 / 6.32ms | 効果なし (0.98x) |
| 4bit に打ち直し (675 -> 358MB) | 3.65ms | 98 GB/s |

同じカーネル・同じデータで常駐の有無だけが違い、**2.9 倍**。MLX の qmv は
既に 315 GB/s 出せている。**lm_head に自作カーネルを書く価値は無い。**

`fastmlx/kernels/dispatch.py` の経路表に `(2560, 248320)` が無いのは事実だが、
強制的に nocap / mma を通しても 0.98x で効かない (既存の較正は M=5..16 の
投機検証幅向けで、M=1 のデコードには合わない)。

### これはモデル全体の話でもある

デコード 34.29 ms/token は 1 トークンあたり約 4.7GB の重み読みに対して
**実効 137 GB/s** 相当。非常駐時に出ている 315 GB/s の 43% しかない。
このマシンは累計 swapout 34M ページ (543GB) で、98.4GB を 128GB に載せると
常時メモリ圧の下にある。

**残るカーネル融合の余地 (MoE ルーティング 2.7ms など) より、モデルを
小さくする方が効く可能性がある。**v-96 (70.8GB) レシピが該当。
これはレシピ側の判断なので親に委ねる。

> 注意: 直接の証拠は lm_head の常駐あり/なし比較 (2.9x) だけ。モデル全体が
> 同じ倍率で効いているとは確かめていない。断定しないこと。

## 実測: 別実装由来の 2 つの仮説を検証した (2026-08-28)

親が `ddalcu/mlx-serve` (MIT、Zig) を読んで立てた 2 つの仮説を、こちらの環境で
測った。**どちらも再現しない。**引用された数字はあちらの環境・あちらのモデルの
ものと考えるのが妥当。

### 仮説 1: stock の gather_qmm は理想の 3 倍のバイトを動かしている -> 否

`tools/probe_gather_qmm.py`。bank=[512,640,2560] 4bit、x=[1,1,2560]、top_k=10。

**バンク全体は読んでいない。**エキスパート数を 64 -> 512 に振っても時間は
ほぼ平ら (n=512 で 229 GB/s)。

同じバイト数を動かす密な量子化行列積との比:

| top_k | gather_qmm | 密 | 倍率 | 理想MB |
|---|---|---|---|---|
| 1 | 28.4us | 8.5us | 3.33x | 0.82 |
| 5 | 28.2 | 13.0 | 2.17x | 4.10 |
| **10** | **33.8** | **23.5** | **1.44x** | 8.19 |
| 20 | 54.6 | 45.3 | 1.21x | 16.38 |

**3.33x が出るのは top_k=1 のときだけで、バイト数の倍率ではなく固定費。**根拠:

- top_k=1〜5 で時間がほぼ平ら (28.4 / 29.2 / 28.2us)。バイト数 5 倍でも変わらない
- top_k=10 -> 20 の傾きは gather 2.08、密 2.18 us/expert で**一致**。
  大きい top_k ではバイトあたりの速度が同じ

固定費は密との差で 1 回あたり約 10us。3 投影 x 48 層 = 144 回で
**上限 1.5ms/token**。ブリーフの ~2.5ms には届かない。

なお `take + qmm` は 80-103us で gather_qmm (24-58us) より**遅い**。
あちらと優劣が逆で、take 経路に利は無い。

### 仮説 2: lm_head は巨大 N のタイル問題 -> 否

`tools/probe_lm_head_tiling.py`。**N を分割しても速くならない。**
同じバイト数を k 本に割って動かす:

| 分割数 | 非常駐 | 常駐 (98GB) |
|---|---|---|
| 1 | 263.5 GB/s | 224.2 GB/s |
| 2 | 250.8 | 202.6 |
| 8 | 253.5 | 246.4 |
| 16 | 237.7 | 240.9 |

非常駐では割るほど単調に悪化。常駐でも最良 1.10x で、2 分割が 0.90x と
非単調 (雑音の幅)。**タイルの潰し合いは観測できない。**

単体の絶対値は親の測定と一致する (こちら 1.96ms/263.5 GB/s、親 1.87ms/256 GB/s)。
食い違うのは「モデルの中で遅い」ことの**原因**の解釈だけ。

### 残る説明はメモリ圧

lm_head は非常駐 315 GB/s、常駐 (アイドル) 224 GB/s、実デコード中 104 GB/s。
フォワード中は他の重みが同時にキャッシュを流れるので、そこで落ちている。
**カーネルの書き方では直らない。**

## 引き継ぐ規律 (HC で踏んだもの)

- **`tools/biglock.sh` を必ず通す。**98GB を 2 本載せると先に走っていた方が
  落ちる。一時スクリプトでも `tools/` に置くこと (scratchpad だと親の
  biglock から見えない)
- **ablate は静かなときにペアで。**「PLE を切ると遅くなる」が出た回は捨てる。
  内部整合の目安は MoE 約 11ms、GDN 約 8ms、残り約 10ms
- **合成ベンチは重みを回す。**同じ重みを使い回すとキャッシュに乗って
  融合が不利に出る。絶対値は時間帯で 20-30% 動くので、別々の時刻に
  測った数字を比べない
- **MLX の bf16 reduce は bf16 で逐次加算する。**fp32 で溜めて最後に丸める
  形ではない。MoE の `.sum(axis=-2)` と softmax でここを踏む
- **MLX の bf16 sigmoid はビット一致させられない。**数値の受け入れは
  logits の相対誤差ではなく KLD で見る。対照 (該当 op だけ fp32 にした、
  素より正確な版) を必ず並べて測ること。向きが逆なら実装の誤りを疑う
- **ablation の変種では、外した op の入力が下流で消費され続けているか
  確かめる。**MLX は遅延評価なので、消費されない入力はそれを作る計算まで
  消える。`self.in_proj_z(x)` の戻り値を捨てて「RMSNormGated 2.37ms」という
  4 倍過大な値を出し、空振りのカーネルを 1 本書いた
- **`mx.fast.metal_kernel` はストライドを見ない。**行優先の連続配置を
  仮定して読むなら `mx.contiguous` を通すこと。非連続なビューが来る
- **カーネルの照合は「その場で」やる。**テンソルを捕まえてから `mx.eval`
  して比べると、eval が連続化して上のバグを隠す。全呼び出しを見ること
  (最初の数回だけ見て「ビット一致」と誤報告した)
- **`--ngram` を忘れると load が「Missing 128 parameters」で落ちる。**
  vendored arch は import 時に `FASTMLX_NGRAM_DISK` を読む。新しい道具を
  書くたびにこれを踏んだ (2 回)
