# POSITIONING — 何を看板にするか (2026-08-30、同日に全面改訂)

公開初日に [oMLX](https://github.com/jundot/omlx) を見つけて一度この文書を書いた。
その数時間後に [mlx-serve](https://github.com/ddalcu/mlx-serve) が見つかり、
**書いたばかりの根拠が 3 つとも崩れた**ので、全面的に書き直す。

崩れた側の記録も残す。同じ読み違いを繰り返さないため。

## 崩れたもの

### 1. 「3 プロトコルを話せるのはほぼ唯一」— 誤り

mlx-serve は OpenAI / Anthropic Messages / OpenAI Responses / Ollama を
**同一ポートで 4 つ**出している (実機で `/v1/responses` の存在を確認済み)。
こちらが立てるつもりだった土俵に先客がいた。

前版に「oMLX が Anthropic 互換を足したら土俵が消える」と反転条件を書いていた。
条件は正しかったが、**別の実装が既に満たしていることを調べていなかった**。
競合を 1 つ見つけた時点で探索をやめたのが誤り。

### 2. 「128GB 機でメモリに余裕がある」— 誤り

比較対象を oMLX 推奨の 106.3GB に取っていた。mlx-serve 推奨の
ddalcu パックは trunk 68GB + n-gram 表 30GB を mmap で、**常駐 約 70GB**。
こちらの v-l は 77GB。**向こうの方が小さい。**

### 3. 「速度で負けたとは言えない」— 決着し、負けていた

前版では機材も課題も違うので比較が成立しないとして保留した。保留の判断自体は
正しかった。同一機・同一課題で測り直した結果 (`docs/VS-MLX-SERVE.md`):

| | mlx-serve | mlxturbo |
|---|---|---|
| decode 中央値 (31 課題) | 64.0 tok/s | 43.3 tok/s |
| decode (文脈 48k) | 43.3 tok/s | 30.2 tok/s |
| cold prefill (48k) | 55.6s | 99.5s |
| 温まった TTFT | 0.2 秒前後 (文脈長によらず) | 2.6 - 6.6 秒 |

## 残っているもの

**速さの土俵では負けている。プロトコルの土俵は消えた。メモリの優位も無い。**
それでも手元に残るものが 2 つある。

### 分布保証

投機に Block Verification (arXiv:2403.10444) を使っていて、ドラフトを混ぜても
出力の分布が非投機と厳密に一致する。

対して mlx-serve は、速さのための代償を自分で書いている。

- `--decode-attn-quant` (**既定 ON**): "LOSSY: a real requantization"
- `--ane-prefill`: "int8/fp16, lossy"

**既定で品質を削っている。**それが悪いという話ではない (多くの用途で見えない)。
ただし「どれだけ削れたか」を言える実装は、いまのところ他にない。

### 品質の実測

焼き直しレシピごとに KLD を測って出している (v-fast6 で KLD 0.00378 など)。
量子化やカーネル変更の前後を数字で示す作法が積んである。

## 判断

**速さで抜くことを目標に置く。**ただしそれ単独では、追いついた頃に相手が先に
行っている (mlx-serve は 378 commit、Flash-Next 対応を 2026-08-29 に入れてきた)。

だから同時に、**「その速さで出力はどれだけ変わったか」を測って言える**状態を
保つ。速度の数字と品質の数字を必ず対にして出す。これは相手が lossy を既定 ON に
している限り、模倣しにくい。

## やること (差の大きい順)

1. **温まった TTFT** — 10-30 倍の差。原因は特定済みで、再利用の上限を
   `len(prompt)-1` に切っているせいで、プロンプト末尾のチェックポイントが
   常に射程外に落ちる。設計の穴であって速度の問題ではない
2. **MTP depth** — 相手は 1 ラウンド最大 6-8 トークン、こちらは 1。受理率 0.76 で
   depth 1 なら上限が 1.7 倍前後にしかならない
3. **prefill チャンク幅** — 相手 4096、こちら 2048
4. **ANE prefill** — 相手は各チャンクの dense MLP 行の 4 割を Neural Engine に
   逃がす。`docs/research/ANE-PREFILL-BRIEF.md` のレーンはこの形を狙う
5. **Ollama API 互換** — `docs/INTEGRATIONS.md`

## やらないこと

- **GUI** — GUI が要る層は LM Studio と MLX Core を既に使っている。
  完成度の勝負になり、こちらの持ち物と関係しない領域でいちばん人手が要る
- **vision 対応** — 変換のやり直しが要る。mlx-serve も oMLX も対応済み
- **追加のカーネル** — 自作した融合 HC カーネルは実測 1.00-1.01x で効いていない
  (v-l と v-fast6 の両方で確認)。看板から外すこと

## 判断が反転する条件

1. 上の 1-3 を入れても decode が 1.2 倍以内に詰まらない → 速さの目標を降ろし、
   品質計測に寄せるか、貢献側へ回る道を検討する
2. mlx-serve が品質の実測を出し始める → 残った差別化が消える
3. M5 世代が普及する → prefill は第三者ベンチで M3 Max 比 3-4 倍。
   prefill 側の作り込みの価値が相対的に下がる
