# POSITIONING — 何を看板にするか (2026-08-30、同日に全面改訂)

公開初日に [oMLX](https://github.com/jundot/omlx) を見つけて一度この文書を書いた。
その数時間後に [mlx-serve](https://github.com/ddalcu/mlx-serve) が見つかり、
**書いたばかりの根拠が 3 つとも崩れた**ので、全面的に書き直す。

崩れた側の記録も残す。同じ読み違いを繰り返さないため。

## 崩れたもの

### 1. 「3 プロトコルを話せるのはほぼ唯一」— 誤り

mlx-serve は OpenAI / Anthropic Messages / OpenAI Responses / Ollama を
**同一ポートで 4 つ**出している (実機で `/v1/responses` の存在を確認済み)。
こちらが立てるつもりだった土俵に先客がいた。

前版に「oMLX が Anthropic 互換を足したら土俵が消える」と反転条件を書いていた。
条件は正しかったが、**別の実装が既に満たしていることを調べていなかった**。
競合を 1 つ見つけた時点で探索をやめたのが誤り。

### 2. 「128GB 機でメモリに余裕がある」— 誤り

比較対象を oMLX 推奨の 106.3GB に取っていた。mlx-serve 推奨の
ddalcu パックは trunk 68GB + n-gram 表 30GB を mmap で、**常駐 約 70GB**。
こちらの v-l は 77GB。**向こうの方が小さい。**

### 3. 「速度で負けたとは言えない」— 決着し、負けていた

前版では機材も課題も違うので比較が成立しないとして保留した。保留の判断自体は
正しかった。同一機・同一課題で測り直した結果 (`docs/VS-MLX-SERVE.md`):

| | mlx-serve | mlxturbo |
|---|---|---|
| decode 中央値 (31 課題) | 64.0 tok/s | 43.3 tok/s |
| decode (文脈 48k) | 43.3 tok/s | 30.2 tok/s |
| cold prefill (48k) | 55.6s | 99.5s |
| 温まった TTFT | 0.2 秒前後 (文脈長によらず) | 2.6 - 6.6 秒 |

**2026-09-02 に取り直した (上の表は 2026-08-30 のもの)。**
`bench/vs_mlx_serve.py` を 3 箇所直したうえでの実測
(`bench/results/vs-mlx-serve-0902-inter.json`):

| 文脈 | 冷 TTFT serve / turbo | 温 TTFT serve / turbo | decode tok/s serve / turbo |
|---|---|---|---|
| 0 | 0.05 / 0.35 | 0.76 / 1.12 | 52.0 / 51.9 |
| 4k | 5.89 / **8.11** | 0.89 / **1.16** | 49.0 / **46.3** |
| 17k | 22.2 / **31.7** | 0.91 / **1.30** | 50.4 / **44.4** |
| **50k** | 58.1 / **102.4** | 2.19 / **1.72 (勝ち)** | 41.2 / **42.9 (勝ち)** |

**温 TTFT の 10-30 倍差は無くなっている** (1.12-1.30 対 0.76-0.91)。
**50k でだけ温 TTFT と decode が逆転する。**長文脈ほど疎性 (QSA / gather
attention) が効く。

**直したハーネスの不具合 3 つ**: (a) `model` にプレースホルダを送って 404、
(b) 思考 (`reasoning_content`) を数えず長文脈が nan / 0 tok、(c) 温めに測定と
同じプロンプトを使って「冷」が冷えない。**この間に取った数字は信用しないこと。**

## 分布保証は要件から外す (2026-08-30 決定)

一度は「残った差別化」と書いたが、**欲しがる層が狭すぎる**ので降ろす。

欲しがるのは、モデルの品質を測っている人 (サーバーが分布を動かすと、測って
いるのがモデルなのかサーバーなのか分からなくなる)、蒸留や学習データを local
モデルで作る人、logprob を使う人、再現性が要る人。**対話とコーディング
エージェントの利用者、つまり大多数は欲しがらない。**mlx-serve が
`--decode-attn-quant` を既定 ON にしていても、使っていて気づく人はほぼいない。

したがって:

- **既定は速い側に置く。**厳密同一分布 (Block Verification) は、安く分岐で
  残せるなら残す程度。速さと引き換えなら捨てる
- **MTP depth を上げる際、受理を緩めてよい。**厳密同一分布を保ったまま depth を
  上げるのは難しいが、緩めれば depth 6-8 が現実的になる。競合が 2.3 倍を
  出しているのはおそらくそこ
- **ANE prefill の lossy も許容する** ("int8/fp16, lossy")

**品質の計測はやめない。**看板から外すだけ。何をどれだけ削ったかを知らずに
削るのは別の話で、KLD は測り続ける。既定を速い側に置いたうえで、数字は持つ。
