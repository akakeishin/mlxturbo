## 0. 何を作っているか

- mlxturbo (`mlxturbo/`)。MLX の推論エンジン + OpenAI / Anthropic 互換サーバー (`mlxturbo serve`)。GitHub / PyPI / HF に公開済み (MIT)。
- 位置づけ (ユーザー 2026-09-04 11:05): **「mlx-lm の LLM 特化版」が最も近い。**同じ重み・同じ形式・同じ品質で、契約で当たる部品によって新しい族に 8〜9 割ついていく。
- 目標 (ユーザー 11:10): **皆が (意識してもしなくても) 使う推論エンジン** = 製品が中に入れるエンジン。看板 (名前) は架け替えてよい。
  条件 4 つ: (1) 同じ重みで負けない (族専用パック・独自形式に依存しない)、(2) 族の追従、(3) 入れ替えやすさ (OpenAI 互換 HTTP + mlx-lm と同じ Python API)、(4) 品質を測って出す。
- 相手: mlx-serve (Zig、族ごとの手調整、Flash-Next の本命の相手)、oMLX (GUI 一体・全モダリティ)、MTPLX (専用パック)、Mirai / uzu (独自形式 + 蒸留量子化 + 学習 draft、別重みなので参考点)。**比較は相手の推奨設定で公平に測る。**
- 本番の機体は M3 Max 128 GB。**NAX 対応機が本番の目標機**で、自前カーネルは NAX 機では auto=off (NAX 専用命令は使わない)。NAX 機で A/B を取り直すまで自前カーネルの取り分は M3 Max の数字。

## 6. 計測で守ること (詳しくは CLAUDE.md と memory の写しの罠 1〜20)

- 1 プロセス内で交互に測る。起動直後の 1 行目は +7〜9% 遅い。tok/step は複数プロンプト × 512 の平均でだけ。
- 温キャッシュの micro を信じない。連鎖 micro は重みを 100 MB 超巡回させて冷やす。op 1 本ごとの `mx.eval` は往復 165〜270 us が床になる (罠 19)。
- 部品計測は「部品和 ≈ 壁時計」を確認する。ablate の積み上げは過大評価。
- I/O を含む A/B はページキャッシュを共有する (プロセスを分けても)。
- 熱で 25% 落ちる。絶対値は冷えた状態で短く、差は長い連鎖で。
- 判定基準は測る前に宣言する。測る前に説明を組み立てない (5 仮説 5 外れの日がある)。
