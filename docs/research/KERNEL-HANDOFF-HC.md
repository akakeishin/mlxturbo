# KERNEL-HANDOFF-HC — hyper-connections の融合カーネル (2026-08-27)

`docs/KERNEL-BRIEF-HC.md` のミッションの結果。実装は
`fastmlx/kernels/hyper_connection.py`、入口は `fastmlx/fused.py` の
`enable_hyper_connection_kernel()` / `disable_hyper_connection_kernel()`。既定は off。

```python
from fastmlx import fused
fused.enable_hyper_connection_kernel()
```

## 結論を先に

| 受け入れ基準 | 結果 |
|---|---|
| 1. logits 相対誤差 1e-3 未満 | **基準を取り下げ、2 に一本化した** (下の「対照実験」と「決定」) |
| 2. KLD が融合なしと 1e-5 以内 | 字義どおりには未達 (0.00260 -> 0.00253、差 7e-5)。ただし **KLD は素より下がった**。1e-5 は対照でも届かない (下の「品質」) |
| 3. hyper-connections の寄与 5ms 未満 | **達成 20.93 -> 4.76ms** (測定条件は下の注) |
| 4. 既定は off | 達成 |

逐次デコードは **51.96 -> 34.29 ms/token (19.25 -> 29.16 tok/s)、-17.67ms**。

ablate の内訳 (v-stream + n-gram サイドカー、融合なし -> 融合あり):

| 部品 | 融合なし | 融合あり |
|---|---|---|
| MoE ルーティング | 11.00 | 11.12 |
| **hyper-connections** | **20.93** | **4.76** |
| GDN | 7.99 | 8.09 |
| 残り | 10.07 | 10.12 |

BRIEF の見立ては「19.9ms を 2ms 前後へ」だったが、**2ms は構造上出ない**。
下限は「カーネル 2 本 x 実モデルでの起動費用 ~15us + 演算 ~17-20us」で、
1 本に畳むにはグリッド全体のバリアが要るため不可能。4.76ms が
この構造での実質的な底に近い。

### 4.76ms をどう測ったか (と、測り直せなかった話)

この値は**融合なし / 融合あり を続けて回した 1 回のペア**から取っている。
内部整合が取れている回:

| | 融合なし | 融合あり |
|---|---|---|
| MoE | 11.00 | 11.12 |
| GDN | 7.99 | 8.09 |
| 残り | 10.07 | 10.12 |

MoE・GDN・残りが両側で揃っているので、hyper-connections の差
(20.93 -> 4.76) は信用できる。

**ただしこのペアは mean 修正の前のコードで測っている。**修正後に 2 回
測り直したが、どちらもマシンが熱で劣化していて整合しなかった
(1 回目は「PLE を切ると遅くなる」、2 回目は hyper-connections が -0.77ms)。
代わりに次の 2 つで裏を取った:

- mean 修正の速度影響を同一プロセス内の A/B で測ると 2us/call
  (96 回で 0.2ms) で、しかもその差自体が雑音に埋もれている
- `tools/hc_equiv_test.py` は融合なし / ありを**同じプロセスで続けて**
  測るのでドリフトに強い。最終コードで 51.96 -> 34.29 ms/token (-17.67ms)。
  20.93ms あった部品が消えた量として整合する

**測り直すなら、マシンが冷えているときにペアで回すこと。**単独の回を
別々の時刻に測って比べても意味がない。

### ablate は他のジョブと同時に走らせると壊れる

この測定は**マシンが静かなときにしか意味を持たない**。親のジョブと重なった
ときの実測例:

```
  そのまま           48.94 ms/token
  - PLE (n-gram)   52.27 ms/token   <- 切ったのに遅くなっている
  MoE 18.83ms / GDN 15.90ms / 残り 13.47ms   (通常は 11.0 / 8.0 / 10.1)
```

**「PLE を切ると遅くなる」が出たらその回は捨てる。**内部整合の目安は
MoE 約 11ms、GDN 約 8ms、残り約 10ms。ここが揃っていない回の
hyper-connections の値は読まないこと (この回は 2.25ms という*良すぎる*
値が出ていて、うっかり採用しかねなかった)。

n-gram のページキャッシュが冷えていると「そのまま」行だけ跳ねる
(187ms を観測)。hyper-connections の差分は PLE を切った後の段どうしで
取っているので、そこは影響を受けない。

## 何を作ったか

`GatedResidual.__call__` の中身 (約 15 op) を **Metal カーネル 2 本**に畳んだ。

```
hc_pre   レーンごとの rms -> normed -> down(10240->320) -> silu、ついでに inject
hc_post  up(320->10240) -> sigmoid -> レーン重み付き平均
```

### なぜ 1 本にしなかったか

`down` の全出力が揃わないと `up` を始められない。Metal にグリッド全体のバリアは
無いので、この境目は必ずカーネルの切れ目になる。1 スレッドグループに全部
押し込めば 1 本にはできるが、量子化重みは down/up 合わせて 6.5MB あり、
1 スレッドグループでは帯域を引き出せない。GPU を遊ばせてまで起動を 1 回
減らす取引にはならない。

`hc_pre` はレーンの rsqrt を副産物として書き出し、`hc_post` がそれを受け取って
normed を組み直す。`hc_post` の出力 j は入力の `(l*d + j)` しか見ないので、
組み直しても hyper と norm_weight をちょうど 1 回ずつ読むだけで済む。

### 起動 1 回の値段を測ってから決めた

`mx.fast.metal_kernel` の限界ディスパッチ費用は **3.9us/回**で、素の
elementwise op (5.6us) より安い。「2 本に畳めば十分」はこの実測から決めた
(チェーン長 2/8/32 の傾きで測定。単発の `mx.eval` には 160us の固定費が
乗るので、単発計測だと 200us に見えて判断を誤る)。

### 形状は全部引数

`hc` / `d` / `lowrank` / `bits` / `group_size` / `eps` / combine の有無を
テンプレート引数で受け、組み合わせごとにカーネルを 1 本コンパイルして
キャッシュする。GLM-5.3-Flash の mHC もこの引数を差し替えれば載る想定。
扱えない形・量子化 (`eligible()` を参照: threadgroup メモリに `hc*d` が
収まるか、bits が 4/8 か、など) はその場で素の実装へ落ちる。

`hyper` の先頭次元は平坦化してグリッドの z に載せているので、S=1 のデコードでも
プロンプトの一括 forward でも同じカーネルが動く。ただし**行ごとに重みを
読み直す**ので、S が大きいと素の GEMM より帯域を食う (S=725 で 1 forward
あたり約 4.7GB x 96 回)。quant_eval の 6865 行ぶんで十数秒の上乗せに収まる
ので実用上は放置しているが、プレフィルを速くしたいなら M ブロック化が要る。

## 対照実験: 受け入れ基準 1 は届かない

`tools/hc_equiv_test.py` に**対照**を仕込んだ。素の実装と MLX の op 単位で
完全に同じで、**sigmoid だけ fp32 で計算する**版。つまり素より*正確*な実装で、
実装の誤りは一切入っていない。

プロンプト一括 forward の最終位置 logits、v-stream + n-gram サイドカー:

| 版 | logits 相対誤差 | top1 |
|---|---|---|
| 素をもう一度 (再現性) | 0.000000 | 一致 |
| **対照: fp32 sigmoid (素より正確)** | **0.072587** | 一致 |
| mx.compile | 0.049643 | 一致 |
| **融合カーネル** | **0.063399** | 一致 |

**素より正確な実装が 7.3% ずれる。**つまりこの数 % は実装の誤りではなく、
bf16 の丸めが 96 段の hyper-connection を通って増幅した量そのもの。
BRIEF が「mx.compile 版は 5% ずれた、原因未特定」と書いていたものの正体は
これで、バグではない。

融合カーネルの 6.3% が対照の 7.3% に近いのは偶然ではない。**デコード形状では
両者はビット一致する** (下の「数値の作り方」)。

裏付けとして、MLX の bf16 `sigmoid` はカスタムカーネル側から**ビット単位では
再現できない**ことも確かめた。安定形 / 素朴形、`metal::exp` /
`fast::exp` / `precise::exp`、中間を bf16 に丸めるか否かの総当たり 20 通りで、
最良でも 40 万要素中 4.1 万個 (10%) が 1 ulp 違う。逆に `down` の量子化行列積
だけは fp32 で溜めて出力で bf16 に丸める形で **MLX とビット一致**しており、
ずれの出どころが sigmoid だけであることは切り分け済み。

### 決定 (2026-08-27、親の判断)

**受け入れ基準 1 は取り下げ、品質は基準 2 の KLD に一本化する。**

理由は上のとおり、logits の相対誤差は実装の正しさではなく bf16 の丸めの
増幅量を測っているため。`bench/quant_eval.py compare` の KLD は分布の距離を
測るので、丸めのカオスをノルム比のようには拾わない。

**この決定が反転する条件**: 融合ありの KLD が融合なしから 1e-5 を超えて
動いた場合。そのときは丸め地点の切り分けに戻る (どの段でずれるかを
素の実装と突き合わせる手順は下の「数値の作り方」の順で追える)。

なお `tools/hc_equiv_test.py` の logits 相対誤差は**捨てない**。**対照
(fp32 sigmoid) より大きくずれていないか**の目安として残す。対照より
大きく出たら、それは丸めではなく実装の誤りを疑う根拠になる。

## 品質 (受け入れ基準 2)

`bench/quant_eval.py compare`、v-stream + n-gram サイドカー、bf16 基準、31 プロンプト:

| 版 | KLD | 素との差 | top1 一致 | delta_p rms |
|---|---|---|---|---|
| 融合なし (基準) | 0.00260 | — | 0.9881 | 0.02114 |
| 対照: fp32 sigmoid | 0.00251 | -7e-5 | 0.9886 | 0.02070 |
| **融合カーネル** | **0.00253** | **-7e-5** | 0.9875 | 0.02077 |

融合なしの 0.00260 / 0.9881 は STATUS.md の記録値と完全一致した。測定系は健全。

**結論: 品質は落ちていない。むしろ素より KLD が下がった。**融合カーネルは
デコード形状で対照とビット一致するので、これは当然の結果
(対照 0.00251 との残り 2e-5 は S>1 経路の差、下の「数値の作り方」参照)。

字義どおりの「1e-5 以内」は満たしていないが、**この基準も届かない**。素と
op 単位で同じで sigmoid だけ fp32 にした対照ですら 7e-5 動く。1e-5 は
このモデルの丸め感度より細かい。

### 途中で踏んだ罠 (mean の蓄積型)

最初の測定では融合ありが **0.00277 (素より +1.7e-4 悪い)** だった。
per-prompt では悪化 18 / 改善 13、振れ幅 ±0.003 と散らばって見えたが、
対照が -9e-5 と*良い*方向へ動いていたので「散らばりだから良し」とは
できなかった。追ったところ `mean(axis=-2)` の蓄積型の取り違えだった
(下の「数値の作り方」7 番)。直して 0.00277 -> 0.00253。

**対照を置いておくと、こういう「向きが逆」に気付ける。**散らばりの
幅だけ見て納得しないこと。

## 数値の作り方 (再実装するとき用)

**まずこれ**: デコード形状 (S=1) では、このカーネルは対照 (fp32 sigmoid 版) と
**ビット完全一致**する (`rel = 0.000e+00`)。つまり「素より正確な実装」に
なっており、素からのずれはすべて素の側の bf16 丸めである。

S>1 では対照と 1.5e-3 ずれる。MLX の `quantized_matmul` が M=1 の GEMV から
GEMM 経路に切り替わり、蓄積の仕方が変わるため。**`quant_eval` は一括 forward
なのでこの S>1 経路を測っている**ことに注意 (生成で走るのは S=1 の方)。

参照が bf16 配列を実体化する地点をすべて再現している。fp32 で通して丸めを
減らすと、正確にはなるが参照からは*遠ざかる*。

1. `mx.fast.rms_norm` の出力 -> bf16
2. `(1 + weight)` 自体 -> bf16 (Gemma 系の規約。`x * w` にすると生成が壊れる)
3. `(rms 出力) * (1+w)` -> bf16
4. 量子化行列積: fp32 で溜めて出力で bf16 (MLX とビット一致を確認済み)
5. `/ hc` -> bf16、`silu` は `x * sigmoid(x)` で 2 段とも bf16
6. up の出力 -> bf16、`sigmoid` -> bf16
7. `u * normed` -> bf16、`mean(axis=-2)` は fp32 で溜めて出力で bf16

### biglock を通すこと (2026-08-27 に踏んだ)

98GB のモデルを読む実行は **必ず `tools/biglock.sh` 経由**で呼ぶ。
このセッションは最初それを知らずに ablate と quant_eval を素で回しており、
親の sweep と同時に 98GB を 2 本載せて自分の compare を落とした
(31 プロンプト中 28 個まで進んで、書き出し前にプロセスごと消えた。
トレースバックが出ないのでこれと分かりにくい)。

**さらに悪い罠**: biglock の「ロック無しの相手」検出は

    pgrep -f "\.venv/bin/python3? (tools|bench)/"

なので、**scratchpad に置いたスクリプトは親から見えない**。ロックを持って
いる親の側が「誰も走っていない」と判断して開始してしまう。この
セッションが最初 scratchpad にドライバを置いていたのがそれで、
`tools/quant_eval_hc.py` に移してある理由でもある。

一時スクリプトでも 98GB を読むなら `tools/` に置くこと。あるいは
biglock 側のパターンを広げる (親の持ち物なので、こちらでは変えていない)。

## チューニング

`(_ROWS_PER_TG, _SIMDGROUPS)` は、重みを 96 組み用意して回し
**キャッシュに乗らない状態**を作った上で 3 回ずつ測って選んだ。

| 設定 | us/call (中央値) |
|---|---|
| 素 | 90.7 |
| **(16, 32)** | **39.9** |
| (32, 32) | 40.9 |
| (8, 16) | 41.2 |
| (16, 16) | 42.4 |
| (8, 8) | 46.2 |
| (4, 4) | 64.3 |

同じ重みを使い回す素朴な合成ベンチだと全部がキャッシュに乗って融合が
不利に出る (最初にそれで「融合の方が遅い」と誤読した)。**重みを回すこと。**

合成ベンチの絶対値は時間帯でまとめて 20-30% 動く (実モデルを回した後は
遅い側に寄る)。**別々の時刻に測った数字を比べないこと。**採否は必ず
背中合わせで測って決める。

### 効いた手・効かなかった手

- **効いた: uint4 でのまとめ読み** (lane あたり 4 byte -> 16 byte)。
  hc_pre 22.2 -> 19.2us、実効帯域 195 -> 227 GB/s
- **効かなかった: `as_type<uchar4>` + `float4` + `dot` によるベクトル逆量子化。**
  hc_pre 19.2 -> 24.8us、hc_post 15.6 -> 28.8us と*遅くなった*ので戻した。
  threadgroup メモリから 4 要素を集めて float4 を組む方が、スカラーの
  FMA 連鎖より高くつく
- **効かなかった: スレッドグループ数を増やす。**(4,4) で 80 本まで増やしても
  改善せず悪化した。スレッドグループごとに normed の staging を作り直す
  ぶんが増えるため

### 何で律速しているか

**帯域ではない。**重みを一切読まない版 (`uint4 wv = uint4(vi)` に差し替え)
でも hc_pre は 19.7 -> 16.6us にしかならない。3.3MB の重み読みは
19.7us のうち 3us しか占めていない。残りは rms の前処理、normed の staging、
threadgroup メモリ読み、要素ごとの逆量子化 ALU、simd_sum の縮約。

つまり次に効くのは「帯域を上げる」ではなく「要素あたりの命令数を減らす」。
ただし上のとおり素直なベクトル化は外している。

## 残っている手

**帯域の最適化は筋が悪い** (上の「何で律速しているか」)。やるなら要素あたりの
命令数を減らす方向。ただし素直なベクトル化は外しているので、次に試すなら:

- 4bit へ落とす。HC の 3 層はレシピで明示的に 8bit を割り当てられている
  (`model.layers.N.*_hyper_connection.*` が `bits: 8, group_size: 64`)。
  4bit なら要素あたりの取り出しは変わらないが読む byte 数が半分になる。
  品質への影響は quant_eval で測れる。**レシピ側の話なので親の判断が要る**
- 冗長読みは重み 6.5MB に対して約 0.9MB (各スレッドグループが hyper と
  norm_weight を読み直す)。normed を別カーネルで実体化すれば半分になるが、
  起動が 1 回増えるので割に合わないと判断した。帯域律速でないと分かった
  いまはなおさら
- プレフィル (M 大) の M ブロック化。上の「形状は全部引数」を参照。
  デコードには効かない

次の標的は BRIEF どおり **MoE ルーティング 11.1ms と GDN 8.1ms**。
どちらも同じ「起動回数が多い」型で、`hc_pre` / `hc_post` の骨格
(threadgroup メモリに入力を置いて量子化行列積を simdgroup で分担) が
そのまま使える。

このカーネルの取り分を入れた現状は 28.5 tok/s。MoE と GDN を同じ比率で
畳めれば 40 tok/s 圏。BRIEF の積み上げ表 (30 -> 45 -> 70) より各段の
取り分は小さく出ると見ておくこと。**起動費用がゼロにはならず、
カーネル 1 本あたり実モデルで ~15us かかる**ため。
