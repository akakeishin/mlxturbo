## A. 測っていない場所を測る (先にこれ)

### A1. 17k decode の部品解剖がまだ無い

prefill 17k は解剖済み (moe 15.0 / gdn 9.4 / attn 9.0 / hc 5.5 / ple 2.3)。
**decode は短文脈しか解剖していない。**17k の 35ms/token が短文脈 14.6ms から
どこで 20ms 増えたのかが分かっていない。

容疑者と、机上の見積もり:

| 容疑者 | 机上 | 備考 |
|---|---|---|
| KV 読み出し | 12 層 x 17000 x 2 head x 256 dim x 2 (k,v) x 2B = **418MB**、達成帯域 393GB/s で 1.06ms | QSA が効くので実際はもっと少ない |
| QSA の pooled 再計算 | 毎フォワード raw_k 52MB を読んで block 平均を取り直している | 増分キャッシュ可能 (下の B4) |
| QSA の argpartition | 4250 ブロックに対する部分ソートを層 x 位置ぶん | GPU で重い可能性 |
| indexer の einsum | 24 head x 4250 block x 128 dim x 12 層 | 小さいはず |

**机上の合計が 20ms に届かない。**つまり見えていない項目がある。解剖しないと
次の一手が選べない。重さ: 半日。反転条件: なし (測るだけ)。

### A2. 定数の再掃引 (前提が変わったのに固定されているもの)

今日 depth で「単一プロンプトの結論が複数プロンプト平均で符号が逆だった」
という事故が出た。同じ形の固定値が他にもある:

| 定数 | 現在値 | 決めた時期・根拠 | 疑う理由 |
|---|---|---|---|
| `PRIME_WINDOW` | 2048 | 32k プロンプトで受理 0.574→0.827 | 単一測定。depth 1 が既定になった長文脈では priming の価値が変わる |
| `RERANK_TOP` / `RERANK_BITS` | 32 / 2 | draft-rerank 移植時 | 掃引の記録が無い。top-16 で足りるなら粗読みが半分 |
| `MLXTURBO_STAGE_EVERY` | 2 | 泡 7.3ms の刈り取り | QSA 修正と depth 変更でラウンド構造が変わった |
| `MLXTURBO_PREFILL_GROUP` | 4 | layer-major 導入時 | 同上。G=2/8 は未再測 |
| `MLXTURBO_SORT_MIN` | 16 | gather sort 閾値 | 由来の記録が薄い |
| `HYPER_KEEP_CHUNKS` | 2 | PRIME_WINDOW から導出 | PRIME_WINDOW が動けば連動 |

`tools/decode_ab.py` に knob を足すだけで測れる (回文順・複数プロンプト x 512 の
作法は実装済み)。重さ: 1 つあたり 30 分の計測 + 実装 10 分。
**反転条件**: 3 プロンプトで符号が揃わなければ既定を動かさない。

## B. 構造で取れるもの

### B1. 受理率連動 depth (load/text adaptive)

depth は今 2 値 (短文脈 = 既定 2、QSA 境界超え = 1) の固定則。だが実測の
tok/round はテキストで大きく振れる: 900 tok の同じ設定で depth 3 が
tok/round 3.37 を出したプロンプトもあれば、17k で depth 3 でも 2.33 の
プロンプトもある。**当たる文脈では深く、外れる文脈では浅く**が素直。

実装: engine に直近 N ラウンドの受理率の移動平均を持たせ、閾値で depth を
上下させる。ヒステリシスを入れて振動を止める。重さ: 半日。
効き: 掃引の表から、当たる文脈で d2→d3 が取れれば数 %、外れる文脈で
d2→d1 が取れれば数 %。**根拠は間接的** (固定 depth の掃引結果からの外挿)。
**反転条件**: 固定 depth の最良値に対して 3 プロンプト平均で勝てなければ捨てる
(適応の複雑さは無料ではない)。

### B2. 2 ターン目の checkpoint 粒度 (layer-major の代償を減らす)

layer-major prefill は G=4 チャンクをまとめて流すので、checkpoint は
8192 トークン間隔でしか立たない (従来は 2048)。2 ターン目の LCP が group の
内側に落ちると再 prefill が最大 4 倍になる (17k で 1760 → 3808 トークンの実測)。

**グループ内で checkpoint を刻むのは構造的に不可能** — レイヤー主導では
「チャンク k を全層通した状態」がどの瞬間にも存在しない。取れる手は
「末尾側をチャンク主導のまま残す幅を広げる」ことだけ。現在は最終チャンク +
端数のみ。ここを 4 チャンク (8192 トークン) にすれば、2 ターン目の LCP が
落ちやすい末尾で 2048 粒度が戻る。代償は prefill の MoE バッチ効率。

重さ: 実装 1 時間 + 計測。**反転条件**: 17k TTFT の悪化が 2% を超えたら幅を戻す。

### B3. QSA の全 -inf 行 (今日見つけた穴)

可視ブロックが 1 つも無い行 (`q_col < compress_ratio - 1`) は mask が全面
-inf になり、softmax が全列一様 = 未来を見る。本番構成 (budget 2048、
prefill チャンク 2048) では QSA が効き始める時点で `q_col >= 2048` なので
**発生しない**が、budget をチャンク幅より小さくすると踏む。他パックへの
横展開で効いてくる。

恒久解は「causal を捨てず sparse と連言を取る」。batch 経路は左パディングの
bool mask があるときだけ既にそうしている。重さ: 実装 1 時間、計測は品質側
(KLD) と速度側の両方。**反転条件**: 速度が 2% 以上落ちるなら、境界の行だけ
causal に落とす形に狭める。

### B4. QSA の pooled キーを増分キャッシュ

`QSAIndexer.__call__` は毎フォワード、kv 全体から block 平均を取り直して
`k_layernorm` と rope をかけている。ブロックは確定したら不変なので、
新しく完成したブロックぶんだけ足せばよい。17k で読み直しが 52MB/フォワード。
**A1 の解剖でここが効いていると出たら着手**する (机上では 0.2ms 程度なので、
解剖の結果次第では割に合わない)。重さ: 半日。

### B5. バッチ x 投機の配線 (進行中)

帳簿・行別 rollback・prefill マスクまで完成。残りは生成器 (同期ラウンド)、
admission (長さバケツ化、負荷連動 depth)、サーバー配線。
紙モデルでは B=4 で 1.95x (共有タイルの項は今日の実測で外した)。
**反転条件**: B=4 で 1.6x 未満なら畳む (宣言済み、まだ発火していない)。

## D. fable-advisor が出したもの (2026-09-01、統合済み)

### D1. **top_p を投機経路で受ける (最優先。私の見落とし)**

`server.py` の `_pick_runner` は、`SUPPORTED_SAMPLING_PARAMS` に無い**非恒等値**
(top_p=0.9、top_k、min_p、penalty 系) と `logprobs` が来たら、そのリクエストを
丸ごと非投機の FallbackRunner に降格する。docstring 自身が「実クライアント
(opencode、OpenAI SDK) は top_p を既定で送る」と書いている。

つまり**実トラフィックのほぼ全部が投機の 1.26-1.44x を静かに捨てている。**
スコアボードには 1 ミリも映らない。ベンチは全部 greedy か temperature のみで
測っているため。

そして**降格は理論の壁ではなく実装の穴**である。`_verify` の temp>0 分岐は
「全位置を先にサンプルして、draft と一致したプレフィックスだけ採用」で、
位置 j のサンプルは `lg[:, j]` にしか依存せず、受理判定は samples[0..j-1] に
しか依存しない。条件付けても位置 j の分布は歪まないので、**サンプラーの形
(top_p フィルタ込み) に依らず逐次版と厳密一致する。**

重さ: 実装は半日程度 (サンプラーを位置ごとに適用する形に変えるだけ)。
効き: 実トラフィックで 1.26-1.44x。**判定は KLD 不要** (分布は構成上厳密)、
「top_p=0.9 / temp=0.7 の実測 tok/s > fallback」だけ。
**反転条件**: top_p 込みの受理率が崩れて fallback より遅くなったら、降格を
残して条件付き有効化に縮める。

**実装済み (コミット caf3b15)。**線引きは「位置局所な logits 変換のみ厳密対応、
履歴依存は降格維持」。`SUPPORTED_SAMPLING_PARAMS` に top_p / top_k / min_p /
logit_bias を足し、`_position_local_sampler` (恒等なら None を返すので既存経路は
1 ビットも変わらない) を `generate_stream` に通した。実トラフィックでの効きは未測。

追撃で分かったこと:

- **logprobs も投機経路から出せる** (未実装)。採用位置 j の `lg[:, j]` は
  正しく条件付いた logits で、棄却位置の logits は採用側に混ざらない。
  先頭トークンだけ出所が `logits_tail` (prefill 末尾) なので 1 行余分に持つ。
  整合の基準は OpenAI の仕様書ではなく `runner.py` の `_logprob_entry`
  (log_softmax の段、top_k の取り方) に合わせること — 投機/降格でリクエストの
  答えが変わるのが一番悪い。streaming + logprobs の 400 は投機化と無関係に残る。
  優先度は top_p より下 (logprobs を送る実クライアントは少ない)。
- **penalty 系は近似で合っている。**ただし線引きは param 名の列挙ではなく
  「位置局所な logits 変換か、履歴依存か」で書くべき (そうした)。
  `logit_bias` は履歴非依存なので厳密に載る側。
  **反転条件**: 逐次適用 (位置ごとに履歴を更新して 1 位置ずつサンプル) しても
  同期コストが実測で無視できるなら (depth<=2 で +2 同期/round)、線引きを撤廃
  してよい。`_verify` が同期を 1 回に畳んだ経緯があるので予想は「載せない」。
- **seed の契約は「版内」。**top_p 対応で「今まで fallback に落ちていた
  リクエスト」が投機経路に移るので、同じ seed の出力が版をまたいで変わる。
  版内の再現性は保たれる (draft は貪欲で決定的、categorical はラウンドごと
  1 回で消費数固定)。docs に一行書くこと。

### D2. 前提が変わったのに固定されているもの (A2 への追加)

- **`MLXTURBO_DRAFT_RERANK=1` の単独 A/B が無い。**「stage2+rerank+head4+depth2」の
  複合構成でしか測られていない。しかも depth2 短文脈時代の決定で、長文脈は
  今 depth1 (draft 1 本/round) なので損益構造が変わった。粗 top-32 から真の
  argmax が漏れると受理率を静かに削る側の knob。
- **`_STAGE_EVERY=2` の掃引が端点で打ち切られている** (16→2 で単調改善のまま)。
  1 が未測。しかも短 decode probe でしか測っておらず 17k は未測。
- **`MLXTURBO_SORT_MIN=16`**: コメントの「検証幅 22..44」は depth2/3 前提の記述。
  長文脈 depth1 では添字が ~20-22 に縮んでいるので、損益分岐が 16 のままかは
  再確認が要る。
- **`MLXTURBO_PREFILL_CHUNK` を立てると group prefill が黙って無効化される**
  (`spec_flash.py` の `big == step` 条件)。棄却記録 (-2%) は layer-major 以前の
  もので、将来チャンク幅を再測する人が layer-major を落として偽の負けを記録する罠。
  **ガードかログを 1 行足すべき。**

### D3. スコアボードが陳腐化している

4k -4.5% 負けと 17k 42.9 は、**depth 既定変更 (4k -3.1%、17k -10.9%) と QSA 修正
(tok/round +2.1%) の前**の値。つまり 4k/17k は既に勝っている可能性がある。
実装を足す前に出荷経路で 1 回測り直すのが安い (冷ましてから短く。熱で 25% 落ちる)。

### D4. `_IndexerCache` が毎更新 concat している

`qwen4_exp.py` の `_IndexerCache.update` は毎回 concat = 毎ラウンド全長コピーを
12 層ぶん。17k で ~2%/round 相当。KVCache 式のプリアロケーションで消せる
(Python のみ、値はビット不変)。取り分は小さいが「構造が古いまま」の実物。

### D5. prefill グループの double-buffer 化 (突飛枠)

`_group_prefill_forward` の後の `mx.eval(*hys)` はグループ境界ごとの完全同期で、
次グループのグラフ構築中に GPU が遊ぶ。全グラフを必ず使うので「作って捨てる」
禁則には当たらない。期待値は 17k で ~0.5-1s。**反転条件**: OOM
(wired + n-gram RAM で 2 グループ分の中間が同時に生きる) か、差がレップの
ばらつき (±3%) に埋もれること。

### D6. ベンチが出荷構成と別物だった (指摘 6、確認して修正済み)

`tools/decode_ab.py` は `enable_hyper_connection_kernel()` だけを呼んでいて、
`build_runner` が当てる `enable_gather_sort(16)` が入っていなかった。
**今日の A/B は全部 gather sort 無しで測っている。**同一ハーネス内の相対比較
なので符号は生き残るが、閾値や交差点は構成で動く (verify 幅は depth で
2/3/4 位置 = 添字 20/30/40 に変わり、sort_min=16 の損益がそこに乗る)。

修正済み: `build_runner` の融合設定を `runner.enable_default_fusions()` に
切り出し、ハーネスからも同じものを呼ぶ (コミット ef87e6d)。

**再実行が要るのは (iii) の 2.6k / 4k だけ** (fable の各個判定):

- (i) QSA 修正は mask の中身の話で MoE ディスパッチと直交。しかも短文脈対照が
  完全一致。両腕に同一に効く構成差では符号が動けない
- (ii) sort 無しハーネスの B 腕 (stock) は本番よりむしろ遅い。本番の sorted
  stock を基準にすれば v2 の負け幅は広がる方向にしかない
- (iv) prefill 幅の添字は 2048x10 = 20k で、stock の既定閾値 64 を超えて元から
  ソートされる。`gather_sort(16)` の有無は prefill に無関係
- (iii) だけ危ない。sort は「1 位置足す限界費用」の文脈非依存項を下げ、深い側を
  一様に有利にする。17k の -10.9% は QSA の文脈比例項が主体で反転しないが、
  2.6k の -3.3% と 4k の -3.1% は薄く、反転しうる。反転したら境界は
  indexer_budget より上に動き、「境界 = QSA 活性化」の機構説明も弱まる

**掃引ハーネス自身のバグも 1 つ出た**: depth knob が `eng.depth` だけを
書いていたので、`depth_ctx_limit` の自動切り替え (今日入れた既定) が効いて
境界の向こう側では全条件が depth 1 になり、**同じものを測っていた**
(2.6k で 1 と 2 の tok/round が 3 桁一致して気づいた)。自動切り替えを外して
再実行中。

`_effective_depth` の政策関数化 (`choose_depth(pos, accept_history, B)`) は
バッチ配線の設計に含める。バッチの同期ラウンドは (B, T+1) の一様幅なので
**行ごとの depth は構造的に存在できず**、行別の受理信号を「ラウンド共有の T
1 つ」に集約する判断が要る = スケジューラの仕事。純関数の器だけ先に切って
おけば、バッチ配線時に捨てるのは呼び出し点だけで済む。捨てるのは
「B=1 で合わせたヒステリシス定数」で、これは B>1 で限界費用が変わる以上
どのみち再調整になる。
