### 1.2 確定した測定事実

**最終スコアボード** (同一セッション、mlx-serve は main ビルド 3afb77d、順序バイアスは往復検証済み):

| セル | mlx-serve | mlxturbo | 差 |
|---|---|---|---|
| short decode | 15.8 ms/tok | **14.6** | **+8% 勝ち** |
| 4k 等窓 121tok | 18.85 ms/tok | 19.74 | -4.5% 負け |
| 17k decode | 43.6-49.3 (要求ごとに劣化) | 42.9-46.3 (安定) | ほぼ同着 |
| 17k prefill | 27.4s | 32.6s | -17% 負け |
| 2 ターン目 TTFT (1k/16k) | 0.66 / 0.73s | 0.94 / 1.1s | 修正後 1.3-1.5 倍差 (修正前は 4-8 倍) |

**prefill 17k の完全解剖** (部品和 41.2s vs 壁 42.7s = 3.6% 以内、帰属ゴースト無し):
moe 15.0 / gdn 9.4 / attn 9.0 / hc 5.5 / ple 2.3。MTP priming は 0.12s で容疑消滅。

**バッチ x 投機の紙モデル** (union 実測 + B=1 較正、B=1 予測 48.3 vs 実測 48.8 で整合):
B=4 で 94.4 tok/s (1.95x)、共有タイル入りで 114.1 (2.36x)、B=8 + タイルで 161.5 (3.34x)。
→ 畳む反転条件 (B=4 で 1.6x 未満) は発火せず、レーン続行を決定。

**競合の構造的弱点** (ソース調査): mlx-serve は継続バッチングを持つが、
**MTP はモデル単位で 1 キャッシュのため MTP リクエスト 2 本が明示的に直列化される**
(`scheduler.zig` の slotExclusiveDecode)。「速い 1 本を順番に」か「MTP を捨てた
遅いバッチ」の二択で、両取りができない。うちのバッチ x MTP はここを突く。

**相手の lossy フラグは無関係と判明**: `--decode-attn-quant` は dense attention 専用で、
ddalcu パックは attention も 4bit 済み = no-op。**彼らのカーネルは同じ量子化重みで
本当に速い**。品質を売って追う道は選ばない (勝利条件は素の速度と宣言済み)。

### 1.3 決めたこと (ユーザー決定)

1. **勝利条件は素の速度** — 品質正規化は看板から降ろす (KLD 3 倍勝ちは商品性として維持)
2. **バッチ x 投機の共存を本気でやる** — FallbackRunner 限定バッチの妥協はしない
3. **上流追随は気にしない** — `_vendor/` はうちが所有し、たまに気合いで取り込む
4. **横展開の順**: Qwen3.8-27B 復帰 → Gemma → GLM-5.3-Flash → DeepSeek V4 Flash
5. **GDN を Flash-Next 独自扱いしない** — 線形注意/再帰系は族として汎用に切る

### 1.4 Opus レビューとその修正

正しさレビューは**確定バグ無し** (写しと本家の読み比べ、合成モデルでの全キャッシュ
比較、BPE 分割の off-by-one 検査を独立に実施)。ただし配線した瞬間に踏む潜在バグと、
決定文と実装の食い違いが出て、全て修正済み (コミット 86956f9):

- `arch.recurrent_layers()` が他族を黙って空リスト → 例外化 (0 個正常系の契約は維持)
- `batched_capture` が full capture 固定で OOM kill を再導入 → `light` 素通し
- `rollback_recurrent_rows` が keep 範囲外を黙って丸める → ValueError
- `enable_moe_verify_gather` が runner から呼ばれていない → 配線 (+ SwitchGLU の
  4 パッチャー重なりを単一パッチャーに統合)
- `MLXTURBO_SORT_MIN` の二重既定、`setdefault` による env 横取り、docs 乖離 4 件、
  CI の誤った除外 (302 テストが外れていた)

### 2.2 負の結果で棚上げした (再訪防止)

HC prefill の融合は、私の見積もりが間違っていた。「帯域比 10 倍の伸びしろ」は
低ランク GEMM の FLOP 項を数え落としたもので、eager の 3.8ms/call は既にほぼ天井に
居る。実装したカーネルは既存カーネルとビット一致したが 6 倍遅く、真の伸びしろは
elementwise 融合分の ~20% (17k で ~1s) しかない。それを取るにも M ブロック化 GEMM という
別設計が要る。

prefill の segment-aware GEMM カーネルは、layer-major prefill が先回りして効率曲線を
登ったため上積みが ≤8% に縮み、棚上げが確定した。楽観先組み、MoE ルーティング融合、
indexer のプールキャッシュはいずれも実測で棄却済み。一律 2bit の量子化は受理率ごと
崩れて速度が帳消しになる。

### 2.3 判明した穴と負債 (直していない)

`_PREFILL_GROUP` は checkpoint の分解能を 2048 から g*2048 に粗くする。2 ターン目の
LCP が group の内側に落ちると再 prefill が増える (17k で 1760 → 3808 トークン)。
末尾側は従来経路のままなので影響はなく、コメントにも「粒度が要るのは末尾」と
書いてある意図的な設計だが、負荷時に効くようなら再検討の余地がある。

`batch_spec` の写しは vendor の `_wide_qkv` 融合を持っていない。これは段 2 の
シーム化で消える。

既存テストの失敗 15 件 (`bench/test_server.py` 9 件、`test_spec_phase0.py` 6 件) は、
フィクスチャが本番既定 (draft-rerank on、MTP base-hidden norm) に追随していないもので、
今日の変更とは無関係。別タスクに切り出してある。CI の `continue-on-error: true` は
これが通ってから外す。

計測できていない軸も残っている。持続 5-10 分の throttle 時系列、並行リクエスト、
ドメイン層別の受理率、tok/J の 4 つ。

## 3. 次にやること

### 3.1 順序 (理由つき)

1. **段 1-2: 写しのシーム化** (`docs/BACKLOG.md` の手順どおり)
   - vendor に `_store_conv_state` / `_positions` / `_final_mask` を切り、
     batch.py と batch_spec.py の写し 3 つを消す
   - これを先に置く理由は、`--max-batch` が投機経路のメソッドを差し替える構造の
     恒久解がシーム化そのものだから。ついでに batch 経路が取りこぼしていた最適化
     (wide 融合、sdpa 壁分割) も自動で戻ってくる
   - 受け入れ: `verify_batch_cache` / `verify_batch_real` / `compat_smoke` /
     `verify_batch_spec`。**反転条件**: シームのオーバーライドが 1 呼び手あたり
     3 個を超えたら止めて写しに戻す
2. **バッチ配線** (BatchGenerator の握り直し + 同期ラウンド + admission)
   - 判定プロトコルは宣言済み (ビット一致は放棄、複数プロンプト x 固定シード x
     tok/step + KLD、**B=1 無劣化ゲート 14.6ms/tok**、長さバケツ化、17k は solo)
   - admission に負荷連動 depth (B が増えると**浅く**する。紙モデルで符号確認済み)
     とステップ予算からの G 導出を載せる
3. **27B 復帰** — 移植済みの BPE checkpoint と段階投入の効果を実測。
   `MLXTURBO_STAGE_EVERY` の掃引を計測項目に入れること (dense では未掃引のまま既定 on)
4. **クリーン計測バースト** — warm TTFT 修正の確定値、共有タイル v2 の in-model A/B
   (配線済み)、depth 再掃引 (tok/s と KLD を同じ表に)、lm_head 焼き直し後の KLD
5. **Gemma 26B/31B** — sliding window prefill (mlx-serve が専用カーネルで 2.4 倍の実績 =
   伸びしろの実在証明)、assistant drafter は KV 共有型で新エンジンが要る

### 3.2 残っているカーネルの札 (取り分順)

1. decode 共有タイル gather の B(T+1) 版 — B=8 で +44% (バッチ設計点が決まってから)
2. prefill の attention 9.0s / GDN 9.4s — 彼我差 5s の主体
3. グラフ構築の泡の残り (GPU idle 8.3%) — `mx.compile` shapeless 化、MLX 内部調査が前提
4. lm_head の verify 幅 (M=3 で 164GB/s、fast_qmm が適格なのに in-model で負ける謎)

### 3.3 判断待ち・未決

GLM-5.3-Flash を焼くかどうか。320B 級なので 4bit の 165GB では 128GB に入らず、
重み 95-100GB (平均 2.5bit) あたりが粘りどころになる。層感度ベースのレシピが前提で、
bf16 元重みの取得 (640GB 級か) かパック逆変換かの判断も要る。

写し 2 (`_group_prefill_forward`) を分解するか (段 5)。段 1-3 でシームの
オーバーライドが 1 呼び手あたり 3 個を超えないことを確かめてから決める。
やらないまま残す選択もある。
