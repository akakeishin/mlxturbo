# デコード 1 ラウンドの解剖と、mlx-serve との残差 (2026-08-31)

同一の一律 4bit 重み (ddalcu を逆変換した `~/models/ddalcu-mlxlm`) で、
mlx-serve --mtp と mlxturbo を同じクライアント・同じプロンプトで測った記録。
数字は全て M3 Max 128GB、このセッションの実測。

## 全セル決着 (2026-09-01、advisor 監査 + 基準最新化の後: 対 release 26.8.11)

基準は最新リリース v26.8.11 (2026-08-29、main の先行コミットに decode 性能は
無いことを確認)。生成長を揃えて全セル再測した最終形:

| | mlx-serve | mlxturbo | 差 |
|---|---|---|---|
| 短 greedy (ms/token) | 15.98 | **15.36** | **-4%** |
| 短 temp0.7 (tok/s) | 54.4 | **59.1** | **+8%** |
| 長 4k・121 トークンに揃えた ms/token | 19.62 | **19.29** | **-1.7%** |
| 長 17k (tok/s) | 46.2 | **47.7** | **+3%** |
| prefill 17k (tok/s) | 366 | **487** | **+33%** |

**以前の「長 4k 同着」は比較バイアスだった** (advisor が指摘): 相手は EOS で
121 トークン、うちは 512 トークン窓で、per-token 費用は位置に伸びる成分を
含むため長い窓が割高に出る。窓を揃えたら 1.7% 勝ち。

advisor 監査で入れたもの: temp>0 verify の一括サンプル化 (分布同一のまま同期
3->1、52.6->56.5 tok/s)。棄却したもの: draft-only 楽観先組み (-2%、百ノード
級でも「作って捨てる」は MLX の評価器に罰される — 3 例目につき決定則へ)。
未測の残り軸 (advisor 指摘): 長文 x temp0.7 のセル、5-10 分持続の throttle
時系列、並行リクエスト、2 ターン目のセッション再利用、ドメイン層別、tok/J。

## 計測カバレッジの監査 (2026-09-01、ユーザー指摘「計測漏れは?」への回答)

見直して漏れは 3 つあった:

1. **temp>0 経路** (実利用のチャット既定)。実測 temp=0.7 で 52.6 vs greedy
   60.8 (-13.5%)。内訳は受理率 2.19->1.92 (-12%、サンプル一致方式の本質) と
   旧 verify 経路 (+0.5ms/round = -1.4%)。基準側との比較は本文の測定を参照
2. **サーバー経路の per-round 消費** (SSE/detok/on_tokens が round 間に同期
   挿入される構造)。server の chunk_gap p95 = standalone のラウンド周期
   (どちらも 35.7ms) で間接確認 — 差は挿入されていない
3. **4271 超の文脈** (8-17k)。xlong (~17k) を測ったら**当たりが出た**:
   DEPTH_CONTEXT_LIMIT=6144 (sdpa 壁時代の遺物) が 17k で depth1 を強制し
   41.9 tok/s (tok/step 1.61) に沈んでいた。壁は分割済みなので depth2 を
   通すと **47.7 (tok/step 2.27) で mlx-serve の 46.2 を逆転**。既定を
   実質無効 (262144) に再較正した。temp=0.7 の短文も 59.1 vs 54.4 で勝ち。
   17k の prefill は 487 vs 366 tok/s (TTFT 35.0s vs 46.4s)

## 追記 (2026-09-01 朝): 泡の第 2 ラウンドと床

投機ループ本体を再トレースすると GPU アイドルは 20.7% -> 8.7%。残りの主因
「verify 後の draft 構築 1.5ms (GPU 完全アイドル)」を draft の段ごと投入で
削り 8.3% へ。残りは eval 覚醒レイテンシ + 段境界の微小ギャップ (~1.5% 相当)
とリクエスト境界 (~13ms/リクエスト、decode 外) で、**非 Metal 側は床**。
ラウンド区間の CPU 計装は MLXTURBO_ROUND_TRACE=1 で残置。

GPU カウンタ (帯域・占有率) は Metal System Trace に無く、Metal GPU Counters
インストルメントは attach では空だった。カーネル別の GPU 内訳を取るには
Instruments GUI か launch モードの試行が要る (次のカーネルセッションの宿題)。

## 最終確定 (2026-09-01 未明、同一セッションで両者再測)

| ms/token (温、decode 区間、クライアント計測) | 短 (65) | 長 (4271) |
|---|---|---|
| mlx-serve --mtp | 15.86 | **19.34** |
| **mlxturbo (stage2+rerank+head4+depth2+ngramRAM)** | **15.23 (-4%)** | 19.45 (+0.6%) |

短文脈は超え、長文脈は 0.6% 差 (ラン間振れと同オーダー) の統計的同着。
mlx-serve の長文 121 トークンは EOS による自然終了で、トークンあたりに
正規化して比較した。再審理メモ: 連結射影 + rebit hc は n-gram RAM 常駐
(wired limit 108GiB に張り付き) と両立せず OOM で不成立。pread へ戻すのは
-2% で、RAM 継続が正。

## 旧・現在地 (2026-08-31 深夜、段階投入で決着)

| decode tok/s (温キャッシュ) | 短 (65) | 長 (4271) |
|---|---|---|
| mlx-serve --mtp (当日再測) | 62.1 | **51.7** |
| **mlxturbo 最終 (stage2+rerank+head4+depth2)** | **64.9 (+4.5%)** | 50.2 (97%) |
| mlxturbo 既定 (セッション前) | 47.0 | 39.0 |

**短文脈は超えた。**決め手は xctrace で特定したラウンド間の泡 (~7ms: CPU が
48 層のグラフを組み切るまで GPU が待つ) を、フォワードの 2 層ごと段階投入
(_staged_forward + mx.async_eval) で刈ったこと。出力はトークン列まで不変。
段階間隔の掃引は 16..2 で単調改善して 2 で頭打ち。楽観先組み (捨てるグラフを
作る形) は MLX の暗黙 eval に潰されて不成立、という切り分けの末の形。

長文脈は残り 3%。泡は刈れており、残りは GPU 実行そのもの (Metal 融合レーン)。

**ただし性能は decode 単独では決まらない。**同じ日の壁時計 (prefill 込み、
512 トークン生成、初回 = キャッシュ無し):

| 壁時計 tok/s | mlx-serve | mlxturbo |
|---|---|---|
| 混在 3 プロンプト (68-74 tok) | 49.3-67.1 | 41.3-47.9 |
| **長文脈 4271 tok 初回** | **5.4** | **39.6 (7.3 倍)** |

差の源は prefill: mlx-serve ~185 tok/s に対し mlxturbo ~560 tok/s (3 倍)。
長いプロンプト + 数百トークン出力というエージェント/RAG 型の利用では、
エンドツーエンドで mlxturbo が数倍勝つ。温まった短い会話の連投では
mlx-serve が 1.15 倍勝つ。docs/PLAN.md の「prefill を体感の本丸に据える」は
数字で裏が取れた。

このセッションで入れたもの (すべて A/B 済み):
- **depth 2 を既定に** (+13%)。複数プロンプト x 512 の平均で 1/2/3/4 を比較し 2 が全面勝ち
- **sdpa の 2 行分割** (qL*gqa>32 が 32 行の壁を越える経路)。長文 verify 49.7->45.4ms。
  "causal" 文字列マスクは kv>=512 のときだけブールマスク化して分割
  (kv=200 は壁 0.7ms < マスク実体化、kv=1024 は壁 6.2ms で逆転)
- gather ソート閾値 16、greedy 検証の同期 1 回化、n-gram RAM 常駐、wired limit
  (速度は不変だがコールド TTFT 3.2s->0.7s)

## 1 ラウンドの内訳 (depth2、T=3 検証、実測)

draft 5.3ms + verify 39.0ms + post/rollback 1.3ms = 45.6ms で 2.44 トークン。

verify の中身は、実入力で単体計測 (tools/module_costs.py) すると:

| 部品 | 単体 (パイプライン下限) | 実効帯域 |
|---|---|---|
| MoE (router+gather+shared) | 13.8ms | ~297GB/s (推定上限近傍) |
| GDN 36 層 | 7.2ms | 165GB/s |
| HC 97 回 | 3.8ms | 98GB/s |
| full attention 12 層 | 1.9ms | — |
| lm_head | 2.1ms | 94GB/s |
| 単体の総和 | 28.7ms | |
| **全体** | **40.5ms** | |

総和と全体の差 11.8ms が「直列化の代償」。単体計測は 48 層ぶんの呼び出しに
依存が無くパイプラインが効くが、実フォワードは層 i+1 が層 i の出力を待つので、
カーネルごとのメモリレイテンシが露出する。個別の糊 (残差合成 1.1ms、router の
fp32 経路 1.3ms、GDN キャッシュ更新 0.4ms) を全部足しても説明できない。

## 「Metal 以外の遅さ」の監査 (全滅、これで非カーネル層は監査完了)

- Python グラフ構築 4.4ms は GPU 実行と重なって無害 (build/eval 分離実測)
- **command buffer 分割は MLX の既定が最適**: MLX_MAX_OPS_PER_BUFFER=4000 は
  verify 38.4 -> 42.9ms (-11%)。大きいバッファは GPU の実行開始を遅らせ、
  エンコードと実行のパイプラインを壊す
- ラウンド内の CPU 同期は 1 回 (greedy 検証の束ね済み)、投機機構 (capture/
  rollback) は素のフォワード比 +1ms 以下、draft の全語彙読みは rerank で解消
- moe_glu v4 は in-model で素の gather と互角 (38.6 vs 38.4ms)。温キャッシュの
  マイクロは T=1 で +26%/T=3 で -40% と両方向に噓をつく (罠 8 の再確認)

残る差は全て Metal カーネルの実行形の中にある。

## 計測の罠 (今日引っかかった順)

1. **並行ダウンロードの汚染。** 21.4 tok/s は bf16 再取得と重なった数字で、
   実力は 42.8 だった。サーバー内部の decode= とクライアント実測の乖離で発覚。
2. **ablate.py の積み上げ無効化は部品コストを過大評価する。** 部品を外すと
   下流の意味が壊れ、hidden が退化してアクセスパターンが変わる。HC 7.6ms 説は
   これで生まれた偽値 (実入力の単体では 3.8ms)。
3. **温キャッシュのマイクロは M タックスを誇張する。** 同じ重みを 24 回読む
   計測では 2 回目以降が SLC に当たらない実機ストリーミングを再現できない。
4. **単発 128 トークンの tok/step はテキスト運で ±0.2 動く。** ulp が 1 個
   flip すると greedy の続きが分岐し、受理率が見かけ上 8% 落ちる。複数
   プロンプト x 512 の平均では消える (kernel 2.01 vs compiled 2.07)。
   数値を動かす最適化を受理率で棄却する前に、必ず平均で見ること。

## 追記: lm_head 8bit -> 4bit (--rebit head=4) は当たり

ddalcu パックの lm_head は 8bit (668MB) で、**既にピーク帯域 (344-355GB/s) で
走っていた**。以前の「lm_head 94-109GB/s」はバイト数の誤算 (4bit と思い込んだ)。
つまりカーネルの問題ではなく読む量の問題で、4bit に打ち直すと draft 5.3->3.7ms、
長文 verify 43.6->42.6ms。複数プロンプト平均で **短 +4% / 長 +5.5% (42.0
tok/s)**。品質は焼き比較の実測で KLD +0.0015 (q48->q4)、平均 tok/step も同等。
重みが mlx-serve の実行と 1 テンソルだけ変わる点は比較時に明記すること。

小さい行列 (GDN の 8-13MB/本) が ~160GB/s に留まり、大きい連続読み (lm_head
668MB、gather 83MB/層) が 290-350GB/s 出る、という帯域の二層構造も確定。

品質の受領書 (serve-q24 参照、31 課題): ddalcu 素 kld_mean 0.01308 /
agree 0.968、+head=4 で 0.01851 / 0.963。**rebit の head4 は二重量子化なので
実コスト +0.0054** (焼けば +0.0015 相当、rebit.py の警告どおり)。あわせて
**ddalcu パック自体がうちの自前ベイク q4 (0.00445 / 0.981) より KLD で 3 倍
悪い**ことも確定 — 同じ一律 4bit でも量子化の腕の差がそのまま出る。速度で
まだ 1.15 倍負けている相手に、品質では 3 倍勝っている、が正確な現在地。

## 残差の正体と、超えるのに要るもの

mlx-serve の T=2 フォワードは全体で ~20ms。うちの「パイプライン下限の総和」
28.7ms (T=3) より下にあり、**部品のカーネル自体が同条件で勝っている**。
Zig 側は router+topk+gather+和 や GDN 一式を層あたり数ディスパッチに畳み、
直列レイテンシを隠している。Python + MLX 標準 op の側からは、

- カーネル数削減の単価は実測 2-8us/本 (wide 連結・HC 融合の実績)
- 6ms 縮めるには千本単位の削減 = 層スケルトンごとの megakernel 化

が要る。つまり残り short 1.16x / long 1.30x は「MoE ブロック 2 カーネル +
GDN ブロック 3 カーネル + 層骨格の融合」という Metal のプログラムであり、
既存の kernels/ の流儀 (hyper_connection.py の 2 段構成、単体でなく実経路
A/B、KLD で品質確認) で数日単位のレーン。着手判断は親に委ねる。
