# デコード 1 ラウンドの解剖と、mlx-serve との残差 (2026-08-31)

同一の一律 4bit 重み (ddalcu を逆変換した `~/models/ddalcu-mlxlm`) で、
mlx-serve --mtp と mlxturbo を同じクライアント・同じプロンプトで測った記録。
数字は全て M3 Max 128GB、このセッションの実測。

## 現在地

| decode tok/s (温キャッシュ) | 短 (65) | 長 (4271) |
|---|---|---|
| mlx-serve --mtp (当日再測) | **62.1** | **51.7** |
| mlxturbo (このセッション後: +head4+rerank) | 54.0 | 42.0 |
| mlxturbo 既定 (セッション前) | 47.0 | 39.0 |

**ただし性能は decode 単独では決まらない。**同じ日の壁時計 (prefill 込み、
512 トークン生成、初回 = キャッシュ無し):

| 壁時計 tok/s | mlx-serve | mlxturbo |
|---|---|---|
| 混在 3 プロンプト (68-74 tok) | 49.3-67.1 | 41.3-47.9 |
| **長文脈 4271 tok 初回** | **5.4** | **39.6 (7.3 倍)** |

差の源は prefill: mlx-serve ~185 tok/s に対し mlxturbo ~560 tok/s (3 倍)。
長いプロンプト + 数百トークン出力というエージェント/RAG 型の利用では、
エンドツーエンドで mlxturbo が数倍勝つ。温まった短い会話の連投では
mlx-serve が 1.15 倍勝つ。docs/PLAN.md の「prefill を体感の本丸に据える」は
数字で裏が取れた。

このセッションで入れたもの (すべて A/B 済み):
- **depth 2 を既定に** (+13%)。複数プロンプト x 512 の平均で 1/2/3/4 を比較し 2 が全面勝ち
- **sdpa の 2 行分割** (qL*gqa>32 が 32 行の壁を越える経路)。長文 verify 49.7->45.4ms。
  "causal" 文字列マスクは kv>=512 のときだけブールマスク化して分割
  (kv=200 は壁 0.7ms < マスク実体化、kv=1024 は壁 6.2ms で逆転)
- gather ソート閾値 16、greedy 検証の同期 1 回化、n-gram RAM 常駐、wired limit
  (速度は不変だがコールド TTFT 3.2s->0.7s)

## 1 ラウンドの内訳 (depth2、T=3 検証、実測)

draft 5.3ms + verify 39.0ms + post/rollback 1.3ms = 45.6ms で 2.44 トークン。

verify の中身は、実入力で単体計測 (tools/module_costs.py) すると:

| 部品 | 単体 (パイプライン下限) | 実効帯域 |
|---|---|---|
| MoE (router+gather+shared) | 13.8ms | ~297GB/s (推定上限近傍) |
| GDN 36 層 | 7.2ms | 165GB/s |
| HC 97 回 | 3.8ms | 98GB/s |
| full attention 12 層 | 1.9ms | — |
| lm_head | 2.1ms | 94GB/s |
| 単体の総和 | 28.7ms | |
| **全体** | **40.5ms** | |

総和と全体の差 11.8ms が「直列化の代償」。単体計測は 48 層ぶんの呼び出しに
依存が無くパイプラインが効くが、実フォワードは層 i+1 が層 i の出力を待つので、
カーネルごとのメモリレイテンシが露出する。個別の糊 (残差合成 1.1ms、router の
fp32 経路 1.3ms、GDN キャッシュ更新 0.4ms) を全部足しても説明できない。

## 計測の罠 (今日引っかかった順)

1. **並行ダウンロードの汚染。** 21.4 tok/s は bf16 再取得と重なった数字で、
   実力は 42.8 だった。サーバー内部の decode= とクライアント実測の乖離で発覚。
2. **ablate.py の積み上げ無効化は部品コストを過大評価する。** 部品を外すと
   下流の意味が壊れ、hidden が退化してアクセスパターンが変わる。HC 7.6ms 説は
   これで生まれた偽値 (実入力の単体では 3.8ms)。
3. **温キャッシュのマイクロは M タックスを誇張する。** 同じ重みを 24 回読む
   計測では 2 回目以降が SLC に当たらない実機ストリーミングを再現できない。
4. **単発 128 トークンの tok/step はテキスト運で ±0.2 動く。** ulp が 1 個
   flip すると greedy の続きが分岐し、受理率が見かけ上 8% 落ちる。複数
   プロンプト x 512 の平均では消える (kernel 2.01 vs compiled 2.07)。
   数値を動かす最適化を受理率で棄却する前に、必ず平均で見ること。

## 追記: lm_head 8bit -> 4bit (--rebit head=4) は当たり

ddalcu パックの lm_head は 8bit (668MB) で、**既にピーク帯域 (344-355GB/s) で
走っていた**。以前の「lm_head 94-109GB/s」はバイト数の誤算 (4bit と思い込んだ)。
つまりカーネルの問題ではなく読む量の問題で、4bit に打ち直すと draft 5.3->3.7ms、
長文 verify 43.6->42.6ms。複数プロンプト平均で **短 +4% / 長 +5.5% (42.0
tok/s)**。品質は焼き比較の実測で KLD +0.0015 (q48->q4)、平均 tok/step も同等。
重みが mlx-serve の実行と 1 テンソルだけ変わる点は比較時に明記すること。

小さい行列 (GDN の 8-13MB/本) が ~160GB/s に留まり、大きい連続読み (lm_head
668MB、gather 83MB/層) が 290-350GB/s 出る、という帯域の二層構造も確定。

## 残差の正体と、超えるのに要るもの

mlx-serve の T=2 フォワードは全体で ~20ms。うちの「パイプライン下限の総和」
28.7ms (T=3) より下にあり、**部品のカーネル自体が同条件で勝っている**。
Zig 側は router+topk+gather+和 や GDN 一式を層あたり数ディスパッチに畳み、
直列レイテンシを隠している。Python + MLX 標準 op の側からは、

- カーネル数削減の単価は実測 2-8us/本 (wide 連結・HC 融合の実績)
- 6ms 縮めるには千本単位の削減 = 層スケルトンごとの megakernel 化

が要る。つまり残り short 1.16x / long 1.30x は「MoE ブロック 2 カーネル +
GDN ブロック 3 カーネル + 層骨格の融合」という Metal のプログラムであり、
既存の kernels/ の流儀 (hyper_connection.py の 2 段構成、単体でなく実経路
A/B、KLD で品質確認) で数日単位のレーン。着手判断は親に委ねる。
