# prefill チャンク分割の決定性の範囲 (2026-08-28)

`fastmlx/spec.py` の `SpecEngine` と `fastmlx/runner.py` の `FallbackRunner`
はどちらも新規プロンプトを `PREFILL_STEP_SIZE` (既定 2048、`fastmlx/spec.py`
で定義し両経路が共有する) トークンずつチャンク分割して forward する。

**決定性は同一構成内で保証する。** 同じモデル・同じ `PREFILL_STEP_SIZE`・
同じ量子化であれば、同じプロンプトから毎回ビット単位で同じ出力が出る。

**構成が変わればビット一致はしない。** `PREFILL_STEP_SIZE` を変える、
分割を無効化する (一括 forward に戻す) など、チャンク幅そのものが変わると
出力が変わり得る。原因は `mx.quantized_matmul` (4-bit 量子化モデルの行列積)
がバッチ長 (一度に処理するトークン数) に応じて異なる丸めを返すこと — 実測
では、この差は 1 層目の出力で相対誤差 ~0.4%、40 層を通すと ~30% まで拡大
し、greedy デコードの受理判定を変えるのに十分な大きさになる。これは
fastmlx 固有の不具合ではなく MLX の量子化行列積カーネルの性質で、vLLM や
llama.cpp を含め、チャンク幅を変えてもビット単位で不変な出力を保証する
実装は一般的ではない。

保証しているのは次の 2 点だけ:

1. 同一チャンク幅・同一構成での決定性。
2. 投機デコード (MTP 連鎖 / lookup) の受理判定が、実際に計算された
   target logits と整合していること — 固定したチャンク幅の下で、投機あり
   (spec-on) と投機なし (spec-off, `n_draft=0, max_draft=0, lookup_len=0`)
   の貪欲デコード出力トークン列が完全一致することで検証している。

分割の有無やチャンク幅を跨いだ出力の一致は要求しない (要求すると
バッチ不変性の検査になり、このプロジェクトが主張している正しさの範囲を
超える)。
