# BAKE-PLAN — 2 本焼くための計画 (2026-08-28)

## 目標: 4 段階を焼く

| 名前 | 容量の目安 | 推奨 RAM | 空き | 予測 KLD | 位置づけ |
|---|---|---|---|---|---|
| **v-xl** | ~91GB | 128GB | 34GB | 0.00378 (実測、v-fast6) | 品質最優先。専用機向け |
| **v-l** | ~77GB | 128GB | 48GB | 0.00619 | **クライアント兼用。いま一番欲しい段** |
| **v-m** | ~67GB | 96GB | 26GB | 0.008 前後 (未測定) | 96GB 機向け |
| **v-s** | ~49GB | 64GB | 12GB | 0.08178 (要再評価) | 64GB 機向け。動くことを優先 |

### 名前の方針

**大小関係が名前だけで分かること**を優先した。使う人の RAM は 128GB とは
限らないので、対象マシンで名付けると「自分の機械にどれが入るか」を推測できない。

**容量を名前に入れない。**`v-96` が実際は 71.7GB になった前科がある。
名前は順序だけを担い、**実容量と推奨 RAM はモデルカードと README に書く**
(数字は更新できる場所に置く)。

### 各段の作り方

**サイズを目標にして配分を後付けしない。**既存の `v-96` は `default: 4bit` で
head/attn/shared まで落とし、KLD 0.02902 になった。**サイズが悪いのではなく
配分が悪い。**同じ 67GB 帯でも A の作り方 (experts だけ落として他は 6bit 維持)
なら 0.008 前後に収まるはず。

各段とも:

- hc は 8bit 固定 (融合カーネルが 4/8 しか受けない)
- head / attn / shared / gdn は 6bit を維持する (掃引で「一番おいしい」側)
- **容量は experts のビットと層の配り方だけで合わせる**

### v-s は最後に回す

予測 0.08178 は experts を 6bit -> 2bit と大きく落としたときの rebit 値で、
**二重量子化の罰が「14% 悲観」より確実に大きく出る**。焼けば改善するが幅が
読めない。参考として **n-gram 表を丸ごと捨てた場合の KLD が 0.04795** (STATUS)
なので、予測値はそれより悪い水準にある。**「焼いてみないと使い物になるか
分からない」段**として最後に置く。

## 前提と制約 (先に潰しておく)

- **bf16 元重みは無い。**外付け SSD 上の元 checkpoint は削除済みで、
  焼くには再取得が要る。外付けの空きは 640GB。規模は本体 121B + n-gram 51.2B の
  bf16 で **300GB 級**と見積もり (要確認)。**一晩仕事**として計画に入れる
- **内蔵ディスクの空きは 163GB。**v-fast6 (91GB) を互換性のため残すので、
  T1 (91GB) と T2 (78GB) は**同時に置けない** (169GB > 163GB)。
  焼く -> 検証 -> 退避か削除、を 1 本ずつ回す
- **hc は 8bit 固定。**融合カーネルが 4/8bit しか受けず、6bit を選べない。
  4bit は KLD +0.01337 で高すぎる (掃引で却下済み)
- **容量の実質的なつまみは experts だけ。**97.5GB のうち 85.6GB が experts で、
  他クラスは全部合わせても 12GB。head を 6->4bit にしても 0.16GB しか減らない。
  **「どのクラスを削るか」ではなく「experts をどう配るか」の問題**
- **rebit の予測は約 14% 悲観側** (v-fast6 予測 0.00432 -> 実測 0.00378)。
  「予測で保てるなら焼いても保てる」の向きにだけ使う。逆は言えない

## 焼く前に潰す論点 (ダウンロード不要、rebit で全部できる)

`tools/predict_recipe.py` で回す。1 本あたりモデル読込 + 打ち直し + 31 プロンプト
評価で 15-25 分。**biglock 必須**。

### 配分の原則 (2026-08-28、確定)

**高いビットは後ろへ。削るなら前から。**

`tools/predict_recipe.py --lo-layers` で v-fast6 (0.00378) から 8 層ずつ
experts を 4bit に落とした感度地図:

| 落とした層 | KLD 増 | 実効層数 | 層あたり |
|---|---|---|---|
| 0-7 | +0.00027 | 7 | **0.0000386** |
| 8-15 | +0.00032 | 6 | 0.0000533 |
| 16-23 | +0.00046 | 7 | 0.0000657 |
| 24-31 | +0.00063 | 7 | 0.0000900 |
| 32-39 | +0.00085 | 6 | 0.0001417 |
| **40-47** | **+0.00133** | 7 | **0.0001900** |

**深さに対して単調。出口は入口より 1 層あたり 4.9 倍敏感。**KLD は決定的な
計算なので、この順位に測定雑音は無い。

同一予算での対照 (どちらも 76.8GB、6bit が 8 層):

| 6bit にする層 | KLD |
|---|---|
| **後ろ (40-47)** | **0.00598** |
| 前 (0-7) | 0.00682 |

**置き場所だけで 12% 違う。**感度地図は配分の指針として使える。

**`_FIRST5_LAST5` の folklore は半分間違い。**入口と出口の両方ではなく、
**出口だけが効く。入口はいちばん効かない。**端寄せが等間隔に勝ったのも、
たまたま出口側を 4 層含んでいたため (下の Q1)。

### 段のサイズは wired limit で決める

総 RAM ではなく **GPU wired limit (既定で RAM の約 75%)** に KV 込みで
収まる必要がある。

| 機種 | wired limit の目安 | 本体の上限 |
|---|---|---|
| 128GB | ~96GB | v-xl 91GB (ぎりぎり) / v-l 77GB |
| 96GB | ~72GB | **v-m は 65GB 以下** |
| 64GB | ~48GB | **v-s は 45GB 以下** |

当初 v-s を 49.4GB としていたが、**64GB 機に入らない。**45GB 前後に作り直す。

### Q1. 層別の配分は効くか -> **効く。端寄せが勝った** (解決)

| | 実効 hi 層 | 容量 | KLD |
|---|---|---|---|
| 端寄せ (edge:10) | **8** | 77.4GB | **0.00619** |
| 等間隔 (spread:10) | 10 | 78.7GB | 0.00694 |

**8 層で 10 層に勝ち、しかも 1.3GB 小さい。**端寄せの指定 10 層のうち
2 層 (3, 45) は v-fast6 で既に 4bit だったので、実効は 8 層。

`_FIRST5_LAST5` の folklore は、少なくともこの粒度では正しかった。
**以後 `_spread` を既定にしない。**Q2 でどこまで端かを詰める。

### Q2. 深さ方向の感度地図 (6 本)

v-fast6 から 8 層ずつ 4bit に落として KLD を測る (0-7, 8-15, ..., 40-47)。

- 均一なら Q1 と合わせて「層別は無意味」で決着し、以後 `_spread` 固定
- 偏っていれば、その形に沿った配分が **T1 と T2 の両方に効く**

これが「細かく層別に変えると効果あるか」への直接の答えになる。

### Q3. サイズ曲線 (3 本)

hi 層数 n ∈ {10, 20, 30} の KLD。両端は既知 (n=0 が A の 0.00727、n=40 が
v-fast6 の 0.00378)。**T2 をどこに置くかを曲線の形で決める。**
1 層 = 0.629GB なので、n が 10 増えるごとに +6.29GB。

### Q4. T1 で v-fast6 に勝つ手はあるか

同容量 (~91GB) で配分だけ変える。候補を安い順に:

1. **Q2 の感度地図に沿った hi 層の選び直し** (容量ゼロで効く可能性)
2. **group_size を効く場所だけ 32 に。**experts は +9.4GB で高すぎるが、
   head/attn/gdn なら安い。未測定の軸
3. experts の 6bit 層を減らして浮いた容量を別クラスへ — **experts 以外は
   全部で 12GB しかない**ので、行き先が無い。優先度は低い

## 確定レシピ案 (親へ) — `convert_flash.RECIPES` への追加

**このファイルは私の触らない領域なので、内容だけ渡す。**

### 追加が要るヘルパ

```python
def _last(n: int) -> list[int]:
    """末尾 n 層。感度は深さに対して単調に増えるので、高いビットは後ろへ寄せる
    (docs/research/BAKE-PLAN.md の感度地図)。`_FIRST5_LAST5` は入口も高くしていたが、
    入口はいちばん効かないことが実測で分かった。"""
    return list(range(48 - n, 48))
```

### 検証の度合いが段ごとに違う

- **v-l / v-m / v-s**: rebit で予測済み。**ビットを下げる向きだけ**なので、
  「予測で保てるなら焼いても保てる」が言える。v-m と v-s は 6/4bit から
  3/2bit へ大きく落としているので、二重量子化の罰は 14% よりかなり大きいはず。
  **焼くと予測よりだいぶ良く出る**と見ておく
- **v-xl は rebit で検証できない。**v-fast6 は既に 8 層が 4bit で、それを
  6bit へ戻せないため。0.0033 は感度地図からの加算性を仮定した概算で、
  **焼いて確かめるしかない唯一の段**

### 既存レシピへの示唆

`v-exp6` と `v-ng2` は `_FIRST5_LAST5` で組まれている。入口は効かないので、
同じ予算のまま `_last(10)` に置き換えるだけで良くなるはず (未測定)。

## 焼く順

1. Q1-Q4 の結論でレシピを 2 本確定 (ここまでダウンロード不要)
2. bf16 を外付けへ再取得
3. **T2 を先に焼く。**小さい方から。ディスクに余裕があり、失敗しても傷が浅い
4. T2 を検証: KLD / 速度 (融合カーネル込み) / **予測との差で rebit の悲観幅を
   再較正**。この較正値は T1 の判断に効く
5. T2 を外付けへ退避するか削除してから T1 を焼く (同時には置けない)
6. T1 を検証。v-fast6 に勝てなければ T1 は捨てて v-fast6 を「余裕なし版」にする

## 消すもの

- 予測用の中間物は作らない (rebit はメモリ上だけで、ファイルを残さない)
- 焼いたもののうち採用しなかった方は、検証が終わり次第すぐ消す
- **v-fast6 は残す** (互換性のため)
- 消す前に必ず対象を名指しで告げる。ディスクは戻せない

## 未解決 (計画時点)

- bf16 元重みの実サイズ。300GB 級という見積もりは params からの算術で、
  実際のリポジトリ構成 (MTP や tied embedding の有無) で変わる
- rebit の悲観幅 14% は v-fast6 の 1 点でしか較正していない。experts を
  6->4bit と大きく落とす場合に同じ幅とは限らない。**予測は順序の信頼に使い、
  絶対値は焼いて確かめる**
