## レーン 1: decode 短文脈の +6 ms (GPU 時間 24.0 対 18.1 ms、S=1)

- **正体**: 部品別に未帰属。読解で潰した候補: RoPE 融合 (取り分なし)、MoE router /
  RMSNormGated 融合 (遅い + 受理率 -6%)、GDN 前処理融合 (実モデルで bf16 の A_log で
  落ちていた → 修正済み、A/B 待ち)。
- **ゲート**: `tools/decode_prof.py` (うち) と相手の `[decode-prof]` を同じ切り方で並べ、
  embed / attn / mlp / lmhead の差が最大の部品を 1 つ決める。差の 6 割以上が 1 部品に
  集中していればその部品の融合カーネルを書く。散っていれば「dispatch 数」の問題で、
  `mx.compile` で層をまとめる実験 (shapeless、S=1..4 の 4 変種) に切り替える。
- 反転条件: GDN 前処理融合の A/B で短文脈 ms/round が -3% 未満なら融合の手は畳む。
- **独立レビュー (REVIEW-2026-09-02-INDEPENDENT.md) からの前提**: `tools/micro_kernel_latency.py` は
  A/B がブロック測定 (fused 200 回 → plain 200 回) で lm_head が 8bit (本番は 6bit)。直してから
  でないと固定費の帰属に使えない (D-11)。HC カーネルを触るなら、down/up/inject の bits・
  group_size 不一致を通す適格判定の穴 (D-4) も同時に締める。

- **実測 (2026-09-02 21:03)**: カスタム Metal カーネルの起動固定費は組み込み op と同じ 3 us
  (冷えた GPU、直列 500 本)。「融合カーネルの固定費が高い」仮説は棄却。S=1 forward の 1879 op ×
  3 us ≈ 5.6 ms が起動の床。残る仮説は「自前の融合カーネル 1 回の実行がデータ量に対して遅い」
  (素朴なカスタムカーネルは同じバイト数で組み込みの 4.7 倍遅い実測あり)。
  `tools/kernel_chain_cost.py` (作成中) で HC / GDN step / prework の 1 回の費用と forward 内の
  呼び出し回数を掛け、6 ms への寄与を出す。寄与が 3 ms 以上なら該当カーネルを書き直す
  (ベクトル化 load、threadgroup の再配置)。1 ms 未満なら dispatch 数の問題に戻り、
  `mx.compile` で層をまとめる実験へ。

## レーン 2: prefill MoE (時間の 4-5 割、効率 47%) — **2026-09-02 に畳んだ**

- **手**: fused MoE (gate+up を N=1280 の 1 本に、SiLU と down を共有メモリで)。
  vLLM / TensorRT-LLM の fused_moe と oMLX `qwen35_moe_gate_up` が同型。うちの
  `MLXTURBO_WIDE` は decode で負けたが prefill 幅は未測 (A/B を待ち行列に入れた)。
- **ゲート**: `--knob wide --only long --ctx 17000` の prefill_s。-3% 以上ならこのレーンを
  進める (次: gate+up+SiLU の 1 カーネル、`moe_glu.py` の prefill 版)。
- 反転条件: N=1280 にしても prefill_s が動かなければ、MoE の効率 47% は行数でも N でも
  なくルーティングの偏り (タイル水増し) が主因。その場合は「専門家ごとの行数で
  bm を切り替える」MLX 本体側の話になり、うちでは畳む。
- **結果 (17:07)**: 連結は 15-20% 遅かった (`bench/results/wide-prefill-17k.json`)。反転条件に該当、畳む。
  再訪するなら MLX 本体の `gather_qmm_rhs` のタイル選択 (bm を専門家ごとの行数で決める) を patch する側。
- **訂正 (2026-09-02 夜、独立レビュー D-2)**: この A/B は専門家の gate+up 連結を測っていない疑いが強い。
  (1) `fused.py:788` の注記どおり、既定 `MLXTURBO_SORT_MIN=16` では gather_sort が必ず優先され、
  `_fused_w` の連結経路には到達しない。`decode_ab.py --knob wide` は SORT_MIN を変えず、結果 JSON の
  `fired` にも連結の発火記録が無い。(2) B 側の `disable_wide_projections` は誰も代入しない
  `_wide_experts` を消すだけで `_fused_w` を外さない。よって A の 15-20% は GDN / attention / shared の
  連結射影の費用で、専門家側は未測。**畳む判定は保留に戻す。** 再測の条件: `disable` が
  `_fused_w/_fused_s/_fused_b` を外すように直し、`MLXTURBO_SORT_MIN=0` を明示し、`fired` に連結経路の
  発火回数を記録した上で、17k x 3 本の prefill_s。ゲートと反転条件は上のまま。

- **再測 (2026-09-02 19:20、D-2 修正後、`bench/results/wide-prefill-17k-b.json`)**: `disable` が
  `_fused_w/_fused_s/_fused_b` を外すように直し、A 側で SORT_MIN を無効にして専門家の連結経路を通した
  回文順 3 本。prefill_s A 78.6 対 B 48.3 (+62.6%)、decode ms/tok +43.2%、tok/round 同じ。
  3 本とも A が 25 s 以上遅い。**連結そのものが gather_qmm の効率を落とす。畳む判定で確定。**
  MoE 超過 1.07 s の帰属は `tools/moe_routing_skew.py` (行数分布の偏り) で決める。

## レーン 3: prefill QSA attention (50k で時間の 3 割)

- **事実**: dense マスクは kv に比例して伸びる。真の union は tile 32 で kv の 6 割
  (17k 以下では gather で取れない)。相手は qL>=16、kv>8192 で直接添字のカーネル。
- **手**: クエリ 1 本 (または 4 本) x 選択ブロック 512 の block-sparse Metal カーネル。
  前セッションの `prefill_attn.py` (1 threadgroup = 1 クエリ x 1 kv head) は dense と
  同速だったので、設計を変える: (a) 12 の GQA head を 1 threadgroup に載せて K/V タイルを
  共有 (相手と同じ)、(b) クエリ 4 本を同じ threadgroup に載せて union (4 本なら kv の
  2 割台と見込む) を 1 回読む。
- **ゲート**: 50k の prefill_s で -10% 以上、KLD 受け入れ幅内。17k では -5% 見込み。
- 反転条件: 合成テンソルの単体で dense sdpa (kv=16k) の 2 倍を切れなければ書き直さず畳む。

- **判定 (2026-09-02 20:40、`bench/results/gather-union-stats-t4t8.json`)**: 真の union は T=4 で
  kv の 36% (17k 末尾 22%)、T=8 で 44%。FLOP は T=4 で dense causal の 70%、T=8 で差なし。
  dense の steel はクエリ 32 本で K/V を共有するので読み出しは T=4 のブロック疎の 1/3。
  反転条件 (合成で dense の 2 倍) にどの T でも届かない。**畳む。**設計書
  `QSA-PREFILL-KERNEL-DESIGN.md` と骨組み `kernels/qsa_prefill_attn.py` は記録として残す。
  17k 以上の attention で残る候補は indexer (選択側) の費用と、相手が prefill で QSA を
  省略・近似していないかの確認 (調査中)。

## レーン 4: ANE (dense 射影の offload)

- **事実** (scout 実読): 相手 (mlx-serve `--ane-prefill`) と oMLX は dense MLP と GDN の
  token-local 射影だけを ANE に落とす (MoE の gather と再帰状態は対象外)。私的
  framework `AppleNeuralEngine.framework` を dlopen して MIL を直接渡す。重みは
  per-channel int8 に再量子化 (近似)。**M5 では mlx-serve が既定 off** (NAX の GPU が
  勝ち、16k/32k で -11%/-7.5%)、oMLX は割合を下げて残す。うちの Stage1 ゲートは
  「GPU が忙しいときだけ 1.29-1.45x、空きなら 0.91x」。oMLX の 32K 実測: 再帰 qkv を
  ANE に載せると順序保持タスクが壊れ、z だけなら +18% (16K/32K)。
- **Flash-Next で載る形**: attention の qkv/o (12 層)、GDN の in_proj_z / out_proj
  (36 層)、共有専門家 (幅 640、FLOP 5% で対象外)。GDN の qkv は再帰なので載せない。
- **ゲート**: oMLX の `.mm` を nanobind か ctypes で包み、17k の prefill で GDN の z 射影
  だけを ANE に出して prefill_s -8% 以上、KLD 受け入れ幅内。M3 Max (ANE 1 基) で測る。
- 反転条件: -3% 未満か KLD 超過で畳む。M5 実機では mlx-serve と同じ判定 (off) が
  出る可能性が高いので、**M5 の値を取ってから既定を決める**。

## レーン 5: 並列デコード (continuous batching) — **実装レーン (ユーザー方針 2026-09-02: ベンチマークの並列列はこれを直してから)**

- **事実**: `batch_spec.py` は B=4 で 1.47 倍 (閉じたバッチ)。HTTP の相方待ち (既定 15ms
  では会えず、1000ms は取り分を食う) が問題。vllm-mlx (waybarrios) は continuous
  batching + paged KV + prefix cache で 16 本同時 4.3 倍を主張 (調査中)。
- **ゲート**: 走行中バッチへの途中参加 (chunked prefill で入れる) を配線し、2 本同時
  到着 (間隔 200ms) の壁時計が単独 x2 の 0.8 倍以下。
- 反転条件: 途中参加のための同期がラウンドを 5% 以上遅くするなら畳む。
- 前提の修正 (独立レビュー): B-1 (budget 以下の短い行がブロックマスクで自分自身を見失う)、B-3 (`classify()` の QSA
  発火条件がバッチの物理列数を見ていない) を先に直す。混在長で出力が変わる状態のまま並列を測らない。
- 設計の写し元: vllm-mlx (待ち窓なし、毎 tick の途中参加、chunked prefill と decode の交互、MTP はバッチ全体に毎ステップ)。
- **着手前に直すもの (独立レビュー B-1、B-3)**: 混在長のバッチで踏む欠陥が 2 つある。budget を越える行が
  1 つでもあると短い行までブロックマスクを通り、クエリ自身が不可視になる (`batch_spec.py:768,831-836`)。
  `classify()` が単体の `prompt_len + max_tokens` で solo/pool を決めるので、pool 同士でも物理列数が
  budget を越える (`batch.py:647-657`)。途中参加は混在長を作るので、この 2 つを直してから
  `tools/verify_batch_spec.py` の一致を取り直す。

## レーン 7: 履歴依存の penalty を投機に乗せる (もらった意見の検証、2026-09-02)

- **事実**: top_p / top_k / min_p / logit_bias は既に投機経路 (`FlashSpecRunner`、位置局所な
  変換なので `_verify` の全位置先サンプル方式と厳密に両立)。**repetition / presence /
  frequency penalty だけ非投機 runner へ透過的に降格** (400 ではない)。
- **手**: 位置 j の penalty マスクを prefix + draft[:j] から作り (決定的)、`_verify` の
  `lg[:, j]` に掛けてからサンプルする。draft 側は変更不要 (検証が任意の提案に対して厳密)。
  受理率を上げたければ draft の argmax にも同じマスクを掛ける。
- **ゲート**: 先に「penalty を送るクライアントの割合」を確かめる (Ollama 互換経路が
  `repeat_penalty` 既定 1.1 を写すなら全 Ollama クライアントが非投機)。写していれば着手。
  実装後は penalty 付きの逐次生成とトークン列一致 (seed 固定) + 512 トークンの ms/tok。
- 反転条件: penalty を送るクライアントが無視できるほど少なければ後回し。
