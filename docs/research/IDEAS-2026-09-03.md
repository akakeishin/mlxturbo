## 方向 (prefill)

### P1 — 低占有の op を 2 本目の GPU stream に逃がして隣チャンクの行列積と重ねる
- 一手: `_group_prefill_forward` の層主導ループで、chunk の偶奇 (または GDN の scan だけ) を `mx.new_stream(mx.gpu)` に載せる。
  op も順序も同じで stream 間の依存は MLX の Event が張るのでビット一致。
- 効く理由: scan 3.2 ms + 前処理 1.5 ms + HC の elementwise + PLE + indexer が 1 チャンクの 15% で、どれも占有率が低い。
  同じ 1 stream では op ごとの barrier で直列。見込み -2〜-5%。
- proof-of-life (30 分、モデル無し): stream A に GDN scan の連鎖、stream B に qmm の連鎖。1 stream の和と 2 stream の壁時計を比べる。
  2 stream が 1 stream の 0.95 倍以上なら Apple GPU が compute queue を直列化しており、畳む。
- 最大の未知: Apple GPU が 2 本の compute command buffer を同時に走らせるか。
- 支払うもの: 一時 +1〜2 GB。

### P2 — HC の elementwise を prefill 幅で mx.compile

### P3 — MoE の grouped GEMM を自前で書く (カーネルレーン)

## 方向 (decode)

### D1 — draft の 1 段目を verify のグラフに同梱する (Scout 2 本が独立に同じ案)
- 一手: `_staged_forward` の直後、`mx.eval` の前に、`nxt_all` の S 行を入力に MTP 層 1 回を因果ブロックで組んで同じ eval に乗せる。
  同期後は hit の行だけ取って残りの段を今の `_draft_chain` で組む。`_prime_accepted_gap` の hit 回の逐次呼び出しが消える。
- 効く理由: eval_done 4.7 → drafts_submitted 7.1 ms の 2.4 ms は GPU に何も無い区間。MTP の重み読みは行数に依らない。見込み ms/round -3〜-5%、tok/round 不変。
  棄却済みの `MLXTURBO_PIPELINE` との違いは捨てるグラフが無いこと (行 ≤ hit は必ず使う)。
- proof-of-life: knob で短 3 本 × 512、出力トークン列と tok/round の一致を先に確認、ms/round -5% で採用、-2% 未満で畳む。
- 最大の未知: M=3 の行が M=1 とビット一致するか (ずれると draft が変わり運に埋もれる)。
- 支払うもの: `_draft_chain` が 2 つに割れる。MTP キャッシュの不変条件が push から trim までの間だけ破れる。

### D2 — depth を定常 EMA 以外の信号で決める (2 つの信号を 1 つの trace で当てる)
- 信号 a (分岐予測器の履歴表): 直近 3〜4 ラウンドの全採用ビット列で表を引く。短文脈で depth 3 が一度も選ばれないのは、
  定常 EMA がバーストと谷を平均するから。コード・引用・定型文の中だけ 3〜4 を引ければ ms/tok -5〜-8%。
- 信号 b (draft の確信度): `_draft_argmax` の top-1/top-2 の差を `_effective_depth` に渡し、マージンが小さいラウンドは depth 1。
  depth 2 の 48% は 2 本目が棄却されて 7 ms 捨てている。半分当てれば -1.7 ms/round。
- proof-of-life (30 分、GPU 1 回): 静的 depth 4 で短 3 本 × 512 を流し (round, depth, hit, margin) を積む。
  オフラインで P(hit≥3 | 直前全採用) − 周辺、マージンと hit の AUC。前者の上昇 0.15 未満、後者 AUC 0.6 未満なら各々畳む。
- 支払うもの: Python 50 行ずつ。短文脈で静的 depth 2 を下回る危険があるので既定 off から。

### D3 — 長文脈で文脈 n-gram (SAM) の draft を MTP の代わりに使う

  一致しないラウンドは今のまま。verify はトークン比較だけなので分布は変わらない。

  長 3 本の予測が -3% 未満ならエンジンに触らず畳む。
- 最大の未知: ベンチ文の一致率。幅 6〜7 の verify 費用が線形 +7 ms で済むか。

### D4 — command buffer の粒度 (MLX_MAX_OPS_PER_BUFFER / MLX_MAX_MB_PER_BUFFER)

## NAX 対応機の扱い (ユーザー方針 2026-09-03 08:30)

この機 (M3 Max) は NAX 非対応だが、本番では NAX 対応機 (M5 系) でも使う。P3 のカーネルは NAX 専用の intrinsic を使わず
simdgroup_matrix の経路だけで NAX 機でも正しく動く形にし、発火は `MLXTURBO_MOE_GEMM=auto|on|off` (auto = 非 NAX で on、
NAX 機では off。MLX 自身の `gather_qmm_rhs_nax` との A/B を NAX 機で取り直すまで既定にしない)。機種判定は 1 箇所に集める。
この機で取った「BM=16 の straddle」「dense 比 1.19」は非 NAX の数字で、NAX 機では MLX の別カーネルが走るので、
NAX 機に着いたら P3 と MoE の dense 比を `--knob` で全部取り直す。他の自前カーネル (gather prefill、GDN Metal) も同様。

## 追加の方向 (prefill の attention、Scout 2026-09-03 09:35)

事実の確定: MLX 0.32.2 の sdpa は head_dim 256・S>8 では steel ではなく **fallback (matmul → where → softmax → matmul)** で、
bool マスクでも causal でもタイルを 1 つも飛ばさない (`scaled_dot_product_attention.cpp:756-766`、`fast.cpp:835-886`)。
現チャンクの上三角 (kv 1024 列ぶん = 5.1 ms/層/チャンク) も、QSA で不可視のブロックも全部計算している。
相手 (mlx-serve) は d=256 用の自前 flash カーネルで causal と配列マスクの両方を skip する。

### P5 — dense fallback を行タイル × 前方だけの K/V に割る (Python だけ)
- 一手: `Attention.__call__` の dense 分岐 (S ≥ 64) で、q を R=256 行ずつ 8 回の sdpa に割り、各タイルは `[0, offset+(t+1)R)` の K/V とマスクの
  スライスだけを渡す。可視集合は不変 (近似無し)。シームは触らない。
- 効く理由: 上三角 5.1 ms/層/チャンクのうち R=256 で 4.6 ms 回収。4k -1.6〜1.8%、17k -1.4〜1.5%。NAX 機でも配列マスクは fallback のまま。
- proof-of-life (20 分、モデル無し): S=2048, Hq=24, Hk=2, D=256, kv 2k/4k/8k で whole 対 R∈{512,256,128}。判定線 -3.9/-4.6/-4.9 ms。
- 最大の未知: dispatch が 5 → 40/層に増え、層主導ループの CPU build が伸びるか。
- 支払うもの: PV の縮約長が変わるのでビット一致せず (集合は同じ)。KLD で確認。

### P6 — T=1 gather カーネルの段階 load を uint4 (16 B) 化し、発火下限を 12288 → 6k 台へ
- 一手: `kernels/prefill_attn.py:223-229` の 1 スレッド 1 要素 (2 B) のコピーを 1 スレッド 8 要素に。次段で K 載せ直後にスコアを計算しつつ V を載せる。
- 効く理由: カーネルは kv に依らず 56〜59 ms で load 41.6 (207 GB/s 相当、床 21.5) / score 17.1。load が 25 ms なら dense との交差点 11k → 8k 台。
  17k の 6k〜16k の 6 チャンクで -1.4 s (4.5%)、50k -7%、4k 0。
- proof-of-life (30〜60 分、モデル無し): `prefill_attn_v2.py` の stage=compact_load を uint4 化して kv=16896 で load 単体 ABAB。load < 30 ms で次段、≥ 38 ms なら
  飛び飛び読みのレイテンシ律速で畳む。
- 支払うもの: Metal 数十行。発火範囲を広げるので kv 6k〜12k の課題正答率ゲートを取り直す。

indexer / argpartition は prefill では 1.2% (kv > 8k の merge 分は 0.07%) で案なし。

- 4k: 末尾チャンクを layer-major のグループに入れて MoE を 4000 行 1 回に (専門家あたり 40 → 80 行)。
順: P5 / P6 (小物) → K1 の設計と前提確認 → 4k の末尾 → 小さいベンチ → K2 → 融合カーネルが decode で負ける理由の 1:1 テスト。

## 4k の末尾チャンク (scout 2026-09-03 09:50)

- 4000 トークンは「端数 1952 を g=1 のグループ + 末尾 2048 を chunk 主導」に割れる (`spec_flash.py:2057-2087`、`_PREFILL_TAIL_CHUNKS=1` が末尾を常に予約除外)。
  1 トークンあたりの費用は群 1.70 ms / 末尾 1.73 ms で差 2% (CATCHUP 19:30) — 「末尾が高い」は否定済み。残るのは MoE の行数効果だけ
  (1825 → 3873 行、M/E 36 → 75)。見込み 4k **-3〜-5%**。
- 末尾が chunk 主導な理由は 2 つ: (a) lm_head (と最終 mixer) を chunk 主導分岐だけが計算する (`spec_flash.py:2208`、`_group_prefill_forward` には無い)、
  (b) BPE 境界の checkpoint 分割 (`prefill_common.py:32`) が chunk 主導にしか無く、層主導の内側では checkpoint を刻めない (構造的制約)。
- 入れるには: グループの最終メンバーだけ mixer + lm_head を通す処理を `_group_prefill_forward` に足し、末尾 checkpoint は諦める (2 ターン目の LCP が
  checkpoint の 1 トークン手前に落ちる場合の再計算が増える)。`_group_prefill_forward` は不揃いの行数で動く (fold-tail が既に使っている)。
- 進め方: knob (`MLXTURBO_PREFILL_TAIL_CHUNKS=0` 相当) で 4k の冷 prefill を A/B し、既定にするかは温 TTFT の小さいベンチと合わせて決める。
  D1 のエージェントが `spec_flash.py` の同じ関数 (generate_stream) を編集中なので、D1 の A/B が終わってから着手。
- D3 (文脈 n-gram の draft): 畳む。17k -2.1% / 50k -2.6% が上限 (発火率 21〜25%、一致長 5+ でも累積受理が浅い)。K2 で行が安くなったら再計算。(09:45)

## K1 の設計調査の結果 (fable 2026-09-03 10:05、メモは scratchpad/flash-attn-d256-design.md)

- **QSA の意味論**: 「dense に見える現チャンク」は無い。sparse 域 (kv > 2048) の全行は「完全ブロックから top-512 ∪ kv 末尾の端数列 ∧ causal」だけを見る。
  チャンク幅が効くのは先頭呼び出しの dense ゲート (kv ≤ 2048) だけで、**先頭 2048 以下 + 以降 8192 (4 の倍数) なら chunk 2048 と同じ可視集合**。
  ただし attention の費用は行数比例なので、8192 化の取り分は attention には無く GEMM 効率と境界だけ。
- **K1 の mask arm は取り分が小さい**: 64 行タイルの可視 union は 32 キー粒度でほぼ 1 (相手も "skips ~nothing")。kv ≥ 8k では dense causal と同じ仕事量で、
  fallback (実効 10 TFLOPS) との差は現チャンクの上三角 + 実体化ぶんだけ。見込み 4k -1.3〜-2.0%、17k -0.4〜-1.1%、50k -0.3%。**flash の「skip」は死に筋。**
- **attention のレバーは gather カーネルの作り直し**: 現行 T=1 gather は load が 65〜70% (151 GB/s = 38%)、相手の gather も 229 GB/s (42%) で同程度。
  uint4 + mma 16 行 + load/compute の重ね合わせで kv ≥ 8k を ~33 ms/層に (現行 56〜59、fallback 8k 40.8) → 17k -3〜-4%、50k -5%。P6 の延長線。
- **品質側の発見 (K1 より大きい可能性)**: mlx-serve と mtplx は QSA の tail を「クエリごと (自分の未完成ブロックの列を見る)」で実装し HF と一致を主張。
  うちは global tail のみで、sparse 域の 3/4 の行が自分自身 (と自分のブロックの列) を見ていない可能性。タイの扱い (torch.topk は小さい添字) も未対応。
  **HF の参照実装で確認する** (要 scout)。品質の物差し (bf16 参照) がうちの vendor 実装なら、この差は物差しに映らない。
- proof-of-life は arm A (causal のみ、S=2048、kv=2048、10.5 → 6.5 ms 以下) だが、上の見込みから **優先度を下げ、gather 作り直し (P6 延長) を先に**。

Commit の追記 (2026-09-03 09:55、ユーザー): K1 の調査結果の方針に同意。**QSA の tail 意味論の確認 (品質) を速度より先に**、attention の速度は
gather カーネルの作り直し (P6 延長) で、flash の mask arm は後回し。チャンク 8192 は GPU 稼働率の測定を見てから。

## K2 の設計調査の結果 (fable 2026-09-03 10:10、メモは scratchpad/decode-qsa-attn-design.md)

- decode 幅の sdpa は MLX の `sdpa_vector_2pass` で、各 simdgroup が全キーを stride で回り毎回 `bmask` を device から読む (17k で 1024 threadgroup × 12S × 33 回の依存ロード) —
  これが sdpa 153 us/層の主因。argpartition は GPU では全ソート (安定、同点は index 昇順)。**相手は decode 幅を融合していない** (K2 は構造的な先行になる)。
- 層あたり (17k、S=2): indexer 235 + マスク 6 + sdpa 153 + 射影系 200 ≈ 595 us。融合で消えるのは argpartition 系 + マスク組み + sdpa の分割 + 25k 以上の gather tile 一式 (25〜40 本 → 3 本)。
- **K2a (1 dispatch)**: einsum 出力 (S, n_blocks, 4) を入力に relu/sum/visible を再現し、radix select (4 pass × 256 bin) で閾値、`>t` 全部 + `==t` を index 昇順で不足分 → argpartition と同じ集合。~20 us/層。
- **K2b (2 dispatch, mirror)**: MLX 2-pass vector の写しで、`bmask` の device 読みを threadgroup 常駐のビットマップ + tail 規則に替えるだけ → ビット一致を狙う。17k S≤2 で ~30 us、S=3〜4 で ~45 us。
- 見込み T(S) (短文脈): S=1 25.2 → 22、S=2 33.1 → 25.5、S=3 39.8 → 29、S=4 47.1 → 32.5。17k: S=2 39.3 → 30.5、S=3 47.9 → 34.5。
  depth 2→3 が短文脈で通り (閾値 5.3 ms)、17k は depth 1 → 2 に反転。行あたり attention 4〜5 → 1 ms 未満、MoE の重み読み ~3 ms/行が床。
- PoL-0 (今日): K2 全体の天井スタブ (固定 slice + 末尾 2048 列の causal sdpa 1 回) を `--knobs` に足す。1.5 ms/round 未満なら畳む。
  PoL-1 (2〜3 h): K2a + 検証器 (同点・-0.0・-inf・可視<k を含めて集合 100% 一致、17k S=2 で ≤30 us)。PoL-2: K2b mirror の `mx.array_equal` (S 1..4、kv 4k/17k/25k/50k)。
  PoL-3: `verify_width_cost` で 1 行の追加費用 短 ≤4 ms、17k ≤5 ms。
- 危険: 同点規則、attention の 1 ulp 差が verify の argmax を割る前例 (prefill_attn で tok/round -0.7%)、NAX 機は blocks 表が分岐 (`MLX_SDPA_BLOCKS` で釘付け)、
  batch.py / batch_spec.py の差し替え検知で退く、`_final_mask` の口は保つ、可視集合は本家の写し (tail の意味論の確認結果を反映する)。
- D1 (draft 1 段目を verify に同梱): 畳む。ms/round +1.7〜1.8% (温まった位置)。隠れていた MTP の仕事を同期の壁に出しただけ。D2b は前ラウンドのマージンか 0.3 ms の同期で。(10:15)
- D2b (マージンで 2 段目を省く): 畳む (K2 の後に再計算)。1 ラウンド遅れの信号は AUC 0.567、同期案は D1 と同じ費用構造で相殺。(10:20)

## QSA の tail の意味論: HF 参照と食い違い (確定、2026-09-03 10:30)

HF transformers main の `models/qwen4_exp/modeling_qwen4_exp.py` (`Qwen4ExpTextQSAIndexer.forward`) を取得して確認:
- `local_visible_indices = nonzero(attention_mask[b, 0, q])` = そのクエリが causal で見える位置 (0..q)。
- `num_complete_blocks = len(visible) // ratio`、ブロックはその visible を 4 個ずつに切ったもの (絶対位置に整列、うちの `block_end <= q_col` と同じ)。
- **`tail = visible[num_complete_blocks*ratio:]` をそのクエリの可視に必ず足す** = 位置 4·floor((q+1)/4) .. q (自分自身を含む、0〜3 個)。**クエリごと**。
- `scores.topk(min(block_topk, num_complete_blocks), dim=0)` (torch.topk、同点は mlx-serve の検証では小さい添字を残す)。
- dense ゲートは無い (kv ≤ 2048 なら全ブロックが選ばれるので結果として dense)。
うち (`_vendor/qwen4_exp.py:509-522`、`_gather_tile_attn` 754-758、`batch.py:458-469`) は **global tail (kv 末尾の端数列) ∧ causal** だけ。
S=1 の decode (最終行) は一致するが、S>1 の行 (prefill の全行、verify の非最終行) では (q+1)%4≠0 の行が自分自身と直前 0〜3 トークンを見ていない。
prefill では 3/4 の行、verify では非最終行がこれに当たる。**verify 行の logits が自分自身を見ずに受理判定している**ので、受理率にも効いている可能性。
mlx-serve は per-query tail と同点規則を HF と比較して合わせ済み。

対応 (品質の修正、速度より先): `MLXTURBO_QSA_TAIL=query|global` (既定は検証後 query) を vendor のシーム (`_pooled_and_top` の keep、`_final_mask`)、
`_gather_tile_attn`、`batch.py`、`prefill_attn.py` の gather カーネル (tail 規則) に入れ、呼び手 3 つを全部直す。同点は小さい添字を残す (serve と同じ bias)。
検証: S=1 decode はビット一致 (不変)、HF の規則を numpy で書いた参照と可視集合が一致、in-model で tok/round (受理率) と長文脈の課題正答率、
KLD は teacher (bf16、同じ vendor) を作り直してから。K2 の設計も per-query tail に合わせる。
- 追記 (10:55): oMLX の vendored `qsa_fast.py:642-648` も per-query tail (`complete_counts[p]*ratio` 以降)。dense ゲートはうちと同じ `kv_len <= budget`、同点は argpartition のみ。
  HF / mlx-serve / oMLX の 3 実装が per-query で一致、global tail はうちだけ。

## prefill の追加の方向 (2026-09-03 11:00、ユーザー「末尾グループ化と gather 以外に何がある?」)

理想との差: 1 チャンク 2048 tok ≈ 14 TFLOP を 3.6 s = 実効 4 TFLOPS (bf16 天井 ~14 の 3 割)。差の半分は 4-bit qmm の上限 (10〜11 TFLOPS) で相手も同じ壁。
- **P7 MoE の行列積以外**: MoE 48 層 2041 ms のうち行列積 1238 ms、残り **約 800 ms (チャンクの 2 割) が未測**。router (fp32 GEMM + softmax)、top-k、argsort、
  x の gather、SwiGLU、scatter/合成、共有専門家。`tools/moe_split.py` で内訳 (Sonnet 作成中) → grouped GEMM のエピローグに SwiGLU / router 重み / scatter を畳む。見込み -10% 級。
- **P8 dense 射影を bf16 GEMM で**: GDN / attention / HC の射影はチャンクの半分で全部 4-bit qmm。層ごとに `mx.dequantize` して `mx.matmul` (12〜13 TFLOPS 級?) なら
  15〜20% 速い可能性。戻す費用は 5 GB/チャンク = 12 ms。`tools/dequant_gemm_micro.py` (Sonnet 作成中)。見込み -5〜10%。
- **P9 チャンク 8192**: 先頭 2048 以下 + 以降 8192 で QSA の可視集合は同じ (K1 メモ)。P5 の行タイルでスコア行列のメモリが抑えられるので flash カーネル無しで可能。
  全 op が M=8192、境界 1/4。17k 以上で -4〜8%、4k は不変。P7 / P8 の後に末尾グループ化と同じ場所へ。
- 境界の泡 (GPU 稼働率、測定待ち) 0〜-2%、HC の elementwise は床の 1〜2 割増しで ≤2%。

Commit の追記 (2026-09-03 11:05、ユーザー): 「やるべき」。prefill は P7 / P8 → P9 → **P10 (4-bit のまま BM=64 タイルで逆量子化を 2 倍償却する自前 qmm)** の順で 1.5 倍を取りに行く。
decode は K2 + HC (負けの原因が取れれば) + depth 3〜4 で 2 倍を狙う。

## 後でやる: ANE (Apple Neural Engine) の利用 (2026-09-03 11:30、ユーザー「あとでやるところに記録」)

価値の見立て (この機 M3 Max、ANE 16 コア fp16 約 18 TOPS = GPU と同じ桁、GPU と並列に回せる唯一の追加計算力):

2. 共有専門家 (チャンクの 3%、ルーティング非依存): 配管が最も簡単で API の動作確認を兼ねる最初の 1 手。

費用: 公式 API は CoreML だけ (静的な形でモデルをコンパイル、入出力は MLMultiArray 経由のコピー、Metal のバッファと共有できない)。
直叩きは私的フレームワーク (oMLX が使っている経路、OS 更新で壊れうる) か、自前でその層を書く必要がある。重みを fp16 で別に持つのでメモリ +数 GB。
NAX 機では GPU の GEMM が 3〜4 倍速くなるので ANE の相対価値は下がる (この機向けの手)。
判断: GPU 側の手 (P6〜P10、K2) が頭打ちになってから。着手するなら oMLX の実装 (`~/dev/omlx`) を読む scout から。

Commit の追記 (2026-09-03 11:20、ユーザー): ANE は「基本的に 2 (共有専門家で API の実現性) → 1 (dense 射影をチャンク跨ぎで重ねる)」の形でやる。

ANE の scout 結果 (2026-09-03 11:30、oMLX `omlx/custom_kernels/qwen35_prefill/`、`docs/experimental/qwen35_ane_prefill.md`):
- 入口は CoreML ではなく私的フレームワーク `AppleNeuralEngine.framework` を dlopen + objc_msgSend で直叩き (MIL テキストを手書き生成)。署名や entitlements の記述なし。

## 最終ゴール (2026-09-03 11:35、ユーザー): 短文脈で 100 tok/s。MTP 頭の学習はしない。

算数 (受理率は今の 0.72 のまま): ms/tok 10 = 1 ラウンド (verify 幅 S=5、depth 4、期待 2.88 トークン) を 29 ms 以内。
- S=1 forward 24 → **17 ms 以下** (K2 で attention 8 → 4、HC 4.7 → 2、残り小物 1)。
- 行の追加費用 7 → **2.5 ms 以下** (K2 で attention の行費用を 1 ms 未満に、MoE の異なる専門家の読み増分 ~1.5 ms は残る)。
- draft 3 ms は次ラウンドの構築と重なって隠れる (D1 の知見)。
→ 17 + 4 × 2.5 = 27 ms、+ 隠れきらない分 2 ms = 29 ms = 100 tok/s。受理率が tail 修正で 0.75 に上がれば余裕が 5% できる。
必要な順: K2 (attention と行費用) → custom kernel の負けの原因 → HC 作り直し → depth を 4 に (DepthController の費用表を K2 後に取り直す)。

## 机上の見込み: 同じベンチを M5 Max / M5 Ultra で (2026-09-03 11:45、純粋な算数、±20%)

前提: NAX で行列積 3〜4 倍、帯域 400 → 600 GB/s (Max) / 1.2 TB/s (Ultra)、行列積以外の小物 1.3 倍、P3 / P10 は off、gather / GDN Metal は取り直し。
| 項目 | この機のゴール | M5 Max | M5 Ultra |
|---|---|---|---|
| 冷 prefill 17k | 22 s | 7〜8.5 s | 4〜5 s |
| 冷 prefill 50k | 61 s | 20〜24 s | 11〜13 s |
| decode 短文脈 | 100 tok/s | 140〜150 | 200〜230 |
| decode 17k | 60 | 85〜95 | 130〜150 |
prefill は計算律速で NAX とコア数がそのまま効く。decode は帯域と op 起動遅延の律速で、Ultra ではダイ跨ぎの同期が小さいカーネルに不利。
M5 で価値が増す手: P7 (MoE の行列積以外)、P9 (チャンク 8192) — GEMM が縮む分、行列積以外の比重が 6〜7 割に上がる。
Ultra の真価はバッチ (同時実行) なので、単一リクエストより `batch.py` の伸びが効く (今日の範囲外)。

## custom kernel の負けの正体 (2026-09-03 12:00): 温キャッシュの連鎖 micro
負けは GPU 側。連鎖 micro が重み 1 組を読み回していたので、並列度の低い自前カーネルが冷の DRAM レイテンシを隠せない負け (+78 us/回 × 97) が見えなかった。
CPU 費用・段階投入・command buffer・非連続入力は全部棄却。decode 幅で qmv / qmm を自前に置き換える筋は構造的に不利。判定ゲートは冷の連鎖に。
HC の見込みを -2.5 ms → -0.5〜-1 ms に下方修正。100 tok/s の算数: S=1 forward は K2 で 20 ms 級に留まるので、受理率 0.8 (tail 修正) か行費用 2 ms 以下が要る。

## 後で: Qwen3.8-27B (dense) の速度と RTX 5090 との比較 (ユーザー 12:05、机上)
27B 4-bit ≈ 14 GB。decode は帯域律速で M3 Max (400 GB/s) は素 28 tok/s、MTP 込み 45〜55 が上限。5090 (1.8 TB/s、32 GB) は 4.5 倍 (素 120、投機 200 超)。
prefill は計算力 10 倍差。肉薄しないのが算数で、M3 Max の価値は 128 GB (50k 文脈 + 51B MoE) と温 TTFT。実測は Flash-Next のフルベンチ後 (27B / 35B-A3B、mlx-lm / oMLX 比較込み)。

## HC 第 4 変種 (2026-09-03 12:10、ユーザー「相手は HC で速いのだからやりようがある」)
形: GEMV 2 本 (10240→320→10240、3.3 MB/層) は MLX の qmv のまま (行ごとの threadgroup で冷のレイテンシを隠す)、前後の elementwise (RMSNorm 統計、4 本の混合、
sigmoid、書き戻し) を 1 要素 1 thread の custom kernel 2 本に。dispatch 12 → 4/層で起動の床 4 → 1.4 ms、重み読み 0.8 ms → **HC 4.7 → 2.2 ms 級 (-2.5 ms)**。
以前の mx.compile 版 (-0.4 ms) は RMSNorm (fast op) と reshape をまたいで融合しきれず dispatch が減らなかったと読む。
判定は冷の連鎖 (重み 97 組巡回) で素より 25 us/回以上速いこと → in-model 短文脈 ms/round -4% 以上、出力一致。Opus 実施中。

## 判定の追記 (2026-09-03 12:15)

- **P10 (BM=64 の自前 qmm): 畳む。**冷の最良 0.935 (判定線 0.90)、bf16 常駐 0.90 にも届かない。BM→∞ の漸近 0.85〜0.89 は bf16 の TFLOPS そのもので、逆量子化は 8〜12% しかない。
- **P8 (bf16 常駐): 閉じる。**0.90 から書き戻しを引くと残らない。dense 射影を 4-bit qmm より速くする方向は両腕とも閉じた。
- **P10 の残り (BM=64 タイルを dense 射影に、ビット一致 -5〜6.5%): in-model へ。**判定線 prefill -2%、`MLXTURBO_QMM_WIDE=auto` (非 NAX で on)。
- **P3: 純 BM=16 ではなく mix48 / WM=1 で in-model へ。**MoE 層 -9.9% (r=40) / -5.4% (r=160) 対 seg32。WM=1 だけで r=160 の取り分の大半。判定線 prefill -2%、`MLXTURBO_MOE_GEMM_MIX=48`。
- 計測の運用: 親の A/B が 1 本終わったらエージェントの GPU 待ちを全部先に流す (biglock 3 段、commit 5c220cb)。長文脈の A/B は 1 往復で足りる (50k の 6 本が ±0.3 s)。
- **HC v4 (elementwise だけ融合): 速度は棄却** (冷 -9 us、in-model ms/round 短 +2.4% / 長 +0.1%)。ビット一致の HC 経路として残す。
  tok/round が既定 (HC=kernel) より短長とも +2〜4% 高い手がかりがあり、elem / off / kernel の 1 プロセス A/B で切り分け中。kernel が受理率を削っていれば既定から降ろす。
- 冷連鎖ゲートのバグ: HC 項目が 8bit 既定で符号が反転していた (4bit/gs64 + bf16 inject に修正中)。ゲートを使う前に本番の量子化設定と合わせること。
- **K2b (decode QSA attention カーネル): ビット一致 120/120、置換対象 2.0〜2.7 倍 (17k S=2 -1.7 ms/forward、50k S=6 -9.6 ms)。K2c (配線) へ。**判定線 75 us は未達 (123 us) だが置換対象全体で判定する。
  blocks 64 釘付けで更に 1.3〜1.8 倍 (kv 非依存) の分岐は後回し。K2c は `MLXTURBO_QSA_TAIL=query` が必須。
- **末尾チャンク v2: 4k -4.9% / 8k -3.4%、サーバー経路ビット一致。17k を測って既定へ。**
- **QSA tail (query): 実装 + CPU 検証済 (5 か所)。GPU 3 本 (配列検証 / 17k decode A/B / 17k 正答率) 待ち。既定化には teacher の再生成が要る。**
- **P3 (混合タイル mix48/WM=1) と P10 の残り (BM=64 dense 射影): 8k で -4.3% / -2.6%、ビット一致 → 既定に入れた (14:05)。**17k は確認待ち。
- **K2c 配線済 (既定 off)。**17k の A/B は両側 query で chain95。
- **HC v4: 完全に閉じる (14:55)。**既定の HC=kernel は受理率を売っていない (hc-off 対 既定で tok/round 0.2% 以内、ms/round は既定が速い)。elem の tok/round 差は prefill 幅で軌道が分かれただけ。
  冷連鎖ゲートの HC 項目は 4bit/gs64 + bf16 inject に修正済み (fused 136.5 / plain 61.6 を再現)。
- **QSA tail の query 既定化の判定は課題の正答率で行う (ユーザー 2026-09-03 15:00)。**17k の 12 問 (seed 1、chain96) で query が global を下回らなければ `MLXTURBO_QSA_TAIL=query` を既定にし、K2c の 17k が通っていれば K2c も既定 on。
  KLD の teacher (`qe-ref.npz`) は serve-q24 を global で流した相対参照で、serve-q24 は手元に無い。bf16 の元 (外付け SSD) が挿さったら `bench/teacher_bf16.py` を query で流して絶対参照を作り直す (後日)。
- **末尾 v2: 既定 on (15:35、17k -0.6%)。P3 / P10 は 17k でも -4.0% / -2.5%、退行なし。**
- **P6 MIN_KV 8192: 畳む (10k で -0.8%、判定線 -1%)。既定 12288 のまま。**
- **K2c 17k: ms/round -0.7% (見込み -4.8%)。既定にしない。**天井スタブ (chain96) で切り分けてから、畳むか配線の固定費を削るかを決める。

## Lily (Perplexity) からの取り込み (ユーザー 2026-09-03 16:40: 全部やる)
