## 方向 (prefill)

### P1 — 低占有の op を 2 本目の GPU stream に逃がして隣チャンクの行列積と重ねる
- 一手: `_group_prefill_forward` の層主導ループで、chunk の偶奇 (または GDN の scan だけ) を `mx.new_stream(mx.gpu)` に載せる。
  op も順序も同じで stream 間の依存は MLX の Event が張るのでビット一致。
- 効く理由: scan 3.2 ms + 前処理 1.5 ms + HC の elementwise + PLE + indexer が 1 チャンクの 15% で、どれも占有率が低い。
  同じ 1 stream では op ごとの barrier で直列。見込み -2〜-5%。
- proof-of-life (30 分、モデル無し): stream A に GDN scan の連鎖、stream B に qmm の連鎖。1 stream の和と 2 stream の壁時計を比べる。
  2 stream が 1 stream の 0.95 倍以上なら Apple GPU が compute queue を直列化しており、畳む。
- 最大の未知: Apple GPU が 2 本の compute command buffer を同時に走らせるか。
- 支払うもの: 一時 +1〜2 GB。

### P2 — HC の elementwise を prefill 幅で mx.compile
- 実装済み (`MLXTURBO_HC_PREFILL_COMPILE`、既定 off)。A/B は chain81 で走っている。ビット一致せず (1e-7 の丸め)。

### P3 — MoE の grouped GEMM を自前で書く (カーネルレーン)
- 一手: gather_qmm_rhs がタイル境界で expert ごとにフル BM×BN×K をやり直すのが dense 比 1.19 の正体
  (mlx `kernels/quantized.h` の `affine_gather_qmm_rhs`)。2 段タイルで 40〜160 行のセグメントでも BlockMMA を保つカーネル。
- 効く理由: prefill の唯一の大物で 6〜7%。同じ根拠で T=1 gather を 12k 未満で dense に勝たせれば 17k で約 5%。
- 最大の未知: 2 敗の理由 (ジオメトリ) を超えられるか。工数は日単位。
- 支払うもの: 数日。フルベンチの後に回すのが自然。

## 方向 (decode)

### D0 — 構築か GPU かの切り分け (全案の上限を決める測定)
- `MLXTURBO_STAGE_EVERY=0` (完全直列) 対 2 の短 decode。悪化 15% 未満なら構築は 5 ms 級で CPU 仮説は死ぬ。
  35% 以上なら構築 20 ms 級で、融合カーネルの敗北記録は「呼び出し回数の記録」に読み替わり、
  レーンは融合から「層単位の mx.compile (GDN 36 層、MoE 48 層で共有)」に丸ごと替わる。chain81 で走っている。
- 合わせて測るもの: サーバー経由の 1 リクエストで `[round]` trace を取り、`decode_ab` の 43 ms との差 (detokenize / SSE が GPU 遊びになっていないか)。

### D1 — draft の 1 段目を verify のグラフに同梱する (Scout 2 本が独立に同じ案)
- 一手: `_staged_forward` の直後、`mx.eval` の前に、`nxt_all` の S 行を入力に MTP 層 1 回を因果ブロックで組んで同じ eval に乗せる。
  同期後は hit の行だけ取って残りの段を今の `_draft_chain` で組む。`_prime_accepted_gap` の hit 回の逐次呼び出しが消える。
- 効く理由: eval_done 4.7 → drafts_submitted 7.1 ms の 2.4 ms は GPU に何も無い区間。MTP の重み読みは行数に依らない。見込み ms/round -3〜-5%、tok/round 不変。
  棄却済みの `MLXTURBO_PIPELINE` との違いは捨てるグラフが無いこと (行 ≤ hit は必ず使う)。
- proof-of-life: knob で短 3 本 × 512、出力トークン列と tok/round の一致を先に確認、ms/round -5% で採用、-2% 未満で畳む。
- 最大の未知: M=3 の行が M=1 とビット一致するか (ずれると draft が変わり運に埋もれる)。
- 支払うもの: `_draft_chain` が 2 つに割れる。MTP キャッシュの不変条件が push から trim までの間だけ破れる。

### D2 — depth を定常 EMA 以外の信号で決める (2 つの信号を 1 つの trace で当てる)
- 信号 a (分岐予測器の履歴表): 直近 3〜4 ラウンドの全採用ビット列で表を引く。短文脈で depth 3 が一度も選ばれないのは、
  定常 EMA がバーストと谷を平均するから。コード・引用・定型文の中だけ 3〜4 を引ければ ms/tok -5〜-8%。
- 信号 b (draft の確信度): `_draft_argmax` の top-1/top-2 の差を `_effective_depth` に渡し、マージンが小さいラウンドは depth 1。
  depth 2 の 48% は 2 本目が棄却されて 7 ms 捨てている。半分当てれば -1.7 ms/round。
- proof-of-life (30 分、GPU 1 回): 静的 depth 4 で短 3 本 × 512 を流し (round, depth, hit, margin) を積む。
  オフラインで P(hit≥3 | 直前全採用) − 周辺、マージンと hit の AUC。前者の上昇 0.15 未満、後者 AUC 0.6 未満なら各々畳む。
- 支払うもの: Python 50 行ずつ。短文脈で静的 depth 2 を下回る危険があるので既定 off から。

### D3 — 長文脈で文脈 n-gram (SAM) の draft を MTP の代わりに使う
- 一手: verify 後に SAM を伸ばし、一致長が損益点 (1 行追加の累積受理 > 7/22 ≈ 0.32) を超える k だけ draft を積む。
  一致しないラウンドは今のまま。verify はトークン比較だけなので分布は変わらない。
- 効く理由: 17k+ は depth 1 で tok/round 1.7〜2.0。要約や数字抜き出しで文脈をなぞる区間なら受理 0.85 で k=5 が 14 ms/tok (現行 22)。
- proof-of-life (30 分、GPU 不要): 既存の 17k / 50k の出力に SAM を流し、一致長ごとの真の続きとの一致数を数える。
  長 3 本の予測が -3% 未満ならエンジンに触らず畳む。
- 最大の未知: ベンチ文の一致率。幅 6〜7 の verify 費用が線形 +7 ms で済むか。

### D4 — command buffer の粒度 (MLX_MAX_OPS_PER_BUFFER / MLX_MAX_MB_PER_BUFFER)
- コード変更なし。既定 10 op / 50 MB を 100 / 500 級にして 1 stage (約 78 op) を 1 バッファに収める。
  1 forward あたり 190 個以上の command buffer が乗っている。見込み 1〜3 ms/forward。
- proof-of-life (10 分): `sample <pid>` で MLX の worker スレッド占有率、`tools/verify_width_cost.py` を A B B A の 4 プロセス。
- 支払うもの: 一時バッファの解放が遅れてピークが増える。別プロセス比較になる。

### D5 — verify 行間の専門家の重複を実測して MoE の重み読みを縮める
- 一手: まず `idx` を `_fire` に積んで |union|/(S×top_k) を測る。gather_qmm が行数でなく異なる専門家数でスケールするかを micro で確かめる。
- 重複率 1.5 なら -2.4 ms/round、1.8 超なら死。小重みの専門家を落とす変種は品質を触るので既定では出さない。

### D6 — indexer 228 us/層の内訳 (12 層で 2.7 ms/round)
- 計測のみ: einsum / argpartition / where / put_along_axis を割る。argpartition が 150 us なら前回の k 番目スコアをピボットにした厳密選択で -1.2〜-1.8 ms/round。
  呼び出し 12 回なので融合の Python 実費の危険は HC の 8 分の 1。

## NAX 対応機の扱い (ユーザー方針 2026-09-03 08:30)

この機 (M3 Max) は NAX 非対応だが、本番では NAX 対応機 (M5 系) でも使う。P3 のカーネルは NAX 専用の intrinsic を使わず
simdgroup_matrix の経路だけで NAX 機でも正しく動く形にし、発火は `MLXTURBO_MOE_GEMM=auto|on|off` (auto = 非 NAX で on、
NAX 機では off。MLX 自身の `gather_qmm_rhs_nax` との A/B を NAX 機で取り直すまで既定にしない)。機種判定は 1 箇所に集める。
この機で取った「BM=16 の straddle」「dense 比 1.19」は非 NAX の数字で、NAX 機では MLX の別カーネルが走るので、
NAX 機に着いたら P3 と MoE の dense 比を `--knob` で全部取り直す。他の自前カーネル (gather prefill、GDN Metal) も同様。
