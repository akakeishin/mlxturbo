# decode と prefill を下限まで詰める

前半が **decode (帯域律速)**、後半が **prefill (FLOP 律速)**。下限の出し方が
違うので分けてある。

# やることの現在地 (2026-09-01 時点。ここが最新)

決定済みの方針: **後追い 4 本は全部実装する** (ユーザー決定)。そのうえで
**木構造投機を新しいレーンとして立てる**。ただし木は最も高いので、
**安い判定を 2 つ通してから着手する。**

## 判定 (安い。これが他の順番を決める)

| # | やること | GPU | 何が決まるか |
|---|---|---|---|
| G1 | verify 幅 M ∈ {2,4,8,16} の ms/round 掃引 | 要 | **木の前提**「dispatch 律速なら幅は安い」が成立するか。同時に **MoE の直し方** (`SORT_MIN=16` の谷に verify 幅が乗っているか) |
| G2 | 実受理トレースから木 (ノード 8-16) の期待 tok/round を卓上計算 | 計測 1 回 | 木の取り分。鎖の depth 適応比 **+0.3 tok/round 未満なら木は作らない** |
| G3 | 同時 N 要求での対戦比較 (`bench/vs_mlx_serve.py`) | 要 | **相手の専用カーネルは `B*S==1` でしか発火しない。**同時実行下で非対称が出るなら、畳んだバッチ×投機レーンの評価が変わる |

**G1 で M=8 の ms/round が +25% 以上伸びたら、木の取り分は消える** (fable の
反転条件)。G2 が +0.3 未満でも同じ。**両方通ったときだけ木を作る。**

G3 は木とは独立。安くて、当たれば位置づけが変わる。

## G1 決着 (2026-09-01): 幅は安くない。木は作らない

`tools/decode_ab.py --knob depth --variants 1,3,7,15 --only long --ctx 17000
--prefill-once` (幅 M = depth+1、prefill 1 回使い回し、回文順で順序バイアス相殺)。

| 幅 M | ms/round | tok/round |
|---|---|---|
| 2 | 39.6 | 1.678 |
| 4 | 56.2 (+41.9%) | 2.195 (+30.8%) |
| **8** | **94.5 (+138.6%)** | 2.325 (+38.6%) |
| 16 | 156.4 (+295.0%) | 2.335 (+39.2%) |

**反転条件が発火した。**宣言は「M=8 で ms/round が +25% 以上伸びたら幅は安く
ないと判断する」で、実測は +138.6%。桁で外している。

**さらに tok/round が飽和する。**M=4 → M=16 で幅を 4 倍にして +6.4% しか
伸びない。fable が挙げた「木は対数的にしか伸びない」がそのまま出た形。
**費用 3 倍に対して取り分 6%。**G2 (受理トレースの卓上計算) を待つまでもなく
木の取り分は消えた。

**結論: 木構造投機は作らない。**分布保証つきの多 draft 厳密再帰棄却という、
このレーンで一番高い実装を、測定 1 本で回避できた。

**副産物 1: 現行の既定は正しい。**17k では ms/tok が depth 1 で最小
(23.6ms、depth 3 は +8.5%)。`_depth_ctx_limit` が indexer_budget 超えで
depth 1 に落とす既定の挙動が、実測で裏付けられた。

**副産物 2: MoE の設計判断 (K6) にも答えが出た。**M=4 (添字 40 本) から
M=8 (80 本) で ms/round が +41.9% → +138.6% と跳ねる。top_k=10 なので
M=8 はちょうど `total_inds >= 64` / `SORT_MIN=16` の境界をまたぐ。
**経路が切り替わる谷が実測に見えている。**

## K1/K2 決着 (2026-09-01): どちらも負け。MoE の共有タイルは畳む

**K2 MoE (`MLXTURBO_MOE_VERIFY`) — 反転条件が発火した。**宣言は「同期を消しても
in-model で負けるなら、今度こそカーネルの出来の問題として畳む」。

| | 短文脈 | 長文脈 |
|---|---|---|
| ms/tok | **+15.9%** | **+13.4%** |
| ms/round | — | +11.1% |
| tok/round | **-3.8%** | **-1.9%** |

**遅いだけでなく受理率まで落ちる。**ホスト同期 (`.tolist()` x3) の除去も、
パディング threadgroup の早期 return も、in-model の負けを覆さなかった。
micro でも本家 `mx.gather_qmm` の 233.8us に対し 301.8us。

**「共有タイル v2 が負けたのはホスト同期のせいかもしれない」という仮説は棄却。**
差の出どころは fable のコード実読どおりで、(a) そもそも帯域律速ではない
(本家の読み出し 27MB は 300GB/s なら 90us、実測 234us なので起動・レイテンシ
律速)、(b) 68us のギャップは `_segments_gpu` の 15 本前後の直列小カーネル。
v1 (ホストでセグメント計算、計測ループ外) が 230.3 vs 234.6 で同着だった記録と
整合する。**前処理を外に出しても上限は同着。**

**これで MoE の共有タイル機構は打ち止め。**`docs/BACKLOG.md` の残件 12
(`_segments_gpu` が層あたり 2 回) は、この機構を使わないので直さない。

**K1 HC 書き戻し (`MLXTURBO_HC_WRITE`) — 長文脈で負け。**

| | 短文脈 | 長文脈 |
|---|---|---|
| ms/tok | -0.6% | **+5.2%** |
| tok/round | 一致 | 一致 |

tok/round は完全一致なので純粋に費用の話。**2 op を 1 に畳んで遅くなる**のは
説明が要る。仮説: `mx.compile` は入力の形ごとにキャッシュを引くので、
draft と verify で S が変わる長文脈では引き直しの費用が乗る (短文脈では
depth が 2 で形が安定し、長文脈では depth 1 に落ちて混ざる)。**未検証。**
既定 off のまま。採るなら形を固定するか、短文脈限定にする必要がある。

### 4 本そろっての所見

見に行くのが先で、カーネルを書くのはその後。

## 木構造投機 (G1 と G2 を通ったら)

**実装の本体は速度ではなく分布保証。**素朴な木 + 受理は分布を動かすので、
多 draft の厳密再帰棄却 (SpecTr 系) が要る。ここを緩めたら
「品質を売らない」という看板と矛盾するので、**緩めた実装は作らない。**

既知の障害:

- **GDN の再帰状態は木と相性が悪い。**KV キャッシュと違い分岐ごとに複製か
  再走が要る。`spec_flash.py` の rollback 用 GDN 転記が既にその兆候で、
  簿記コストが分岐数に比例する
- tok/round は幅に対数的にしか伸びない。MTP ヘッドの深部品質が低ければ
  2.0 → 3.0 に必要なノード数は 16-64 に膨れ、そのとき verify はもう安くない
- MoE の expert union は幅に線形に増える帯がある (飽和点は未測 = G1)

**MTP 自体は売りにならない** (相手も持っている。draft rerank に至っては
相手の設計の移植)。木にして初めて差になる。

# decode を帯域まで詰める (MoE / GDN / attention / indexer)

2026-09-01 の解剖 (`tools/decode_anatomy.py`) と帯域下限の突き合わせで、
**decode の 4 部品が全部、達成帯域 393GB/s の下限に対して 18-50% しか
出ていない**ことが分かった。ここはその 4 つを順に詰めるための作業計画。

数字は 17k・width=2 のフォワード 1 回 (壁時計 40.83ms)。1k と比べると、
**文脈長で伸びるのは attention だけ** (MoE +0.6ms、GDN +0.1ms、HC +0.05ms)。

| 部品 | 実測 | 帯域下限 | 効率 | 卓上 | 状態 |
|---|---|---|---|---|---|
| MoE 48 層 | 12.01 ms | 6.0 ms | 50% | **6.0 ms** | カーネル 3 敗 |
| attention (indexer 除く) | 7.59 ms | 1.90 ms | 25% | **5.7 ms** | 未着手 |
| indexer (QSA) | 3.80 ms | 0.13 ms | 3% | **3.7 ms** | 未着手 |
| GDN 36 層 | 6.56 ms | 3.25 ms | 50% | 3.3 ms | 連結射影が未測 |
| HC 97 回 | 4.01 ms | ~0.9 ms | ~23% | 3.1 ms | 融合済み |
| lm_head | 1.98 ms | 0.90 ms | 46% | 1.1 ms | **未解決の謎あり** |
| **未帰属** | **4.89 ms** | — | — | — | 下の注記を読むこと |

**下限の出し方** (達成帯域 393GB/s、実効 4.47bpw = 0.559 B/重み):

| 部品 | 内訳 |
|---|---|
| MoE | (union ~16 専門家 x 3 行列 x 2560x640 + 共有 + router) x 48 層 = 2.4GB |
| attention | KV 414MB (12 層 x 16852 x 2head x 256 x 2 x 2B) + 射影 334MB |
| indexer | 生鍵 52MB (12 層 x 16852 x 128 x 2B) |
| GDN | 重み 1.17GB + 再帰状態 112MB (**書き戻しは数えていない**ので下限は甘め) |
| HC / lm_head | 低ランク重み ~356MB / 語彙 248320 x 2560 = 355MB |

**MoE の union は推定**。実測は「3 トークンで top-10 の union が 21-22/30」で、
2 トークンぶんは内挿した ~16/20。ここは `tools/expert_stats.py` で実測できる
ので、段 5 の最初に測ること。**下限が動けば効率も卓上も動く。**

**「未帰属 4.89ms」を「ディスパッチの隙間」と決めつけないこと。**説明は 2 つ
あって、区別できていない:

1. カーネル間の隙間 (グラフ構築中の GPU 遊休)
2. **単体計測が重なりを再現できていない** — 部品を 1 つずつ呼ぶと、本番で
   重なっているぶんが分離されて和が小さく出る

しかも `tools/decode_anatomy.py` の壁時計は `model(...)` を直接呼んでいて、
**本番の decode が通る段階投入 (`_staged_forward`) を通っていない**。
つまりこの 4.89ms は「段階投入なしの隙間」で、本番の隙間はこれより小さい。
段 6 に着手する前に、まず壁時計側を `_staged_forward` に揃えて測り直すこと。

## 段 1 の結果で、あとの形が決まる

**この計画は QSA の 1 実験を起点にした分岐**になっている。段 2 と段 3 の
中身は段 1 の結果で入れ替わるので、順番を飛ばすと無駄になる。

```
段 1: 17k で QSA を切って measure (--knob qsa)
 │
 ├─ (a) 速くなった × 品質も持つ (KLD 現行比 +0.0005 以内)
 │      → 長文で QSA を切る/budget を上げるのが答え。5ms 級を回収
 │      → 段 2 (indexer の内訳) と B4 (pooled 増分キャッシュ) は **不要**
 │      → 残るのは 段 3'(素の causal を下限へ) / 段 4 / 段 5 / 段 6
 │
 ├─ (b) 速くなった × 品質が持たない
 │      → **QSA は要る。だが「マスクが重い」という仮説は当たり。**
 │      → 段 3 の gather 案 (選ばれたブロックだけ集めて dense sdpa) が本命。
 │        疎性を sdpa に伝えれば、品質を保ったまま同じ 5ms を取れる
 │      → 段 2 は後回し (indexer 自身より、その使い道の方が高い)
 │
 └─ (c) 速くならなかった (3% 以内)
        → 仮説が外れ。attention 本体の 18% は加算マスク以外の理由
        → 段 2 (indexer の内訳) を通常どおり実施し、attention は
          別の容疑者を探し直す (sdpa のカーネル選択、KV レイアウト)
```

(a) と (b) は**どちらも「マスクが重い」の裏付け**で、違うのは品質だけ。
(c) だけが仮説の否定になる。つまり段 1 は「当たり/外れ」ではなく
**「どこを直すかを決める」**実験。

段 4 (GDN)・段 5 (MoE)・段 6 (隙間) はこの分岐と独立に走らせてよい。

## 順序 (取り分 ÷ コスト で並べた)

**先に測る。カーネルから入らない。**3 敗はどれも「micro で勝って in-model で
負けた」ので、まず「なぜ素の実装が下限に届かないのか」を突き止める。

### 段 1. QSA を切ったらどうなるか (取り分 5ms 級、コスト 30 分)

**仮説**: `mx.fast.scaled_dot_product_attention` は加算マスクを渡されても
**全 KV を読んで全スコアを計算する**。つまり QSA の疎性は sdpa 側の節約に
なっていない。だとすると長文の QSA は「indexer の 3.80ms を払って、
attention は 1 ミリも軽くなっていない」ことになる。

attention 本体が下限の 18% しか出ていないのも、16852 列ぶんの加算マスクを
実体化して足す費用で説明が付く可能性がある。

**やること**: `tools/decode_ab.py --knob qsa` (実装済み)。B は
`indexer_budget` を巨大にして早期 return に落とす = 素の causal。

**判定**: 17k decode の ms/token。**出力は変わる** (QSA は full attention の
近似なので、切ると近似が外れる方向 = 品質は上がりうる) ので、速くなったら
**KLD と受理率を測ってから**採否を決める。

**行き先は上の分岐図のとおり** (a) 速い×品質OK / (b) 速い×品質NG /
(c) 速くならない の 3 つ。**反転条件**: (c) = 速度差が 3% 以内なら仮説が外れ。

### 段 2. indexer の内訳を割る (取り分 3.7ms、コスト 半日)

**行き先 (c) のときに実施する。**(a) なら不要 (QSA ごと消える)、(b) なら
後回し (indexer 自身より、疎性を sdpa に伝える段 3 の方が取り分が大きい)。

**内訳の候補**:

| 中身 | 17k での規模 | 増分化できるか |
|---|---|---|
| pooled の作り直し (mean + k_layernorm) | 生鍵 52MB を毎回読み直し、4213 ブロック x 12 層 | **できる** (確定したブロックは不変) |
| pooled への rope | 4213 x 128 x 12 層 | できる (同上) |
| einsum q·pooled | 24 head x 4213 block x 128 x 12 層 | できない |
| argpartition (top-k) | 4213 ブロックの部分ソート x 12 層 x 2 位置 | **できない** (クエリごとに違う) |
| keep マスクの構成 (repeat + concat) | 16852 列 x 2 位置 x 12 層 | できない |

**やること**: 上の 5 つを個別に計時する micro を書き、どれが 3.8ms の主体かを
出す。**pooled が主体なら B4 (増分キャッシュ)、argpartition が主体なら
別の設計** (ブロック数を減らす = compress_ratio を上げる、あるいは
running top-k)。

**反転条件**: 主体が argpartition で、かつ MLX の argpartition が既に
帯域律速なら、ここは畳んで段 3 へ。

### 段 3. attention 本体を下限に寄せる (取り分 6.2ms、コスト 数日)

**行き先で中身が変わる。**

- **(a) QSA を切れる場合 — 段 3'**: 素の causal sdpa で 17k を読む形になる。
  下限 1.05ms に対して実測がいくらかを測り直し、そこからの改善を考える
  (このとき加算マスクは消えているので、残る差は sdpa 自体の効率)。
- **(b) QSA が要る場合 — 段 3 本命**: 疎性を sdpa に伝える経路を作る。
  加算マスクではなく**選ばれたブロックだけを gather してから dense sdpa**
  に渡す (token_budget=2048 なら 16852 → 2048 列 = 読み出しが 8 分の 1)。
  gather の費用 (2048 列 x 12 層の KV コピー = 50MB) を払っても 414MB を
  読むより安い。**MLX の op だけで書ける** (カーネル不要)。
  **出力はビット一致しない** (softmax の対象集合は同じだが加算順が変わる)
  ので、判定は tok/step + KLD。
- **(c) 仮説が外れた場合**: 容疑者を探し直す。候補は sdpa のカーネル選択
  (`docs/research/SDPA-WIDTH-WALL.md` の壁は S=2 では効かないはずだが、
  マスクの型で経路が変わる可能性)、KV のレイアウト、GQA の展開。

**判定**: 17k decode の ms/token + tok/step + KLD。**ビット一致は要求しない** --
(b) の gather 案は softmax の対象集合こそ同じだが加算順が変わるし、(a) は
そもそも別の注意を計算している。
**反転条件**: gather の費用が読み出しの節約を食ったら (実測で 3% 以内なら)
畳んで、そこで初めてカーネルを考える。

### 段 4. GDN の連結射影 (取り分 3.3ms のうち一部、コスト 30 分)

**単独 A/B の記録が無い。**既定 off の理由は「連結で N が変わると qmv の
カーネル変種が変わり、加算順の違いが最終 ulp を動かす疑い (tok/step
2.44 -> 2.23 の低下と時期が一致)」。**時期が一致しただけで犯人扱いされた
可能性がある。**

**やること**: `tools/decode_ab.py --knob wide` (実装済み)。
**判定**: ms/token と tok/round の両方。tok/round が落ちるなら疑いは本物。
**反転条件**: tok/round が 3 プロンプト平均で 2% 以上落ちたら既定 off のまま。

### 相手の GDN を読んだ (2026-09-01、`~/dev/mlx-serve`)

**連結射影そのものは差ではなかった。**相手も既定は qkv/z/b/a を別々に
`qmatmul` で叩いている (`transformer.zig:16016-16018`, `16558-16559`)。
段 4 の掃引は「うちだけが損している」の検証ではなく、単独で得かどうかの検証。

**差は前後の融合で、しかも桁が違う。**

| | うち | mlx-serve |
|---|---|---|
| 再帰カーネル本体 | mlx_lm の移植 | 同じものの移植 + 特化 4 変種 |
| 前処理 | conv1d / silu / rms_norm x2 / スケール x2 / g / beta = **8 dispatch** | **1 カーネル** (`gdnPreworkFused`, `transformer.zig:21969-22165`、既定 on) |
| 後処理 | RMSNormGated 3 op 未融合 (専用カーネルは空振りで off) | **1 カーネル** (`gdnNormGateFused`, `transformer.zig:22279-22370`、既定 on) |
| 状態 dtype | fp32 強制 (`kernels/gated_delta_states.py:239`) | **bf16** (`transformer.zig:16209`) |
| conv1d | MLX 標準 op | decode 幅では prework 内に 4 タップ手書きで吸収、**op ごと消える** |
| decode/prefill の経路 | 同一 | 分岐 (`gdnBlockedEligible`: seq>=64 かつ Dk==128 で blocked-seq。**decode 幅は非該当**) |

再帰本体を除いて、うちは 11-12 dispatch/層、相手は 3。それが 36 層。
`mlxturbo/fused.py` 自身が「Flash-Next の decode は dispatch 律速」と書いて
いる前提に照らすと、GDN が下限の 50% に留まる相当部分はこれで説明が付く。

**RMSNormGated の「空振り」は読み直しが要る。**うちの `enable_rms_norm_gated()`
は 3 op を 1 に畳む**単独差し替え**で、実測で空振りだった
(`runner.py:1156-1157`)。相手の同等機能は**単独では発火しない** — prework 融合
が成立したときだけ動く (`transformer.zig:16345-16350`)。前後に 9 dispatch が
残ったまま 3 を 1 にしても効かないのは、dispatch 律速の系では自然。
記録は「この融合は無意味」ではなく「**単独では足りない**」と読み替える。

**状態 dtype は速度と品質の両方に触る。**fp32 3.1MB/層 → bf16 1.55MB/層。
再帰カーネルは毎ラウンド state_in/state_out を全読み全書きするので、36 層 x 2 で
~223MB/ラウンドが ~112MB になる (393GB/s なら 0.28ms/ラウンド)。ただし
**再帰の累積器を bf16 に落とす**話なので、KLD を測らずに入れない
(受け入れ幅 +0.0005)。相手がやっているから安全、とは言わない。

**やること (dispatch を削る側が先。取り分が桁で大きい)**:

1. GDN 前処理の融合カーネル (conv1d + silu + q/k の rms_norm + スケール +
   conv 状態更新 + g + beta を 1 つに)。decode 幅限定でよい
2. 1 が入った状態で RMSNormGated を再測 (空振りの再審査)
3. 状態 bf16 は速度 A/B と KLD をセットで。1・2 とは独立に測る

**反転条件**: 1 を入れて in-model の GDN 部品時間が 10% 以上縮まなければ、
「dispatch 律速」という前提そのものを疑い直す (xctrace で泡を見る)。

### 段 5. MoE の診断 (取り分 6.0ms、コスト 数日〜)

**カーネルから入らない。**3 敗 (moe_glu v1-v3、共有タイル v2、moe_route) は
どれも「micro で勝って in-model で負けた」か「単に遅かった」。今度は
「なぜ**素の** `gather_qmv_fast` が下限の 50% なのか」から始める。

**測ること**:

1. decode 幅の実形状 (M=2、E=512、union ~16、K=2560/640) で
   `gather_qmv_fast` / `gather_qmv` の単体帯域
2. **同じバイト数を密の `quantized_matmul` で読んだときの帯域**
3. 差が gather の添字コストか、MLX の 4bit qmv 自体の天井か

**分岐**:

- 密が 90% 出て gather が 50% → **添字が犯人**。専門家の重みを連続領域へ
  集めてから密 qmm に渡す案が成立しうる (コピー費用と要相談)
- 密も 50% → **MLX の 4bit qmv 自体の天井**。彼らのカーネルが 1.4 倍速い
  という既知の事実と一致し、ここは「彼ら級の qmv を書く」多日レーンになる

**この段だけは、結論が「多日レーン」でも構わない。**そのときは何を書くべきかが
確定するのが成果。

### 決着 (2026-09-01、micro 実測 + 相手のソース読解)

**micro の結果** (`tools/micro_moe_gather.py`、decode 幅 M=2、union 16、4bit gs=64):

| | us | GB/s | 下限比 |
|---|---|---|---|
| gate/up (K=2560->N=640) gather | 54.1 | 242 | 61.6% |
| gate/up 密 | 36.8 | 356 | **90.6%** |
| down (K=640->N=2560) gather | 94.3 | 139 | 35.4% |
| down 密 | 59.6 | 220 | **56.0%** |

**gate/up は密なら 90% 出る**ので MLX の 4bit qmm 自体は良い。gather の添字が
1.47 倍の費用。**down は密でも 56% しか出ない。**

**相手のソースを読んで分かったこと** (`~/dev/mlx-serve/src/transformer.zig`):

1. **相手の専用カーネルは `B*S==1` (純粋な単一トークン decode) にしか効かない。**
   投機の verify 幅 (B*S>1、M=2..4) では**相手も MLX の `gather_qmm`/`gather_mm`
   を使っている** (`do_sort = B*S > 1 || total_inds >= 64 || has_expert_bias`)。
   **うちの主戦場では op は同じ土俵。**カーネルの有無ではなく、その手前の差。
2. **融合の数**が違う。相手は decode で最大 **2 dispatch** (gate+up+SwiGLU 融合、
   **down + ルータ重み乗算 + top-K reduce まで融合**)。うちは gate/up/down が
   別々の 3 dispatch + reduce を `SparseMoeBlock.__call__` で別途。
3. **K=640 の扱い。**MLX の `gather_qmm` は `K%512!=0` だと "qmv_fast" の対象から
   外れて遅い汎用経路に落ちる (うちの `moe_verify_gather.py` のコメントに実測付きで
   書いてある)。相手のカーネルは K のブロック分割に非依存なので**最初から
   踏んでいない**。密 56% の説明になる。
4. **共有専門家は両者とも「別立てが勝つ」**に着地している (うちの
   `enable_moe_shared_fold` は verify +1.8ms で不採用)。ここは差にならない。

### 過去の敗北の原因が 1 つ特定された (共有タイル gather v2)

`mlxturbo/kernels/moe_verify_gather.py` は、呼び出し口で毎回
**`idx_sorted.tolist()` を叩いている** (379 / 575 / 761 行)。**これは
GPU->CPU の同期点**で、decode の毎トークン・毎層で発生する。相手の経路には
どこにも存在しない。

**共有タイル v2 が in-model で +46〜52% 遅かったのは、カーネルの出来ではなく
これかもしれない。**48 層ぶんの同期が毎ラウンド乗れば、その桁の差は出る。
「micro で勝って in-model で負けた」の典型的な形でもある。

**やること**: ホスト同期を消して測り直す (セグメント境界の計算を GPU 側に
移すか、同期を 1 ラウンド 1 回に畳む)。**これは負の結果の再審査**であって、
新しいカーネルを書く話ではない。反転条件: 同期を消しても in-model で負けるなら、
今度こそカーネルの出来の問題として畳む。

### 段 6. 未帰属の 4.89ms

部品和 35.95 に対して壁時計 40.83。1k では 26.57 に対して 32.68 で、
**未帰属は短文脈の方が大きい** (6.11ms vs 4.89ms)。

**着手の前に 2 つ片付ける** (上の注記):

1. `tools/decode_anatomy.py` の壁時計を `_staged_forward` に揃える。いまは
   段階投入なしの `model(...)` を測っていて、本番より隙間が大きく出る
2. 「隙間」と「単体計測が重なりを再現できていない」を分ける。分ける手は
   xctrace の GPU タイムライン (前回 7.3ms の泡を特定したのと同じ道具)

そのうえで `--knob stage-every` を回す (実装済み、コスト 30 分)。掃引が
16→2 で単調改善のまま端点で打ち切られていて **1 が未測**、しかも短 decode の
probe でしか測っておらず 17k は未測。

**HC の 23% の内訳が読めた (2026-09-01、相手のソース読解)。**読み側は既に融合
済みで相手と同格 (うち 2 カーネル `kernels/hyper_connection.py:183-368` 既定 on、
相手 3 カーネル `transformer.zig:23951-24127`)。**手を付けていないのは書き戻し側。**
`DecoderLayer._combine` (`_vendor/qwen4_exp.py:1299-1304`) は
`hyper + (x[..., None, :] * inject[..., None]).reshape(...)` を生の mx 演算で
呼んでいるだけで、`mx.compile` も専用カーネルも無い。attn/mlp で層あたり 2 回、
**96 回 x 2 op**。相手は `compiled_hc_write` の 1 カーネルにしたうえ、
decode/verify 幅 (<= 16 行、`HC_FUSED_MAX_ROWS`) では**書き込み自体を遅延**して
次の `hcRead` の N カーネルに畳み込み、**書き戻しの dispatch を 0 にしている**
(`transformer.zig:11538-11549`, `23979-23988`)。

**やること**: まず `_combine` を 1 カーネル化する (`mx.compile` で足りるか、
`hyper_connection.py` に 3 本目を足すか)。遅延畳み込みはその次。
**反転条件**: 1 カーネル化して in-model が動かなければ、96 回という回数自体が
効いていないということなので、HC は 23% のまま畳む。

**HC と lm_head もここに関係する。**どちらも下限の 23% / 46% で、合わせて
4.2ms が卓上にある。lm_head は「M=3 で 164GB/s、fast_qmm が適格なのに
in-model で負ける」という未解決の謎が既にあり (`docs/BACKLOG.md`)、
depth 既定が 1 に変わって M=2 になったので**前提そのものが変わっている**。

# prefill 側 (17k、対 mlx-serve で唯一残った明確な負け)

decode と違って prefill は **FLOP 律速**なので、下限は帯域ではなく
**密の 4bit 行列積の実測上限 11.2 TFLOPS** で出す。

## まず: いまの部品時間は古い

手元にある解剖は **moe 15.0 / gdn 9.4 / attn 9.0 / hc 5.5 / ple 2.3
(部品和 41.2s、壁 42.7s)** だが、これは **layer-major prefill を入れる前**の
ビルドの数字。現在の壁は 32.4-32.9s (実文プロンプトでは 35.6s) で、
**24% ぶん古い。**

しかも当時は「部品の絶対時間」しか出しておらず、下限と効率を入れていない。

**最初に書いた効率表は誤っていた (fable-advisor 指摘、訂正済み)。**
attention の下限を「QSA 込み」(1 クエリ最大 budget 列) で数えたが、
**sdpa は加算マスクを渡されても密の全スコアを計算する** -- これは他ならぬ
このリポジトリの実測で確定している (`_vendor/qwen4_exp.py` の該当コメント)。
つまり現行実装が実際に回している FLOP は密の因果であって、疎ではない。

| 部品 | 実測 (古い) | いま回している FLOP | 実効 | 疎性を刈れたときの FLOP |
|---|---|---|---|---|
| MoE 48 層 | 15.0s | 88.2 T | 5.9 TFLOPS | — (疎性の話ではない) |
| **attention 12 層** | 9.0s | **62.9 T** (密因果 42.6 + 射影 20.3) | **7.0 TFLOPS** | **30.0 T** |
| GDN 36 層 | 9.4s | 70.9 T | 7.5 TFLOPS | — |
| HC | 5.5s | 未算出 | — | — |
| PLE | 2.3s | 未算出 | — | — |

**読み方が 180 度変わる。**attention は「実装効率が悪い」のではなく
(7.0 TFLOPS は MoE の 5.9 より上)、**QSA の疎性が計算削減に一切化けていない。**
密 62.9T を 9.0s で回していて、疎性を実際に刈れれば 30.0T で足りる。
**差は最大 4-5s** で、これが prefill に残る単一で最大のレバー。MoE に残る
上積みより大きい。

**合計の「効率 41%」は使わないこと** (fable 指摘)。11.2 TFLOPS は 4bit qmm の
実測上限であって、sdpa のスコア (fp16 稠密) にも GDN の再帰 (行列積ではない)
にも別の天井がある。部品別の結論 (MoE は曲線の上、attention は刈り残し、
GDN はほぼ天井) は生きるが、1 つの数字に潰さない。

## 段 P0. 現行ビルドで解剖し直す (先にこれ。他は全部この上に乗る)

`tools/decode_anatomy.py` は decode 専用 (width=2 の 1 フォワード)。
**prefill 版が無い。**同じ作法 (実キャッシュ、部品和 ≈ 壁の確認、下限と効率を
併記) で prefill 版を書き、現行ビルドで測り直す。

- 部品は moe / gdn / attn / indexer / hc / ple / embed に分ける
  (**indexer を attention から分けること** -- decode では長文ペナルティの 43%
  だった。prefill でも分けないと同じ見落としをする)
- チャンク幅 2048 の 1 チャンクを 1 単位として測る。チャンク番号で費用が
  変わる (kv が伸びる) ので、**先頭・中間・末尾の 3 点**を取る
- HC と PLE の下限も出す (いま未算出)

**反転条件**: なし (測るだけ)。ただし**この結果が出るまで下の段に着手しない。**
古い数字の上に計画を積むと、depth の一件と同じことになる。

## 段 P1. prefill の attention -- タイル分割 gather (卓上 4-5s、最大のレバー)

**「prefill には gather が効かない」という当初の却下は早計だった** (fable 指摘)。

却下の根拠は「1 チャンク 2048 クエリの和集合はほぼ全ブロックになる」だったが、
これは **2048 クエリ全体で見た観測**にすぎない。gather の成否は**タイル幅の
関数**であって、経路そのものの不成立ではない。

budget はクエリあたり 512 ブロック (kv 16852 なら選択率 12%)。**隣り合う
クエリの選択は強く相関する** (局所窓 + 少数のグローバルブロック) ので、
タイル 128-256 なら union が kv の 20-40% に縮む余地がある。

**順序を変えた (実装が小さいので、代理指標より本物を先に測る)。**

当初は「union/kv_len を測ってから実装を決める」段取りにしていたが、
タイルループは既存の `_gather_forward` に for を 1 つ足すだけで、
**実装が代理指標の計測とほぼ同じ重さ**しかない。しかも union 比は代理で、
実際に効くかは gather の帯域コストとタイル毎の重複読みを含んだ壁時計でしか
決まらない -- このリポジトリの作法 (「micro の勝ちを採用の根拠にしない、
in-model で決める」) にも合う。よって:

**P1a (実装)**: `_gather_forward` にタイルループを足す。タイル幅は knob
(`MLXTURBO_GATHER_TILE`、既定 0 = 従来どおり S 全体で 1 回)。
S <= タイル幅なら従来経路に落ちるので decode は影響を受けない。
**新カーネルは要らない** -- `take_along_axis` + 小 bool マスク sdpa という
既存の型をタイルごとに回すだけ。

**P1b (計測)**: 実 17k / 50k で **タイル幅 {0, 128, 256, 512} を掃引**し、
prefill の壁時計で判定する。union 比は `_gather_stats` で併記して、
**速くなった/ならなかった理由を読む**ために使う (判定には使わない)。

**反転条件 (先に宣言)**: 17k の prefill 壁時計が改善しないなら捨てる。
union 比が 0.4 を超えていたのが理由なら、そう記録して畳む
(タイル毎の K/V 重複読みがスコア削減を食っている、という説明が付く)。

和の順序が変わるのでビット一致は失う -> 品質側の判定は in-model の
tok/step + KLD。

**補足**: prefill 側の sdpa には decode で入れた細工 (32 行の壁の分割) が
**何も入っていない** (あの分岐は S<=8 限定)。prefill は 2048 クエリで
加算マスク付きの素の sdpa 1 発。手つかずなのは上の結論と整合する。

### 決着: 相手の実装を読んだ (2026-09-01、`~/dev/mlx-serve` のソース)

**mlx-serve は prefill で疎性を実際に刈っている。**`src/transformer.zig` の
コメントが直球で書いている -- *"Prefill gathers them by index; decode/verify
widths (and a declined gather) run under the bool mask"*。つまり
**prefill は集める / decode は bool マスク**で、今日うちが decode 側の実測で
出した交差点の判断と方向が一致する。

だが**やり方が根本的に違う**。

| | mlx-serve (`gatherQsa256`) | mlxturbo (今日の実装) |
|---|---|---|
| 実体 | **融合 Metal カーネル**。1 threadgroup = 1 クエリ x 1 kv head、`BK`(16/32) 行ずつ threadgroup memory に段取りしながら online softmax | `take_along_axis` -> `sdpa` の**汎用 op 2 段** |
| 中間バッファ | **無い** (カーネル内でポインタ演算で直接読む) | `k_sel`/`v_sel` を**実体化**する |
| gather 後のマスク | **作らない** (読む範囲そのものが可視集合。因果性は読む範囲に埋まっている) | union 幅の bool マスクを作って sdpa に渡す |
| タイルの軸 | **キー方向** (`BK`)。クエリ方向のタイルという概念が無い | **クエリ方向**。タイルごとに union を取り直すので**同じブロックを重複して読む** |
| 降りる基準 | **kv 長の絶対値 8192** (実測ラダー: 8k -3% / 16k +4% / 32k +19% / 64k +42%) | union/kv の比 0.20 (実測: 比 24% +1.1% / 16% -6.7% / 8% -15.4%) |
| dtype | bf16 固定。違えば諦める | cache のまま |

**うちの方式には天井がある。**汎用 op を 2 段重ねる限り、選んだ列を
**書いて、読み直して、マスクを作る**費用が必ず乗る。彼らは読みっぱなしで
書きがゼロ。帯域律速の prefill でこの往復が丸ごと差になる。

交差点の位置もそれで説明が付く -- 彼らは kv 10-12k 付近で黒字化するのに、
うちは 18k 付近 (比 23%)。**実体化の費用が交差点を後ろに押している。**

**判断**: prefill の attention を彼らに並べるには**融合カーネルを書くしかない。**
ただし段 5 の方針どおり、**何を書くべきかが確定したのが成果**である:

- 1 threadgroup = 1 クエリトークン x 1 kv head
- キー方向に `BK`(16 or 32) 行ずつ threadgroup memory へ段取り
- online softmax (スコアを全部実体化しない)
- 中間バッファ無し、gather 後のマスク無し (可視範囲を添字演算で決める)
- bf16、head_dim 256 固定で、外れたら既存経路へ落ちる

**decode 側の gather は捨てない。**S=2 では実体化する量が小さく、50k で
-15.4% と実測で勝っている。「汎用 op の 2 段重ねでは prefill 幅に耐えない」
だけであって、decode 幅では成立している。

## 段 P2. prefill の MoE (卓上 7.1s、効率 53%)

layer-major で 1 エキスパートあたりの行数 r=160 まで上げた後の値。
記録の「segment-aware GEMM カーネルの上積みは ≤8%」は**この上のさらに上積み**の
話で、下限までの 7.1s とは別物。

- `MLXTURBO_PREFILL_GROUP` を 4 から 6/8 に上げると r が 240/320 になる
  (効率曲線は r に単調)。**env だけで測れる** (`--knob prefill-group`、実装済み)
- 代償は checkpoint 粒度が g*2048 に粗くなること
  (`MLXTURBO_PREFILL_TAIL_CHUNKS` で末尾側は守れる)
- **反転条件**: 17k TTFT が改善しない、または追記ターンの warm TTFT が 2% 以上
  悪化したら戻す

## 段 P3. prefill の GDN (卓上 3.1s、効率 67%)

連結射影 (`MLXTURBO_WIDE`) は decode 側で測る予定 (段 4) だが、**prefill 幅でも
効くはず**で、そちらは測ったことがない。P0 の後に `--knob wide` を prefill_s で
判定する形で回す。

## 段 P4. HC と PLE (下限が未算出、紙の上で先に埋める)

合わせて 7.8s = 部品和の 19% を占めるのに、**下限を出していない。**
FLOP とバイトを数えるだけならタダなので、**表の穴を先に埋める** (行動は
その結果次第)。HC は prefill 融合が負けた記録があるが、**あれは「あの実装」の
棄却であって HC の理論下限は未計算**。

**PLE / n-gram の直列化** (fable 指摘、未確認): 計測構成で
`FASTMLX_NGRAM_DISK=1` が有効なら、n-gram 行のディスク読みがチャンク処理と
**直列になっていないか**確認する価値がある。直列なら次チャンク分の先読みで
2.3s の相当部分が消える。無効なら無視してよい。

## 段 P5. indexer を attention から分けて数える (P0 の必須項目)

いまの「attn 9.0s」には **indexer 自身のコストが混ざっている**
(fp32 einsum で (B,S,n_blocks,heads) を実体化 + argpartition)。
タイル gather を入れても **indexer は残る**ので、分けて測っておかないと
gather 化後の残差を読み違える。P0 では attention を
**射影 / スコア / indexer / マスク組み** の 4 つに割ること。

# 閾値をマシン非依存にする (段 C: 較正プロファイル)

いま既定に埋まっている閾値は、ほぼ全部 **M3 Max 1 台で測った値**である。
別の機種では動く。「定数の無い式」にはならないが、**式と、そのマシンで測る
少数の原始量に分ける**ことはできる。

## 原始量 (1 台につき 1 回測れば済むもの)

| 記号 | 中身 | 測り方 |
|---|---|---|
| `B` | 連続読みの達成帯域 (GB/s) | 大きい配列のコピー |
| `G` | 飛び飛び読みの効率 (`B` に対する比) | `take_along_axis` を同じ量で |
| `L` | カーネル起動 1 回の費用 (us) | 小さい op を鎖にして差分 |
| `F` | 密 4bit qmm の上限 (TFLOPS) | 大きい `quantized_matmul` |
| `r(rows)` | `gather_qmm` の効率曲線 | 行数を振る (既に `probe_gather_qmm.py` がある) |
| `D` | グラフ構築 1 層あたりの CPU 時間 | 層ループの構築だけを計る |

## 式 (原始量から閾値を出す)

### gather の比はモデルにも依存する (QSA を持つモデルが増えるなら重要)

式が読む `token_budget` / `compress_ratio` はパックから取るので union の
大きさは自動で追随する。だが**比の閾値そのもの**は、gather の効率 `G` に
依存し、`G` は「1 要素あたり何バイト連続で読めるか」で決まる。

KV は `(B, n_kv_heads, kv, head_dim)` なので、kv 軸で集めると連続長は
**`head_dim * 2` バイト**。Flash-Next は 256*2 = 512B。もし `head_dim=128` の
QSA モデルが来れば連続長は半分になり、`G` が落ちて**閾値は前に動く**。

**つまり定数 0.20 は「Flash-Next 系での測定値」であって、QSA を持つ別の
モデルにそのまま持ち込めない。**一般解は下の較正で `G` を直接測り、
`u* = (1 - n*L*B/(kv*bytes)) / (2 + 1/G)` から出すこと。定数はその
フォールバックとして残す (較正結果が無いときはログに出す)。

**gather の比 `u*`** (段 3(b))。密は `kv*bytes/B`、gather は
「集める読み `u*kv*bytes/(B*G)` + 書き `u*kv*bytes/B` + sdpa の読み
`u*kv*bytes/B` + 追加起動 `n*L`」。等号を解くと

    u* = (1 - n*L*B / (kv*bytes)) / (2 + 1/G)

`G≈0.5` なら第 2 項は 4 で、起動項を無視すると `u*≈0.25`。
**M3 Max の実測 0.23 とよく合う。**起動項は kv が小さいほど効くので、
短い文脈ほど閾値が前に来る -- 実測で 17k がちょうど交差点だったのと整合する。

**`MLXTURBO_PREFILL_GROUP`**: `r(rows)` の曲線の膝そのもの。
G を上げると rows が比例して増えるので、`r` が飽和する rows を探して
`rows / (2048 * top_k / n_experts)` から G を出す。**曲線さえ測れば式は要らない。**

**`_STAGE_EVERY`**: 層ループの構築時間 `D` と、`async_eval` 1 回の費用の比。
`every` 層ごとに投げると、隠せる泡は `every * D`、払う費用は `L`。
`every* ≈ max(1, L/D)` が目安。**M3 Max では 2 が最良と出ている。**

**`fast_qmm.M_MIN`**: 密の MMA タイルが stock qmv を上回る M。
stock は M にほぼ比例して重みを読み直すので `M * kv_bytes/B`、MMA は
`kv_bytes/B + FLOP/F`。等号から `M* = 1/(1 - FLOP*B/(F*kv_bytes))`。

## マシンでは決まらないもの (混同しないこと)

以下は**受理率に依存**する = モデルとテキストで決まるので、原始量からは出ない。
機種を変えても値は動くが、それは「マシン依存」ではなく「そのマシンでの
ラウンド費用が変わったから」であって、**測り直しは in-model の掃引でしかできない**。

- **depth の境界**: 1 位置足す限界費用 vs 受理が増える利得。いま
  `indexer_budget` に置いてあるのは**実測の交差点がたまたまそこと一致した**
  からで、機構的な必然ではない。別機種では一致しない可能性がある
- **`PRIME_WINDOW`**: priming の費用 vs 受理率の伸び
- **`MLXTURBO_SORT_MIN`**: ソートの費用 vs 局所性の利得 (添字数に依存し、
  添字数は depth と top_k で決まる)
- **`MLXTURBO_DRAFT_RERANK`**: 粗ヘッドの費用 vs 受理率の維持

## やること

1. `tools/calibrate.py` を書き、原始量 6 つを測って JSON に落とす
2. 実行時にそれを読み、上の式で閾値を出す (無ければ M3 Max の実測値に
   フォールバックし、**その旨をログに出す** -- 黙って他機種の値を使わない)
3. 受理率依存の 4 つは**式にしない**。「掃引が要る」と docs に書き、
   `tools/decode_ab.py` の knob をその手順として残す

**反転条件**: 較正で出した閾値が、実測の掃引で決めた値と 2 割以上ずれるなら、
式が現実を捉えていない。式を捨てて掃引の値を既定にする。

## 作法 (この計画に固有のもの)

- **下限は「達成帯域 393GB/s」で計算する。**理論値 400 ではなく実測の到達値。
- **micro の勝ちを採用の根拠にしない。**3 敗が全部それ。採否は in-model の
  複数プロンプト x 512 平均で決める (`CLAUDE.md`)。
- **段 1 の結果が段 2/3 の存在を決める。**順番を飛ばさない。
- 出力が変わる変更 (QSA off、連結射影) は、速度が勝っても **KLD と受理率を
  測ってから**採否を決める。品質を売って速度を買わない。
