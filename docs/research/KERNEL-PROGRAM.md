# decode を帯域まで詰める (MoE / GDN / attention / indexer)

2026-09-01 の解剖 (`tools/decode_anatomy.py`) と帯域下限の突き合わせで、
**decode の 4 部品が全部、達成帯域 393GB/s の下限に対して 18-50% しか
出ていない**ことが分かった。ここはその 4 つを順に詰めるための作業計画。

数字は 17k・width=2 のフォワード 1 回 (壁時計 40.83ms)。1k と比べると、
**文脈長で伸びるのは attention だけ** (MoE +0.6ms、GDN +0.1ms、HC +0.05ms)。

| 部品 | 実測 | 帯域下限 | 効率 | 卓上 | 状態 |
|---|---|---|---|---|---|
| MoE 48 層 | 12.01 ms | 6.0 ms | 50% | **6.0 ms** | カーネル 3 敗 |
| attention (indexer 除く) | 7.59 ms | 1.90 ms | 25% | **5.7 ms** | 未着手 |
| indexer (QSA) | 3.80 ms | 0.13 ms | 3% | **3.7 ms** | 未着手 |
| GDN 36 層 | 6.56 ms | 3.25 ms | 50% | 3.3 ms | 連結射影が未測 |
| HC 97 回 | 4.01 ms | ~0.9 ms | ~23% | 3.1 ms | 融合済み |
| lm_head | 1.98 ms | 0.90 ms | 46% | 1.1 ms | **未解決の謎あり** |
| **未帰属** | **4.89 ms** | — | — | — | 下の注記を読むこと |

**下限の出し方** (達成帯域 393GB/s、実効 4.47bpw = 0.559 B/重み):

| 部品 | 内訳 |
|---|---|
| MoE | (union ~16 専門家 x 3 行列 x 2560x640 + 共有 + router) x 48 層 = 2.4GB |
| attention | KV 414MB (12 層 x 16852 x 2head x 256 x 2 x 2B) + 射影 334MB |
| indexer | 生鍵 52MB (12 層 x 16852 x 128 x 2B) |
| GDN | 重み 1.17GB + 再帰状態 112MB (**書き戻しは数えていない**ので下限は甘め) |
| HC / lm_head | 低ランク重み ~356MB / 語彙 248320 x 2560 = 355MB |

**MoE の union は推定**。実測は「3 トークンで top-10 の union が 21-22/30」で、
2 トークンぶんは内挿した ~16/20。ここは `tools/expert_stats.py` で実測できる
ので、段 5 の最初に測ること。**下限が動けば効率も卓上も動く。**

**「未帰属 4.89ms」を「ディスパッチの隙間」と決めつけないこと。**説明は 2 つ
あって、区別できていない:

1. カーネル間の隙間 (グラフ構築中の GPU 遊休)
2. **単体計測が重なりを再現できていない** — 部品を 1 つずつ呼ぶと、本番で
   重なっているぶんが分離されて和が小さく出る

しかも `tools/decode_anatomy.py` の壁時計は `model(...)` を直接呼んでいて、
**本番の decode が通る段階投入 (`_staged_forward`) を通っていない**。
つまりこの 4.89ms は「段階投入なしの隙間」で、本番の隙間はこれより小さい。
段 6 に着手する前に、まず壁時計側を `_staged_forward` に揃えて測り直すこと。

---

## 段 1 の結果で、あとの形が決まる

**この計画は QSA の 1 実験を起点にした分岐**になっている。段 2 と段 3 の
中身は段 1 の結果で入れ替わるので、順番を飛ばすと無駄になる。

```
段 1: 17k で QSA を切って measure (--knob qsa)
 │
 ├─ (a) 速くなった × 品質も持つ (KLD 現行比 +0.0005 以内)
 │      → 長文で QSA を切る/budget を上げるのが答え。5ms 級を回収
 │      → 段 2 (indexer の内訳) と B4 (pooled 増分キャッシュ) は **不要**
 │      → 残るのは 段 3'(素の causal を下限へ) / 段 4 / 段 5 / 段 6
 │
 ├─ (b) 速くなった × 品質が持たない
 │      → **QSA は要る。だが「マスクが重い」という仮説は当たり。**
 │      → 段 3 の gather 案 (選ばれたブロックだけ集めて dense sdpa) が本命。
 │        疎性を sdpa に伝えれば、品質を保ったまま同じ 5ms を取れる
 │      → 段 2 は後回し (indexer 自身より、その使い道の方が高い)
 │
 └─ (c) 速くならなかった (3% 以内)
        → 仮説が外れ。attention 本体の 18% は加算マスク以外の理由
        → 段 2 (indexer の内訳) を通常どおり実施し、attention は
          別の容疑者を探し直す (sdpa のカーネル選択、KV レイアウト)
```

(a) と (b) は**どちらも「マスクが重い」の裏付け**で、違うのは品質だけ。
(c) だけが仮説の否定になる。つまり段 1 は「当たり/外れ」ではなく
**「どこを直すかを決める」**実験。

段 4 (GDN)・段 5 (MoE)・段 6 (隙間) はこの分岐と独立に走らせてよい。

## 順序 (取り分 ÷ コスト で並べた)

**先に測る。カーネルから入らない。**3 敗はどれも「micro で勝って in-model で
負けた」ので、まず「なぜ素の実装が下限に届かないのか」を突き止める。

### 段 1. QSA を切ったらどうなるか (取り分 5ms 級、コスト 30 分)

**仮説**: `mx.fast.scaled_dot_product_attention` は加算マスクを渡されても
**全 KV を読んで全スコアを計算する**。つまり QSA の疎性は sdpa 側の節約に
なっていない。だとすると長文の QSA は「indexer の 3.80ms を払って、
attention は 1 ミリも軽くなっていない」ことになる。

attention 本体が下限の 18% しか出ていないのも、16852 列ぶんの加算マスクを
実体化して足す費用で説明が付く可能性がある。

**やること**: `tools/decode_ab.py --knob qsa` (実装済み)。B は
`indexer_budget` を巨大にして早期 return に落とす = 素の causal。

**判定**: 17k decode の ms/token。**出力は変わる** (QSA は full attention の
近似なので、切ると近似が外れる方向 = 品質は上がりうる) ので、速くなったら
**KLD と受理率を測ってから**採否を決める。

**行き先は上の分岐図のとおり** (a) 速い×品質OK / (b) 速い×品質NG /
(c) 速くならない の 3 つ。**反転条件**: (c) = 速度差が 3% 以内なら仮説が外れ。

### 段 2. indexer の内訳を割る (取り分 3.7ms、コスト 半日)

**行き先 (c) のときに実施する。**(a) なら不要 (QSA ごと消える)、(b) なら
後回し (indexer 自身より、疎性を sdpa に伝える段 3 の方が取り分が大きい)。

**内訳の候補**:

| 中身 | 17k での規模 | 増分化できるか |
|---|---|---|
| pooled の作り直し (mean + k_layernorm) | 生鍵 52MB を毎回読み直し、4213 ブロック x 12 層 | **できる** (確定したブロックは不変) |
| pooled への rope | 4213 x 128 x 12 層 | できる (同上) |
| einsum q·pooled | 24 head x 4213 block x 128 x 12 層 | できない |
| argpartition (top-k) | 4213 ブロックの部分ソート x 12 層 x 2 位置 | **できない** (クエリごとに違う) |
| keep マスクの構成 (repeat + concat) | 16852 列 x 2 位置 x 12 層 | できない |

**やること**: 上の 5 つを個別に計時する micro を書き、どれが 3.8ms の主体かを
出す。**pooled が主体なら B4 (増分キャッシュ)、argpartition が主体なら
別の設計** (ブロック数を減らす = compress_ratio を上げる、あるいは
running top-k)。

**反転条件**: 主体が argpartition で、かつ MLX の argpartition が既に
帯域律速なら、ここは畳んで段 3 へ。

### 段 3. attention 本体を下限に寄せる (取り分 6.2ms、コスト 数日)

**行き先で中身が変わる。**

- **(a) QSA を切れる場合 — 段 3'**: 素の causal sdpa で 17k を読む形になる。
  下限 1.05ms に対して実測がいくらかを測り直し、そこからの改善を考える
  (このとき加算マスクは消えているので、残る差は sdpa 自体の効率)。
- **(b) QSA が要る場合 — 段 3 本命**: 疎性を sdpa に伝える経路を作る。
  加算マスクではなく**選ばれたブロックだけを gather してから dense sdpa**
  に渡す (token_budget=2048 なら 16852 → 2048 列 = 読み出しが 8 分の 1)。
  gather の費用 (2048 列 x 12 層の KV コピー = 50MB) を払っても 414MB を
  読むより安い。**MLX の op だけで書ける** (カーネル不要)。
  **出力はビット一致しない** (softmax の対象集合は同じだが加算順が変わる)
  ので、判定は tok/step + KLD。
- **(c) 仮説が外れた場合**: 容疑者を探し直す。候補は sdpa のカーネル選択
  (`docs/research/SDPA-WIDTH-WALL.md` の壁は S=2 では効かないはずだが、
  マスクの型で経路が変わる可能性)、KV のレイアウト、GQA の展開。

**判定**: 17k decode の ms/token + tok/step + KLD。**ビット一致は要求しない** --
(b) の gather 案は softmax の対象集合こそ同じだが加算順が変わるし、(a) は
そもそも別の注意を計算している。
**反転条件**: gather の費用が読み出しの節約を食ったら (実測で 3% 以内なら)
畳んで、そこで初めてカーネルを考える。

### 段 4. GDN の連結射影 (取り分 3.3ms のうち一部、コスト 30 分)

**単独 A/B の記録が無い。**既定 off の理由は「連結で N が変わると qmv の
カーネル変種が変わり、加算順の違いが最終 ulp を動かす疑い (tok/step
2.44 -> 2.23 の低下と時期が一致)」。**時期が一致しただけで犯人扱いされた
可能性がある。**

**やること**: `tools/decode_ab.py --knob wide` (実装済み)。
**判定**: ms/token と tok/round の両方。tok/round が落ちるなら疑いは本物。
**反転条件**: tok/round が 3 プロンプト平均で 2% 以上落ちたら既定 off のまま。

### 段 5. MoE の診断 (取り分 6.0ms、コスト 数日〜)

**カーネルから入らない。**3 敗 (moe_glu v1-v3、共有タイル v2、moe_route) は
どれも「micro で勝って in-model で負けた」か「単に遅かった」。今度は
「なぜ**素の** `gather_qmv_fast` が下限の 50% なのか」から始める。

**測ること**:

1. decode 幅の実形状 (M=2、E=512、union ~16、K=2560/640) で
   `gather_qmv_fast` / `gather_qmv` の単体帯域
2. **同じバイト数を密の `quantized_matmul` で読んだときの帯域**
3. 差が gather の添字コストか、MLX の 4bit qmv 自体の天井か

**分岐**:

- 密が 90% 出て gather が 50% → **添字が犯人**。専門家の重みを連続領域へ
  集めてから密 qmm に渡す案が成立しうる (コピー費用と要相談)
- 密も 50% → **MLX の 4bit qmv 自体の天井**。彼らのカーネルが 1.4 倍速い
  という既知の事実と一致し、ここは「彼ら級の qmv を書く」多日レーンになる

**この段だけは、結論が「多日レーン」でも構わない。**そのときは何を書くべきかが
確定するのが成果。

### 段 6. 未帰属の 4.89ms

部品和 35.95 に対して壁時計 40.83。1k では 26.57 に対して 32.68 で、
**未帰属は短文脈の方が大きい** (6.11ms vs 4.89ms)。

**着手の前に 2 つ片付ける** (上の注記):

1. `tools/decode_anatomy.py` の壁時計を `_staged_forward` に揃える。いまは
   段階投入なしの `model(...)` を測っていて、本番より隙間が大きく出る
2. 「隙間」と「単体計測が重なりを再現できていない」を分ける。分ける手は
   xctrace の GPU タイムライン (前回 7.3ms の泡を特定したのと同じ道具)

そのうえで `--knob stage-every` を回す (実装済み、コスト 30 分)。掃引が
16→2 で単調改善のまま端点で打ち切られていて **1 が未測**、しかも短 decode の
probe でしか測っておらず 17k は未測。

**HC と lm_head もここに関係する。**どちらも下限の 23% / 46% で、合わせて
4.2ms が卓上にある。lm_head は「M=3 で 164GB/s、fast_qmm が適格なのに
in-model で負ける」という未解決の謎が既にあり (`docs/BACKLOG.md`)、
depth 既定が 1 に変わって M=2 になったので**前提そのものが変わっている**。

## 作法 (この計画に固有のもの)

- **下限は「達成帯域 393GB/s」で計算する。**理論値 400 ではなく実測の到達値。
- **micro の勝ちを採用の根拠にしない。**3 敗が全部それ。採否は in-model の
  複数プロンプト x 512 平均で決める (`CLAUDE.md`)。
- **段 1 の結果が段 2/3 の存在を決める。**順番を飛ばさない。
- 出力が変わる変更 (QSA off、連結射影) は、速度が勝っても **KLD と受理率を
  測ってから**採否を決める。品質を売って速度を買わない。
