# D2 結果記録

## D0 診断（2026-08-26 実測）

計測: `bench/mtp_diag.py`（新規）。spec.py の生成ループを K=3 固定・greedy・
lookup 無効で再現し、深度別の受理と hidden RMS を 1 ステップずつ記録する。
モデルは既定の Qwen3.8-27B-MLX-4bit + 非量子化 MTP、プロンプトは gate.py と
同じ code/prose/edit、各 256 トークン、計 322 ステップ。
結果 JSON: `bench/results/mtp-diag-d0.json`。

### 位置別受理率 α_k

| k | 位置一致 match | 連鎖受理 chain | 条件付き cond |
|---|---|---|---|
| 1 | 69.1% | 69.1% | 69.1% |
| 2 | 56.2% | 43.1% | 62.4% |
| 3 | 46.5% | 26.4% | 60.9% |

- **vanilla 崩壊カーブ（k=1 ~70% / k=2 ~11% / k=3 ~2%）に乗っていない。**
  条件付き受理が深度でほぼ横ばい（69→62→61%）で、崩壊ではなく緩い減衰。
  FastMTP が微調整で到達した k=2 56% / k=3 36% に対し、無調整で 43% / 26%。
- プロンプト別の連鎖受理: edit (77/51/30%) > code (65/44/24%) ≈ prose (66/36/25%)。
- MTP 単独の mean_accepted 1.38、tokens/step 2.38。既知の現状値 ~2.2 と整合
  （本番は可変深度 + lookup 併用なので一致はしない）。

### RMS ドリフト（Attention Drift 診断）

| k | RMS(ĥ_k) | RMS(h_true) | 比 |
|---|---|---|---|
| 1 | 1.67 | 5.25 | 0.325 ± 0.079 |
| 2 | 1.90 | 5.28 | 0.365 ± 0.078 |
| 3 | 1.88 | 5.30 | 0.361 ± 0.077 |

- ĥ は膨張ではなく **約 1/3 に収縮**。深度を上げても比はほぼ一定で、
  連鎖による累積的なスケール逸脱は起きていない。
- ĥ の消費先は 2 箇所とも RMSNorm（`MTPModule.pre_fc_norm_hidden` と
  `mtp.norm`）で、RMSNorm はスカラー倍に不変（eps=1e-6 は RMS ~1.9 に対して
  無視できる）。よって **推論時スカラー再スケールは数学的に無効果**。
  ブリーフの「膨張していれば再スケールを先に試す」経路は閉じた。
  `mtp_diag.py --rescale` で実測しても出力は変わらない（不変性どおり）。

### K=5 での追試（同条件、311 ステップ、`bench/results/mtp-diag-d0-k5.json`）

| k | 位置一致 match | 連鎖受理 chain | 条件付き cond |
|---|---|---|---|
| 1 | 64.8% | 64.8% | 64.8% |
| 2 | 55.8% | 39.3% | 60.2% |
| 3 | 44.6% | 22.5% | 57.0% |
| 4 | 43.3% | 13.8% | 60.9% |
| 5 | 34.5% | 6.9% | 50.0% |

- mean_accepted 1.46 → 2.46 tok/step。K=3→5 で +0.09 tok/step しか増えない
  のに、検証幅は m=4 (1.32x) → m=6 (~1.8x) に増える。**無調整の深掘りは損**。
- ただし条件付き受理は深度 5 でも 50〜61% で保たれている。微調整で条件付きを
  70% 台に乗せられれば、深い K は初めて採算に乗る。RMS 比は全深度 ~0.36 で
  K=3 と同じ（スケールは深度に依らず安定）。

### cos 類似度（方向ドリフト、`bench/results/mtp-diag-d0-cos.json`）

| k | cos(ĥ_k, h_true) |
|---|---|
| 1 | 0.586 ± 0.116 |
| 2 | 0.543 ± 0.098 |
| 3 | 0.505 ± 0.103 |

- スケールは RMSNorm で吸収されるが、**方向は全深度で cos ~0.5-0.6 と大きく
  ずれている**。深度 1 からずれているので、微調整の修復対象は連鎖だけでなく
  ヘッド出力そのものにある。k=1 の 69% にも上積みの余地。

### step コスト分解（`bench/mtp_cost.py` 新規、`bench/results/mtp-cost.json`）

ctx=512、非量子化 MTP。**背景 CPU 負荷（別作業のレンダリングが常時 ~100%）
下の計測で、絶対値は汚染されている**（m=1 検証 51.9ms は README 静音値
42.9ms の 1.21 倍）。倍率と桁だけ読む。

- draft 1 本: 4.72ms = MTP ブロック 2.66 + head (norm+lm_head+argmax) 2.17。
  静音換算 ~3.9ms でも、帯域 roofline（ブロック 0.2GB + lm_head 0.31GB ≈
  1.5-2ms）の約 2 倍。ヘッドとブロックがほぼ半々で、lm_head だけの問題ではない
- 検証 m カーブ（capture・head 込み）: m=2 1.33x / m=4 1.89x / m=6 2.49x /
  m=8 3.08x。README の 1.04/1.32/2.33 系列より大幅に悪い。README 値は
  条件が違う（capture 無しの素 forward か）可能性と負荷汚染の両方があり、
  **エンジン実効の m カーブは静音窓で要再計測**。rollback は 0.25ms で無視できる

### D2 計画への含意（advisor 答申 + 実測で確定）

- 受理低下の原因はスケールではなく方向の誤差（cos < 0.7）。訓練ゼロの
  近道は無く、微調整には明確な修復対象がある。
- FastMTP レシピの主眼は崩壊の修復（11%→56%）だが、ここに崩壊は無い。
  同水準（56/36%）へ上げても sum(chain) = 1.62 → 2.62 tok/step 止まりで、
  **K=3 のままではブリーフ目標の 3.5 tok/step に構造的に届かない**。
  D2 の到達点は「2.38 → 2.6-2.8 tok/step（+ D1 EMA 深度制御）」に再定義する。
- 無調整で K を深くするのは損（K=5 で +0.09 tok/step、検証税は 1.32→~1.9x）。
  K=4-5 が黒字化するかは draft 単価 1 数値で決まり、それは静音窓の再計測待ち。
- 対 MTPLX（41.4-44 t/s）逆転に必要な tok/step は現行コスト構造で ~3.0-3.2 と、
  受理側単独では届かない。**主レバーは L1（m カーブ税・draft 単価）で、D2 は
  「step コストを増やさない無料分（+10-14%）の回収」と位置づけ直す**。
  静音窓での要再計測 2 点（draft 単価、capture 込み実効 m カーブ）を
  カーネル側セッションの計測キューに委ねる。
- 微調整の評価は 1k/2.5k/5k サンプルのチェックポイントで α_k 条件付きの傾きを
  見る。平坦ならレシピ棄却、上昇なら増量判断。5k 一発では「効かない」と
  「量不足」が区別できない。
